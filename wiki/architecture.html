Architecture Overview

mem0 is a polyglot monorepo whose center of gravity is the mem0 Python SDK (PyPI mem0ai) and its TypeScript twin mem0-ts. Both ship two usage modes from one import surface: a fully self-hosted Memory/AsyncMemory engine, and a thin hosted MemoryClient that calls the managed platform. The self-hosted engine is wired entirely by configuration: a single MemoryConfig Pydantic model drives four factories that instantiate concrete LLM, embedding, vector-store, and reranker providers behind abstract base classes. Graph memory, once a fifth provider category, has been removed from the OSS core.

The polyglot monorepo

The repository is a single git tree holding multiple independently-published packages across Python, TypeScript/Node, and a Next.js frontend, plus servers, plugins, docs, and benchmarks. Each package has its own build/lint/test toolchain (Hatch + Ruff + pytest for Python; tsup + pnpm + jest/vitest for TS).

mem0/ — Core Python SDK (mem0ai)
The reference implementation. Subpackages: memory/ (the engine), llms/, embeddings/, vector_stores/, reranker/, configs/, client/ (hosted), proxy/, utils/. See the Memory Engine.
mem0-ts/ — TypeScript SDK (mem0ai on npm)
Two entry points mirroring Python: src/client/ (hosted MemoryClient) and src/oss/ (self-hosted Memory, imported as mem0ai/oss). The OSS tree under mem0-ts/src/oss/src/ carries provider parity dirs llms/, embeddings/, vector_stores/. See the TypeScript SDK.
cli/python/ and cli/node/ — command-line clients
Two CLIs, both with entry point mem0: a Typer-based Python CLI (mem0-cli on PyPI, Python 3.10+) and a Commander-based Node CLI (@mem0/cli on npm). The Python CLI takes mem0ai as an optional [oss] extra. See Integrations.
server/ — self-hosted REST API
A FastAPI server exposing the OSS engine over HTTP, packaged with Docker Compose (FastAPI + PostgreSQL/pgvector + Neo4j). See the Self-Hosted Server.
openmemory/ — self-hosted memory platform
A larger product: api/ (FastAPI + Alembic migrations + an MCP server) and ui/ (Next.js 15 / React 19). Uses Qdrant as its vector store. See the OpenMemory Platform.
mem0-plugin/, openclaw/, vercel-ai-sdk/, skills/ — ecosystem
Editor/agent integrations: mem0-plugin/ (MCP server connection + lifecycle hooks for Claude Code/Cursor/Codex), openclaw/ (@mem0/openclaw-mem0), vercel-ai-sdk/ (@mem0/vercel-ai-provider), and skills/ (reference + pipeline skill definitions). See Integrations.
evaluation/ and docs/
evaluation/ is the benchmark harness (LoCoMo, LongMemEval, BEAM, RAG/full-context/LangMem/OpenAI baselines) — see Evaluation & Benchmarks. docs/ is the Mintlify documentation site.
Insight Each TS package deliberately uses a different lint/test stack (Biome for the Node CLI, ESLint for the Vercel provider, Prettier+jest for the SDK). The monorepo is "polyglot" not just across languages but across toolchains — there is no single root build. The shared contract between Python and TS is the shape of the public API (Memory/MemoryClient, add/search/get_all/...), not shared code.

The two usage modes

Both modes are exported from the package root. mem0/__init__.py is intentionally tiny:

from mem0.client.main import AsyncMemoryClient, MemoryClient  # noqa
from mem0.memory.main import AsyncMemory, Memory              # noqa

Self-hosted: Memory / AsyncMemory

The OSS engine runs the entire memory pipeline in your process: it calls your configured LLM and embedder, writes vectors to your configured vector store, and tracks change history in a local SQLite DB.

  • Defined in mem0/memory/main.py — both Memory and AsyncMemory subclass MemoryBase and accept a MemoryConfig.
  • Construction: Memory(config) directly, or Memory.from_config(config_dict) which validates a dict into a MemoryConfig first.
  • Default config: Memory() with no arguments builds a working stack — OpenAI LLM + OpenAI embedder + Qdrant vector store + SQLite history at ~/.mem0/history.db.

Hosted: MemoryClient / AsyncMemoryClient

The hosted client is an HTTP wrapper around the managed platform API at mem0.ai — no LLM/embedder/vector store runs locally. It exposes the same conceptual methods (add, search, get_all, ...) but the algorithm runs server-side.

  • Defined in mem0/client/main.py (MemoryClient at the top, AsyncMemoryClient further down), with project.py, types.py, utils.py alongside.
  • Proxy wrapper: mem0/proxy/main.py defines a Mem0 class exposing an OpenAI-shaped chat.completions.create surface (Chat → Completions) that transparently injects retrieved memories. See the Hosted Client & Proxy for project APIs and the proxy.
Decision The same four symbols (sync/async × self-hosted/hosted) are exported from one namespace so callers switch modes by swapping the class name, not the import path. Everything else on this page — factories, providers, config — applies only to the self-hosted path; the hosted client owns none of that machinery.

The provider plugin pattern

The self-hosted SDK is built around a single, repeated plugin shape. Each pluggable category is a directory containing an abstract base.py, concrete provider modules, and an __init__.py; configuration classes live separately under mem0/configs/<category>/ and a factory in mem0/utils/factory.py maps a provider-name string to its class.

The four anatomy parts of a provider

1. Abstract base (<category>/base.py)
Defines the contract. VectorStoreBase is the richest — abstract create_col, insert, search, delete, update, get, list, reset, etc., plus a non-abstract keyword_search with a default no-op that BM25-capable stores override (this powers multi-signal retrieval). BaseReranker declares a single abstract rerank(query, documents, top_k).
2. Concrete provider (<category>/<name>.py)
One file per provider, snake_case, subclassing the base. E.g. mem0/vector_stores/qdrant.py defines Qdrant; mem0/llms/anthropic.py defines AnthropicLLM.
3. Config class (mem0/configs/<category>/<name>.py or shared base)
Provider-specific Pydantic config. LLMs and rerankers map each provider to a dedicated config class (e.g. AnthropicConfig, CohereRerankerConfig) or fall back to BaseLlmConfig. Embeddings share one BaseEmbedderConfig. Each vector store has its own config under mem0/configs/vector_stores/.
4. Registry + factory mapping
The __init__.py re-exports selected classes, and the relevant factory in mem0/utils/factory.py holds the authoritative provider_to_class dict mapping name → dotted import path (and, for LLMs/rerankers, a config class). See the Configuration System.
Insight: dotted-string lazy loading Factories store providers as strings (e.g. "mem0.vector_stores.qdrant.Qdrant") and import them on demand via load_class, which does importlib.import_module + getattr. This is why a heavy optional dependency (pinecone, weaviate, faiss) is only imported when that provider is actually selected — installing mem0ai does not pull every backend's SDK. Unknown provider names raise a ValueError at create() time.
Deep dive: why __init__.py registries are partial

The category __init__.py files are not the source of truth for which providers exist — the factory dicts are. For example mem0/reranker/__init__.py only re-exports BaseReranker, CohereReranker, and SentenceTransformerReranker, even though RerankerFactory can build five providers. mem0/llms/__init__.py is empty. The registries exist for convenience re-exports; the factory's provider_to_class is what Memory consults at construction time. When auditing "what's supported", read the factory, not the package init.

Config-driven wiring: MemoryConfig → factories → instances

The engine never imports a provider directly. Construction is a pure function of MemoryConfig: each sub-config names a provider and carries a free-form config dict, and the matching factory turns that pair into a live instance.

MemoryConfig (in mem0/configs/base.py)

  • vector_store: VectorStoreConfig — default provider qdrant.
  • llm: LlmConfig — default provider openai.
  • embedder: EmbedderConfig — default provider openai.
  • reranker: Optional[RerankerConfig] — defaults to None (reranking is opt-in).
  • history_db_path: str — default ~/.mem0/history.db (overridable via MEM0_DIR).
  • version: str — default "v1.1"; custom_instructions: Optional[str] for fact-extraction tuning.

Each sub-config is a tiny two-field Pydantic model: a provider string and a config dict, with a validator that rejects unknown providers. For example LlmConfig and EmbedderConfig validate provider against an allow-list; VectorStoreConfig goes further and uses a model_validator to dynamically import and construct the provider-specific config class from mem0/configs/vector_stores/<provider>.

# What Memory.__init__ does (mem0/memory/main.py), in essence:
self.embedding_model = EmbedderFactory.create(
    self.config.embedder.provider,
    self.config.embedder.config,
    self.config.vector_store.config,   # for embedded-store special cases
)
self.vector_store = VectorStoreFactory.create(
    self.config.vector_store.provider, self.config.vector_store.config,
)
self.llm = LlmFactory.create(self.config.llm.provider, self.config.llm.config)
self.db = SQLiteManager(self.config.history_db_path)

self.reranker = None
if config.reranker:                    # opt-in only
    self.reranker = RerankerFactory.create(
        config.reranker.provider, config.reranker.config,
    )

The four factories

All four live in mem0/utils/factory.py. They share the load_class helper but differ in how much config-coercion they do:

LlmFactory.create(provider, config, **kwargs)
Most elaborate. Maps each provider to both a class path and a config class; coerces dicts, merges kwargs, and even upgrades a generic BaseLlmConfig into a provider-specific config by copying common fields (model, temperature, api_key, max_tokens, vision flags, ...). Supports runtime register_provider and get_supported_providers.
EmbedderFactory.create(provider, config, vector_config)
Simplest mapping (name → class path). Wraps the dict in a single BaseEmbedderConfig. Special case: when the vector store is upstash_vector with enable_embeddings, it returns a MockEmbeddings so the store does its own embedding.
VectorStoreFactory.create(provider, config)
Name → class path; model_dump()s a Pydantic config to a dict and splats it as kwargs into the store constructor. Also exposes reset(instance).
RerankerFactory.create(provider, config, **kwargs)
Name → (class path, config class); validates config type and raises a wrapped ImportError if the optional reranker dependency is missing.
Perf: where the factories are called Factories run once, at Memory.__init__ — provider instances are cached as instance attributes (self.llm, self.embedding_model, self.vector_store, self.reranker). The hot paths (add/search) reuse those instances; see Data Flow. A separate _entity_store vector collection is built lazily on first use, cloning the main vector-store config and (for Qdrant embedded mode) sharing the underlying client to avoid RocksDB lock contention.

Graph memory: removed from the OSS core

Earlier mem0 versions treated graph stores (Neo4j, Memgraph, Kuzu, Apache AGE) as a fifth provider category layered on top of vector memory for relationship-aware retrieval. That category no longer exists in the OSS core.

  • No mem0/graphs/ directory — verified by listing mem0/ (subpackages are client, configs, embeddings, llms, memory, proxy, reranker, utils, vector_stores; no graphs).
  • No graph factory — mem0/utils/factory.py exposes only LlmFactory, EmbedderFactory, VectorStoreFactory, RerankerFactory.
  • No graph field on MemoryConfig — the model in mem0/configs/base.py has no graph section.
  • No graph references in the engine — grep -in graph mem0/memory/main.py returns nothing.
  • TS SDK matches — mem0-ts/src/oss/src/ likewise has no graphs/ directory (again contradicting AGENTS.md, which still lists src/graphs/).

Relationship awareness is now handled inside the vector pipeline as entity linking: entities are extracted, embedded into a sibling <collection>_entities store, and used as a retrieval signal fused with semantic and BM25 scores. See the algorithm's entity linking and the full history in Graph Memory (deprecated).

Decision The April 2026 algorithm rewrite folded relationship retrieval into the single vector-store path (entity linking + multi-signal fusion) rather than maintaining a parallel graph database. This is why the OSS engine now needs only four provider categories. Note that the server/ Docker stack still provisions Neo4j and evaluation/ still has run-mem0-plus-* graph targets — references to "graph memory" elsewhere in the repo are legacy or platform-side, not OSS-core.

Putting it together

A typical self-hosted setup is fully declarative:

from mem0 import Memory

m = Memory.from_config({
    "llm":          {"provider": "anthropic", "config": {"model": "claude-..."}},
    "embedder":     {"provider": "openai",    "config": {"model": "text-embedding-3-small"}},
    "vector_store": {"provider": "qdrant",    "config": {"host": "localhost", "port": 6333}},
    # reranker omitted -> reranking disabled
})
m.add("I prefer window seats", user_id="u1")
m.search("seat preference", user_id="u1")

To swap any backend you change a single provider string; to use the managed platform instead you replace Memory with MemoryClient and drop the config entirely. From here:

Testing & CI/CD

The Python SDK is exercised by 73 pytest files under tests/, organised to mirror the provider layout: tests/configs/, tests/embeddings/, tests/llms/, tests/memory/, tests/rerankers/, tests/utils/ and tests/vector_stores/. Provider tests follow the same shape as the config and provider modules they cover, so adding a provider means adding a parallel test directory.

Sixteen GitHub Actions workflows in .github/workflows/ split into continuous integration (lint + typecheck + test per package) and continuous delivery (tag-triggered publish). Because this is a polyglot monorepo, each package is versioned and released independently via its own tag prefix.

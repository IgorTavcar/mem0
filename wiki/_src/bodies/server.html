Self-Hosted Server

The server/ directory is a standalone FastAPI application that wraps the OSS Memory engine in a secure REST API plus a Next.js dashboard. It is secure by default: every memory endpoint requires a JWT, a per-user X-API-Key, or the legacy ADMIN_API_KEY env var, and refuses to start without a JWT_SECRET unless you explicitly set AUTH_DISABLED=true for local development. The service stack is FastAPI + a single PostgreSQL instance (pgvector for memories, a separate mem0_app database for auth/audit state managed by Alembic) + the dashboard. It is a distinct deployment from OpenMemory and the hosted platform client.

Scope correction The server stack ships no Neo4j/APOC container. Its server/docker-compose.yaml defines exactly three services — mem0 (API), postgres (ankane/pgvector:v0.5.1), and mem0-dashboard. Graph memory is deprecated in OSS core; see Graph Memory. The full graph DB stack lives only in the dev.Dockerfile build (which installs mem0ai[graph]) and the hosted product, not in the default self-hosted compose file.

What the server is

A thin, stateful HTTP layer over a single process-global Memory instance.

  • Entry point: server/main.py builds the FastAPI app, mounts four routers, defines memory CRUD + search + config endpoints inline, and installs CORS, rate-limit, request-log, and upstream-error middleware/handlers.
  • Two databases, one Postgres server: the default postgres database holds the pgvector memories collection; a second mem0_app database holds users, API keys, request logs, refresh-token JTIs, and runtime config overrides. server/init-db.sh creates mem0_app on first boot via a \gexec guarded CREATE DATABASE.
  • Memory history is a SQLite file at HISTORY_DB_PATH (default /app/history/history.db), bind-mounted to the host so it survives container rebuilds.
  • Runtime config is mutable: the LLM/embedder/vector-store config starts from DEFAULT_CONFIG in main.py and can be patched at runtime via POST /configure, persisting to the settings table.

Routers (server/routers/)

routers/auth.py — prefix /auth
GET /auth/setup-status (is any user present?), POST /auth/register (creates the first admin, then closed), POST /auth/login, POST /auth/refresh, GET/PATCH /auth/me, POST /auth/change-password, POST /auth/onboarding-complete. Three endpoints carry per-IP rate limits.
routers/api_keys.py — prefix /api-keys
GET (list the caller's non-revoked keys), POST (mint a key — the full secret is returned once), DELETE /{key_id} (soft-revoke by setting revoked_at).
routers/entities.py — prefix /entities
GET aggregates every user_id/agent_id/run_id across stored memories with counts and timestamps; DELETE /{entity_type}/{entity_id} cascade-deletes that entity's memories via delete_all().
routers/requests.py — prefix /requests
GET returns the most recent request-log rows (default 50, max 200), filtered to API-key/admin-key traffic only (auth_type in ("api_key","admin_api_key")) so the audit view shows programmatic usage rather than dashboard chatter.

Authentication — on by default

All auth logic is centralised in server/auth.py. The verify_auth dependency resolves the caller from three credential sources, in priority order.

  1. Bearer JWT (Authorization: Bearer …) — decoded with HS256, must be an access token, resolves a User by sub. Tags request as bearer.
  2. Per-user API key (X-API-Key) — if it matches ADMIN_API_KEY via secrets.compare_digest, the request is tagged admin_api_key and returns None (no specific user). Otherwise it is looked up as a real per-user key (tagged api_key).
  3. No credentials — if AUTH_DISABLED, tagged disabled and allowed; otherwise 401 with WWW-Authenticate: Bearer.
Startup guardrails main.py raises RuntimeError at import time if auth is enabled but JWT_SECRET is empty — the server simply will not boot misconfigured. If no admin user and no ADMIN_API_KEY exist, _warn_if_unconfigured() logs a loud banner telling operators to set ADMIN_API_KEY, register at /setup, or set AUTH_DISABLED=true.

verify_auth vs require_auth

verify_auth
Returns User | None — None is valid for admin-key/disabled callers. Used by memory and entity endpoints, which operate on the shared Memory instance and don't need a concrete user.
require_auth
Guarantees a non-None User. For admin-key/disabled callers it falls back to the oldest user (_get_default_user) so API-key and audit-log endpoints have an owner to attach to. Used by /api-keys, /requests, and the authenticated /auth/* routes.

API key format & storage

generate_api_key() mints m0sk_<token_urlsafe(32)>, derives a 12-char key_prefix for fast lookup, and stores only a bcrypt hash of the full key. On auth, _resolve_user_from_api_key narrows candidates by prefix, then bcrypt-verifies each and stamps last_used_at. The raw key is never persisted and never recoverable.

Constant-time login If an email isn't found, login() still calls dummy_verify_password() to burn the same bcrypt cycles as a real verify, so response timing doesn't leak whether an account exists. Login/register/refresh also carry per-IP slowapi limits.

Single-use refresh tokens

Each refresh token embeds a jti persisted in refresh_token_jtis. consume_refresh_jti() uses a conditional UPDATE … WHERE used_at IS NULL AND expires_at > now and checks rowcount — closing the read-check-write race so concurrent replays of the same token race on one row and at most one wins. Refresh therefore rotates: a used token is dead.

At most one admin Migration 004_unique_admin_role.py adds a partial unique index ix_users_only_one_admin on role where role = 'admin'. Combined with register()'s "registration is closed once any user exists" check (and its IntegrityError rollback path), the very first registrant becomes the sole admin and the endpoint locks shut.

Bootstrap, setup wizard & make targets

Two paths get a fresh install to a usable state; both live in server/Makefile.

Agent-first: make bootstrap

bootstrap chains up wait-api wait-dashboard seed: it brings up the compose stack, polls /auth/setup-status and the dashboard health endpoint until ready, then runs scripts/seed.sh, which:

# scripts/seed.sh (paraphrased)
GET  /auth/setup-status            # needsSetup?
POST /auth/register {name,email,password}   # create first admin if needed
POST /auth/login    {email,password}         # obtain JWT
POST /api-keys      {label:"dev-seed-key"}   # mint first API key (Bearer JWT)
# prints email / password / API key in the "=== Ready ===" block, once

If EMAIL/PASSWORD/NAME are unset, the script generates a random password via secrets.token_urlsafe(16). OUTPUT=json make seed emits machine-readable credentials instead of the human block.

Browser-first: the setup wizard

make up just starts the stack; the operator then opens http://localhost:3000 and the dashboard's wizard hits /auth/setup-status → /auth/register → /generate-instructions → /auth/onboarding-complete. The wizard's use-case step (which bootstrap skips) feeds POST /generate-instructions, where the live LLM drafts custom instructions and a test message.

Operational make targets

make reset-admin-password EMAIL=… PASSWORD=…
Runs scripts/reset_admin_password.py inside the container — the supported password-recovery path (re-hashes the user's password). Min length 8.
make prune-logs [REQUEST_LOG_RETENTION_DAYS=N]
Runs scripts/prune_request_logs.py — see request logging.
make health / make clean
Health probe of API/dashboard/Postgres; clean = docker compose down -v (wipes the Postgres volume and all data).
Bootstrap skips onboarding telemetry & instructions Because make bootstrap hits the API directly, it never reaches the wizard's success state, so it emits only the admin_registered telemetry event (not onboarding_completed) and never sets custom instructions. Add them later with POST /configure.

Bundled providers gate

BUNDLED_LLM_PROVIDERS = ("openai","anthropic","gemini") and BUNDLED_EMBEDDER_PROVIDERS = ("openai","gemini"). _validate_bundled_providers() rejects POST /configure with a 400 if you select a provider whose package isn't in the image — pointing you to add the package, rebuild, and extend the tuple. The defaults are gpt-4.1-nano-2025-04-14 (LLM) and text-embedding-3-small (embedder). See LLM providers and embedding providers for the full provider catalog and the config system for how config dicts are wired.

Runtime config state

server/server_state.py owns a single process-global Memory instance behind an RLock, rebuilt whenever config changes.

  • initialize_state(DEFAULT_CONFIG) loads any persisted overrides from the settings table (key config_overrides), deep-merges them over the defaults, and constructs Memory.from_config().
  • update_config(updates) deep-merges, rebuilds the Memory instance, and upserts the merged overrides back to settings via a Postgres INSERT … ON CONFLICT DO UPDATE.
  • get_memory_instance() is what every memory endpoint calls; it raises if the runtime was never initialised.
Overrides persist, secrets layer from env Config changes made in the dashboard survive restarts (they live in the DB) and are re-applied on top of the .env-derived defaults, so rotating an API key in .env still takes effect while UI-set model choices stick.

Rate limiting

server/rate_limit.py exposes a single slowapi Limiter keyed by remote address (get_remote_address). It is registered in main.py as app.state.limiter with the RateLimitExceeded handler.

  • Limits are applied only to auth endpoints via decorators: register 5/min, login 10/min, refresh 20/min.
  • Memory CRUD/search endpoints are not rate-limited at this layer — put a reverse proxy in front for that.

Request logging & pruning

An @app.middleware("http") hook (log_requests) assigns a per-request id, times the request, sets X-Request-ID on the response, and persists a RequestLog row.

  • Persistence is off the hot path: _persist_request_log runs via loop.run_in_executor() in a thread so DB writes don't block the response.
  • _should_log_request skips OPTIONS, the docs/health/openapi paths (SKIPPED_REQUEST_LOG_PATHS), and anything under /requests — so the audit log doesn't log views of itself.
  • Each row records method, path, status, latency_ms, and the auth_type tag set during auth.
Append-only table, BRIN-indexed, pruned by script request_logs grows ~864k rows/day at 10 req/s. Migration 006_request_logs_brin.py swaps the created_at btree for a BRIN index so range deletes stay cheap on huge tables. scripts/prune_request_logs.py (via make prune-logs) DELETEs rows older than REQUEST_LOG_RETENTION_DAYS (default 30, min 1). Wire it into cron/systemd in production — nothing prunes automatically.

Error handling & the upstream classifier

server/errors.py turns raw provider/datastore exceptions into clean, classified HTTP 502s instead of leaking stack traces.

  • Every memory endpoint wraps its body in try/except Exception → raise upstream_error().
  • upstream_error() reads the live exception, runs _classify(), and raises an UpstreamError (HTTP 502) carrying a stable code and the request id.
  • _classify() walks the __cause__/__context__ chain so a wrapped provider error still classifies correctly, mapping to codes like provider_auth_failed, provider_rate_limited, provider_timeout, provider_unavailable, datastore_unavailable, or vector_store_unavailable.
  • install_request_id_logging() injects the request_id contextvar into every log record so logs and the X-Request-ID response header correlate.
Deep dive: how a bad OpenAI key surfaces

If the LLM provider raises AuthenticationError (or any exception with status_code 401/403), _classify_one returns ("provider_auth_failed", "…Check your LLM provider API key on the Configuration page."). The client gets 502 {"detail": …, "code": "provider_auth_failed", "request_id": "ab12cd34"} — actionable, no stack trace, and traceable in the logs by request id. The seed script even warns about this case up front when no provider key is set in .env.

The /search 502 fix & rich pgvector filters

PR #5263 (ad736d9a, "add rich filter operators and fix /search 502") changed both the server and the pgvector store.

Server side

The old search_memories splatted the whole request model into Memory.search(**params), which broke when top-level user_id/agent_id/run_id were passed alongside filters — producing a 502. The fix folds the (now deprecated) top-level identifier fields into the filters dict and only forwards top_k/threshold when set, logging a deprecation warning when the legacy fields are used.

# server/main.py — search_memories (paraphrased)
filters = search_req.filters or {}
for entity_key in ("user_id", "agent_id", "run_id"):
    val = getattr(search_req, entity_key, None)
    if val is not None:
        filters[entity_key] = val          # legacy fields -> filters
params = {}
if search_req.top_k is not None:    params["top_k"] = search_req.top_k
if search_req.threshold is not None: params["threshold"] = search_req.threshold
return get_memory_instance().search(query=search_req.query, filters=filters, **params)

pgvector side — rich operators

mem0/vector_stores/pgvector.py gained an OPERATOR_SQL_MAP and a _build_filter_conditions() that compiles a filter dict into parameterised SQL against the JSONB payload column.

Operator(s)SQL
eq / nepayload->>key = / != %s
gt gte lt lte(payload->>key)::numeric <cmp> %s (value cast to float)
in / ninpayload->>key = ANY(%s) / negated
contains / icontainspayload->>key LIKE / ILIKE %s with LIKE-wildcards escaped + ESCAPE '\'
$or / $notrecursively grouped OR / NOT (…) branches
"*" sentinelpayload ? key (key-exists check)
SQL-injection-safe by construction Every value goes through psycopg parameters, never string interpolation; contains/icontains additionally escape \ % _ before building the pattern. A follow-up (PR #5264, 5a2201d7) fixed boolean filter casing (booleans are serialised with json.dumps), LIKE escaping, and TS scalar coercion. These operators flow through to the server's /search and GET /memories filter params.

Database models & Alembic

server/db.py builds the SQLAlchemy engine for the mem0_app database (postgresql+psycopg://…/${APP_DB_NAME}, default mem0_app) with pool_pre_ping=True, and exposes the get_db FastAPI dependency. server/models.py declares five tables.

users (User)
id (UUID), name, unique indexed email, bcrypt password_hash, role (default admin), timestamps. Partial-unique index limits to one admin.
api_keys (APIKey)
id, key_prefix(12), bcrypt key_hash, label, created_by FK→users (CASCADE), last_used_at, revoked_at (soft delete).
request_logs (RequestLog)
method, path, status_code, latency_ms, auth_type, BRIN-indexed created_at.
refresh_token_jtis (RefreshTokenJti)
jti PK, user FK (CASCADE), expires_at (indexed), used_at — backs single-use refresh.
settings (Settings)
key/value text store; row config_overrides holds the JSON runtime config.

Migrations live in server/alembic/versions/ (001→006). alembic/env.py imports models so Base.metadata sees every table, and overrides sqlalchemy.url with the runtime DB URL from db._build_database_url(), so migrations and the app always agree on the target database.

Anonymous telemetry

server/telemetry.py sends at most two PostHog events per install, on by default (MEM0_TELEMETRY=true), opt-out with false.

  • admin_registered — fired when the first admin is created (wizard or API).
  • onboarding_completed — fired only when the dashboard wizard reaches success; API-only bootstraps never emit it.
  • Properties: hashed-ish email domain only (not the address), mem0.__version__, and a random per-install UUID persisted to history/telemetry.json. _capture_once dedupes via that state file so each event fires at most once. No PII, no memory content.

How it fits the wider repo

  • The server is one of the two usage modes: it embeds the OSS Memory engine in-process and exposes it over HTTP — distinct from the hosted MemoryClient which talks to the managed platform.
  • Memory ops flow through the same add()/search() data path and extraction algorithm as the library; the server only adds auth, audit, and config plumbing.
  • Persistence is pgvector for vectors + SQLite for history.
  • For a different self-hosted product (FastAPI + Alembic + MCP + a richer UI), see OpenMemory. Cross-cutting patterns (constant-time login, single-use refresh, BRIN pruning, the upstream classifier) are catalogued in Surprises & Gotchas.

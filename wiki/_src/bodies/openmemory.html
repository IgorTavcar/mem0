OpenMemory Platform

OpenMemory is a self-hosted, single-user memory platform that wraps the mem0 OSS Memory engine in a FastAPI service, exposes memory operations to any MCP client over an MCP server, and ships a Next.js 15 / React 19 dashboard. It is operationally distinct from the multi-tenant self-hosted server: it has no API-key auth, persists a relational mirror of every memory in SQLite (via SQLAlchemy + Alembic), and stores vectors in Qdrant by default. It lives entirely under openmemory/ and is deployed as a three-container Docker Compose stack.

What OpenMemory is (and is not)

A locally deployable "memory layer for AI agents" with a dashboard, an MCP endpoint, and a REST API — built to give one developer a persistent, inspectable memory store across MCP-capable tools (Claude Desktop, Cursor, Cline, Windsurf, etc.).

Three processes
API/MCP (FastAPI + uvicorn, port 8765), UI (Next.js, port 3000), and the vector store (Qdrant mem0_store, port 6333). Defined in openmemory/docker-compose.yml.
Two data planes
The mem0 engine owns the vectors in Qdrant; the FastAPI app owns a parallel relational mirror in SQLite (openmemory.db) that tracks memory state, app ownership, access logs, categories, and ACLs. Memory IDs are shared between the two stores (the SQLite row reuses the UUID minted by mem0/Qdrant).
Single-user by design
There is no authentication. A default user (USER env var, falling back to default_user) and a default app ("openmemory") are created on startup by create_default_user() / create_default_app() in api/main.py. CORS is wide open (allow_origins=["*"]).
Distinct from server/ Both are FastAPI apps that wrap the same engine, but they do not share code. server/ is a multi-tenant hosted-API clone with API keys, rate limiting, and Postgres+pgvector+Neo4j bootstrap. OpenMemory is a single-user desktop-companion platform whose differentiators are the MCP server, the relational ACL/audit mirror, and the Next.js dashboard. When documenting auth or multi-tenancy, you almost always mean server/, not this page.

Application bootstrap

The entire app is wired in api/main.py at import time — there is no lifespan handler.

  • Table creation: Base.metadata.create_all(bind=engine) runs at import, creating all tables directly from the SQLAlchemy models in api/app/models.py.
  • Seeding: create_default_user() and create_default_app() ensure the singleton user/app rows exist.
  • MCP mount: setup_mcp_server(app) includes the MCP router (prefix /mcp).
  • Routers: five routers are mounted — memories, apps, stats, config, backup — re-exported from api/app/routers/__init__.py.
  • Pagination: add_pagination(app) installs fastapi-pagination.
create_all + Alembic both create the schema Because main.py calls Base.metadata.create_all() at startup, a fresh container builds the schema directly from the ORM models — the Alembic chain is a parallel, manually-invoked mechanism (make migrate → alembic upgrade head), not part of the boot path. On a brand-new DB the two will agree; on an existing DB only Alembic applies incremental changes. This dual ownership of the schema is a real footgun: a model change that you forget to encode as a migration will silently appear on new installs but never on upgraded ones.

The MCP server

api/app/mcp_server.py builds a FastMCP("mem0-mcp-server") instance and exposes memory operations as MCP tools. It is mounted into the same FastAPI process under the /mcp prefix (so the MCP endpoint and the REST API share port 8765).

Exposed MCP tools

There are exactly five @mcp.tool-decorated coroutines:

ToolSignatureBehaviour
add_memories(text: str, infer: bool = True)Calls memory_client.add(...) with metadata={source_app:"openmemory", mcp_client:<client>}, then reconciles the returned ADD/DELETE events into the SQLite mirror (creating Memory rows + MemoryStatusHistory entries). infer=False stores text verbatim (no LLM fact extraction).
search_memory(query: str)Embeds the query via memory_client.embedding_model.embed(query,"search"), calls memory_client.vector_store.search(...) directly with limit=10 and filters={user_id}, then filters hits through the ACL and writes a search access log per result.
list_memories()memory_client.get_all(user_id), filtered by per-memory ACL, with a list access log per returned item.
delete_memories(memory_ids: list[str])Deletes only IDs that are both requested and ACL-accessible from the vector store, soft-deletes the mirror row (state=deleted, deleted_at), writes history + delete access log.
delete_all_memories()Soft-deletes every ACL-accessible memory for the user; delete_all access logs.
search bypasses the engine's search() Unlike the other tools, search_memory does not call memory_client.search(). It manually embeds the query and hits vector_store.search() directly — sidestepping the engine's reranking / score-fusion / retrieval pipeline entirely. This keeps the MCP path lean (one embedding + one vector query) but means MCP search results are raw vector hits, not the engine's fused ranking. The result shape is hand-built from OutputData (id, memory, hash, created_at, updated_at, score).

Per-request user / client context

The user id and client name are not parameters — they are carried in contextvars.ContextVar objects (user_id_var, client_name_var) set from the URL path before the MCP server runs, and reset in a finally block. Every tool reads them via .get(None) and errors if missing. This is how a stateless MCP transport injects identity into the tool body.

Two transports

SSE (legacy)
GET /mcp/{client_name}/sse/{user_id} opens an SseServerTransport session; messages POST to /mcp/messages/. Reaches into request._send (the raw ASGI send) because Starlette does not expose it — the documented MCP-SDK pattern.
Streamable HTTP (current, MCP spec 2025-03-26+)
POST|GET|DELETE /mcp/{client_name}/http/{user_id} runs a StreamableHTTPServerTransport in stateless JSON mode (one request = one independent invocation, no persistent session). The handler intercepts the transport's ASGI send via a capture_send closure and re-emits it as a single FastAPI Response — a workaround for the "double-response" bug that would otherwise occur when both the transport and FastAPI try to write.
Resilient (lazy) client init The memory client is never created at import — get_memory_client_safe() wraps get_memory_client() in a try/except and returns None on failure. Every tool checks for None and returns a human-readable "Memory system is currently unavailable" string rather than raising. This keeps the MCP server alive even when Ollama / the LLM provider is down (degraded "database-only" mode). The dashboard's default port is 8765 for the MCP base URL.

REST API surface

All REST routes live under /api/v1 and are consumed by the dashboard. None require auth; user_id is passed as a query/body string on most endpoints. Routers are in api/app/routers/.

Apps — /api/v1/apps

  • GET / — list apps with total_memories_created + total_memories_accessed (computed via subquery joins on memory_access_logs).
  • GET /{app_id}, GET /{app_id}/memories, GET /{app_id}/accessed — app detail, created memories, accessed memories.
  • PUT /{app_id}?is_active=... — pause/resume an app. A paused app blocks add_memories and is excluded from ACL checks.

Config, stats, backup

  • /api/v1/config — get/update the runtime mem0 + openmemory config (see below).
  • /api/v1/stats — GET / returns total_memories, total_apps, and the app list for the dashboard header.
  • /api/v1/backup — POST /export streams a zip (memories.json relational dump + memories.jsonl.gz provider-agnostic logical dump); POST /import ingests it with skip/overwrite modes and re-embeds content into the vector store via memory_client.embedding_model.embed(content,"add").
PUT /api/v1/config/ is a no-op In api/app/routers/config.py, update_configuration() builds updated_config but never calls save_config_to_db() and falls off the end returning None — the change is silently discarded. The working path is PATCH / (deep-merge + save + reset_memory_client()) and the granular setters PUT /mem0/llm, /mem0/embedder, /mem0/vector_store, /openmemory. The dashboard uses the granular setters, so the bug is rarely hit in practice.
Backup is portable across vector stores The memories.jsonl.gz dump stores only content + metadata + categories — no vectors. Import re-embeds with the current embedder, so a backup taken on OpenAI embeddings can be restored onto Ollama/any other provider and any vector store. Cross-user UUID collisions are handled by minting a fresh UUID on import.

Relational data model (SQLite mirror)

Defined in api/app/models.py. The DB is the source of truth for state, ownership, ACLs, audit, and categories; the vector store is the source of truth for embeddings and semantic search.

User
Singleton-ish: user_id string (unique), owns apps and memories.
App
An MCP client / source app (e.g. cursor, claude). is_active gates writes and reads. Unique on (owner_id, name) — see the migration note.
Memory
The mirror row. UUID matches the Qdrant id. state ∈ MemoryState{active, paused, archived, deleted}; carries archived_at/deleted_at soft-delete timestamps. Composite indexes on (user_id,state), (app_id,state), (user_id,app_id).
Category + memory_categories
Many-to-many; categories are auto-assigned (see categorization).
MemoryStatusHistory
Append-only audit of every state transition (old_state→new_state, changed_by).
MemoryAccessLog
Every search/list/delete/delete_all touch, with JSON metadata (query, score, hash). Powers the dashboard's access timeline and per-app access counts.
AccessControl
The ACL table: (subject_type, subject_id, object_type, object_id, effect). Used for app→memory allow/deny rules.
ArchivePolicy
Defined (days_to_archive by criteria) but no router currently enforces it — schema-only scaffolding.
Config
Single-row-per-key JSON config store (key "main"); the runtime mem0 config is read from here.

The ACL: check_memory_access_permissions

api/app/utils/permissions.py centralises read access. A memory is accessible iff: (1) state == active, (2) the app exists and is_active, and (3) the app-level ACL allows it. get_accessible_memory_ids() in memories.py resolves allow/deny rules: no rules → all allowed (None); a blanket deny → empty set; otherwise allowed-minus-denied. This function is invoked per-row in list/search transformers and in every MCP tool.

Deep dive: ID sharing between Qdrant and SQLite

When memory_client.add() returns {"results":[{"id","memory","event"}]}, both the MCP add_memories tool and the REST POST /memories handler parse the engine-minted UUID and create the Memory row with that exact id (Memory(id=uuid.UUID(result['id']), ...)). This is what lets the dashboard's relational queries line up with vector-store deletes/searches by id. ADD events upsert the mirror row to active; DELETE events (the engine's update logic can delete superseded memories) soft-delete it.

Auto-categorization (SQLAlchemy event hooks)

Memories are categorized automatically on insert/update via SQLAlchemy ORM events, not in the request handler.

  • @event.listens_for(Memory, 'after_insert') and 'after_update' in models.py call categorize_memory().
  • get_categories_for_memory() in api/app/utils/categorization.py calls OpenAI gpt-4o-mini with response_format=MemoryCategories (structured parse) and the taxonomy in api/app/utils/prompts.py (MEMORY_CATEGORIZATION_PROMPT, ~20 categories: Personal, Work, Health, Finance, …, and free-form new ones). Wrapped in tenacity retry (3 attempts, exponential backoff).
Categorization is hard-wired to OpenAI categorization.py instantiates a bare OpenAI() client at import. Regardless of the configured LLM provider (Ollama, Anthropic, …), categorization always calls OpenAI gpt-4o-mini and needs OPENAI_API_KEY. The event listener opens its own Session(bind=connection) inside the flush, so a categorization failure is caught and rolled back independently of the main transaction.

Configuration & provider auto-detection

The mem0 engine config is assembled in api/app/utils/memory.py (get_memory_client()): start from get_default_memory_config() (env-driven), overlay any DB-stored mem0 block, substitute env:VAR tokens, then Memory.from_config(). The client is cached globally and only rebuilt when an MD5 of the config changes (_get_config_hash); reset_memory_client() forces a rebuild after config writes.

Vector store auto-detection

get_default_memory_config() picks the vector store by inspecting env vars, in order: Chroma → Qdrant → Weaviate → Redis → pgvector → Milvus → Elasticsearch → OpenSearch → FAISS, defaulting to Qdrant (host="mem0_store", port=6333) if none are set. Each provider has a matching one-file Compose fragment under openmemory/compose/ (qdrant.yml, chroma.yml, pgvector.yml, milvus.yml, weaviate.yml, redis.yml, elasticsearch.yml, opensearch.yml, faiss.yml) that run.sh merges into the stack. See the vector stores layer for the underlying drivers.

LLM / embedder provider factories

Tiny per-provider config factories (_LLM_CONFIG_FACTORIES, _EMBEDDER_CONFIG_FACTORIES) handle ollama and openai specially; any other provider (anthropic, groq, together, deepseek, …) falls through a generic branch that requires LLM_MODEL/EMBEDDER_MODEL to be set. Defaults: openai/gpt-4o-mini LLM, openai/text-embedding-3-small embedder. This mirrors the broader config system and LLM/embedding provider layers, but is a lighter, OpenMemory-local re-implementation rather than reuse.

Docker→host Ollama URL rewriting _get_docker_host_url() / _fix_ollama_urls() detect a container (/.dockerenv) and rewrite localhost/127.0.0.1 Ollama URLs to host.docker.internal (Mac/Windows) or the bridge gateway (/proc/net/route parse, fallback 172.17.0.1 on Linux), honouring OLLAMA_HOST first. Without this, a containerized API could never reach an Ollama daemon on the host.
Deep dive: where config lives

There are three config surfaces: (1) api/.env env vars (the primary install-time knobs, see api/.env.example); (2) the configs table row keyed "main", edited via the dashboard Settings page and /api/v1/config, holding a {openmemory:{custom_instructions}, mem0:{llm,embedder,vector_store}} JSON; (3) api/default_config.json / config.json static defaults. The DB block overrides env defaults at client-build time. custom_instructions become the engine's custom_fact_extraction_prompt, letting users steer what fact extraction stores.

Alembic migration chain

Migrations live in api/alembic/versions/. api/alembic/env.py points target_metadata = Base.metadata and reads DATABASE_URL (default sqlite:///./openmemory.db). There are exactly three revisions, applied with make migrate → alembic upgrade head (also make upgrade; make downgrade steps back one). Migrations are not run automatically on container start.

OrderRevisiondown_revisionWhat it does
10b53c747049a (initial)NoneCreates all base tables: users, apps, memories, categories, memory_categories, access_controls, archive_policies, memory_status_history, memory_access_logs (+ indexes).
2add_config_table0b53c747049aCreates the configs table + idx_configs_key index.
3afd00efbd06b (head)add_config_tableDrops the global-unique index on apps.name, replaces it with a composite unique idx_app_owner_name on (owner_id, name) — so two users can each have an app named "cursor".
DO NOT edit migrations without understanding the chain The chain is linear and ordered by down_revision, not by the Create Date in the docstring. add_config_table carries a misleading Create Date: 2023-06-01 even though it depends on the 2025 initial migration — trust down_revision, never the timestamp. Editing an already-applied migration in place will desync the alembic_version row from real databases and can corrupt upgrades; the correct workflow is always a new revision appended to head. Note also the schema is created two ways (create_all on boot vs. these migrations), so a model change must be reflected in both the ORM models and a new migration to stay consistent across fresh and upgraded installs.

Next.js dashboard (ui/)

A Next.js 15 / React 19 App Router dashboard (TypeScript, Tailwind, Radix/shadcn-ui, Redux Toolkit), served on port 3000. Talks to the API over axios against NEXT_PUBLIC_API_URL (default http://localhost:8765) with user id from NEXT_PUBLIC_USER_ID.

Routes (App Router pages)

/ (app/page.tsx)
Dashboard home: stats, install instructions, charts.
/memories
Filterable, paginated memory table (the POST /filter consumer).
/memory/[id]
Memory detail: content, categories, access log, related memories, actions.
/apps & /apps/[appId]
App grid and per-app memory/access views.
/settings
Edits the configs row (LLM/embedder/vector-store + custom instructions) via the granular /api/v1/config setters.

State: Redux Toolkit store

ui/store/store.ts combines six slices: memories, profile, apps, ui, filters, config. Data fetching is in custom hooks (useMemoriesApi, useAppsApi, useStats, useConfig, useFiltersApi) that call axios and dispatch slice actions. The profile slice seeds userId from NEXT_PUBLIC_USER_ID. The Navbar auto-refetches based on the current route via a regex→fetchers mapping.

Runtime env-var substitution in a static build ui/Dockerfile builds Next.js with placeholder NEXT_PUBLIC_* strings; ui/entrypoint.sh then sed-replaces those placeholders in the prebuilt .next/ bundle at container start. This is how one prebuilt image (mem0/openmemory-ui) is re-pointed at a different API URL / user id without rebuilding — but it means changing NEXT_PUBLIC_API_URL requires a container restart, not just a page reload.

Deployment

openmemory/docker-compose.yml defines three services: mem0_store (Qdrant, :6333, volume mem0_storage), openmemory-mcp (the API/MCP image, :8765, uvicorn main:app --reload --workers 4, env from api/.env + USER/API_KEY), and openmemory-ui (:3000). The one-line installer run.sh requires OPENAI_API_KEY, finds a free frontend port (3000–3010), selects the vector store (--vector-store= / VECTOR_STORE env, default qdrant), and merges the matching compose/*.yml fragment.

  • API image: python:3.12-slim, deps from api/requirements.txt (pins mem0ai>=0.1.92, mcp[cli]>=1.25.4, fastapi-pagination, anthropic, ollama).
  • make targets: up/down/logs/shell/migrate/test/ui-dev. make down also deletes api/openmemory.db.
  • Backup helper: backup-scripts/export_openmemory.sh wraps the /api/v1/backup/export endpoint.
No auth, open CORS — keep it local OpenMemory ships with allow_origins=["*"], no API keys, and a single implicit user. It is intended to run on localhost behind your own machine, not exposed to a network. For a multi-tenant, authenticated deployment use the self-hosted server instead. MCP clients connect by URL path identity only (/mcp/{client_name}/...{user_id}), which is trivially spoofable — acceptable for a single-user local tool, not for shared hosting.

Where it fits

OpenMemory is the platform that the broader mem0 integrations & ecosystem (the mem0-plugin MCP client, editor extensions) connect to. It consumes the OSS Memory engine directly (not the hosted client SDK), shares the same provider plumbing described in the architecture overview, and its MCP search deliberately shortcuts the full retrieval data flow. For the cross-cutting gotchas surfaced here (the config PUT no-op, dual schema ownership, OpenAI-only categorization), see surprises & gotchas.

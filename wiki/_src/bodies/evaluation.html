Evaluation & Benchmarks

mem0 ships an open, reproducible benchmarking harness under evaluation/ that pits the mem0 memory layer against RAG, full-context, LangMem, Zep and OpenAI baselines on conversational long-term-memory datasets. The harness has two clean phases — a per-technique experiment runner that produces answer JSON, and a scorer that applies BLEU, token-F1, and an LLM-as-judge. The headline April-2026 numbers (LoCoMo 91.6, LongMemEval 94.8, BEAM 64.1 / 48.6) come from a separate, larger open-sourced harness (mem0ai/memory-benchmarks) and reflect single-pass retrieval — one call, no agentic loops.

Overview & what is measured

Two distinct things live under the "benchmarks" umbrella, and conflating them is the single biggest source of confusion.

The in-repo LoCoMo harness (evaluation/)
The code described on this page. It targets the LoCoMo dataset only, drives the hosted mem0 platform via MemoryClient plus a set of literature/commercial baselines, and scores with BLEU / token-F1 / a GPT-4o-mini judge. This is the artifact behind the original arXiv paper (2504.19413).
The headline table (README → mem0ai/memory-benchmarks)
A larger, separately open-sourced framework that produces the April-2026 numbers across LoCoMo, LongMemEval, and BEAM (at 1M and 10M token scales). The repo README links it explicitly as the way "anyone can reproduce the numbers." Those datasets/runners are not vendored into this tree — only the LoCoMo harness is.
Decision: single-pass, no agentic loops. The README states all headline benchmarks run "single-pass retrieval (one call, no agentic loops)." This is a deliberate apples-to-apples constraint: the memory layer gets exactly one search() per question and the answer LLM gets exactly one completion. There is no ReAct-style tool loop, no self-querying, no retry-on-low-confidence. It measures the quality of the retrieval algorithm itself, not an agent's ability to compensate for it. (Note the LangMem baseline is the exception — see Baselines.)

The metric definitions from evaluation/README.md:

  • LLM score — binary 0/1 correctness from an LLM judge. This is the headline accuracy metric.
  • BLEU / token-F1 — surface-overlap metrics, reported alongside but secondary (judge correctness is what the paper leads with).
  • Token consumption — tokens needed to produce the final answer (the "Tokens" column, ~7K).
  • Latency — search + answer-generation time (the "Latency p50" column, ~1s).

Research-highlights gloss from the same README:

  • LoCoMo 91.6 — +20 points over the previous algorithm.
  • LongMemEval 94.8 — +27 points, with +53.6 on assistant (agent) memory recall specifically. This jump is directly attributed to making agent-generated facts first-class (see below).
  • BEAM (1M) 64.1 — "production-scale memory evaluation at 1M tokens." BEAM has no "Old" baseline because it post-dates the previous algorithm.
Insight: the token/latency budget is the real story. Across all four benchmarks the retrieval footprint is ~6.7–7.0K tokens and p50 latency is ~1 second. The pitch is not "highest accuracy at any cost" — it is high accuracy at a small, near-constant context budget, which is what makes the algorithm cheap to run in production. Compare against the full-context baseline, which feeds the entire conversation into the LLM every turn.
Deep dive: which algorithm change drove which number

The README attributes the gains to five concrete changes, all of which are documented on the Memory Algorithm page:

Single-pass ADD-only extraction
One LLM call per add; no UPDATE/DELETE phase. Memories accumulate and nothing is overwritten — removing the lossy reconciliation step that previously discarded correct facts.
Agent-generated facts are first-class
When an agent confirms an action, that statement is stored with equal weight to user statements. This is what produced the +53.6 on assistant memory recall in LongMemEval.
Entity linking
Entities extracted, embedded, and linked across memories to boost retrieval.
Multi-signal retrieval
Semantic + BM25 keyword + entity matching scored in parallel and fused.
Temporal reasoning
Time-aware ranking that selects the right dated instance for "current state" vs "past event" vs "upcoming plan" queries.

Datasets & benchmarks

Three benchmarks appear in the headline table; only LoCoMo is wired into this repo's harness.

LoCoMo
Multi-session conversational QA between two speakers, with timestamped turns and category-tagged questions. The harness expects dataset/locomo10.json (original, for mem0/OpenAI/Zep) and dataset/locomo10_rag.json (RAG-formatted, for RAG/LangMem). These files are not committed — evaluation/README.md points to a Google Drive download and instructs placing them under dataset/.
LongMemEval
Long-context memory evaluation emphasizing assistant/agent recall. Run via the external memory-benchmarks repo, not this tree.
BEAM
"Production-scale" memory benchmark evaluated at two context scales: 1M tokens (64.1) and 10M tokens (48.6). The accuracy drop from 1M to 10M quantifies how retrieval quality degrades as the haystack grows roughly 10×.
Gotcha: the in-repo harness only covers LoCoMo. If you clone evaluation/ expecting to reproduce the LongMemEval 94.8 or BEAM numbers, you will not find runners for them. run_experiments.py hard-codes dataset/locomo10.json / dataset/locomo10_rag.json for every technique. The LongMemEval and BEAM results come from github.com/mem0ai/memory-benchmarks.

The experiment runner

One entrypoint, evaluation/run_experiments.py, dispatches to a technique-specific manager class. Each manager reads the LoCoMo dataset, produces answers, and streams a results JSON to results/.

CLI & dispatch

The parser accepts --technique_type (one of mem0, rag, langmem, zep, openai — the TECHNIQUES list in evaluation/src/utils.py), --method (add | search, the METHODS list), plus retrieval knobs:

# mem0 (hosted) add then search
python run_experiments.py --technique_type mem0 --method add
python run_experiments.py --technique_type mem0 --method search --top_k 30

# mem0 + graph (Mem0+)
python run_experiments.py --technique_type mem0 --method add --is_graph
python run_experiments.py --technique_type mem0 --method search --is_graph --top_k 30

# RAG (chunk_size 500) and full-context (chunk_size -1)
python run_experiments.py --technique_type rag --chunk_size 500 --num_chunks 1
python run_experiments.py --technique_type rag --chunk_size -1 --num_chunks 1

The dispatch is a flat if/elif chain in main(). Notable per-branch behaviour:

  • mem0 / add → MemoryADD(data_path="dataset/locomo10.json", is_graph=...) then process_all_conversations().
  • mem0 / search → MemorySearch; the output filename encodes the run config: mem0_results_top_{top_k}_filter_{filter_memories}_graph_{is_graph}.json.
  • rag → RAGManager(...); output rag_results_{chunk_size}_k{num_chunks}.json. chunk_size=-1 is the sentinel for full-context.
  • langmem / zep / openai → fixed output filenames.
Gotcha: --filter_memories and --is_graph are store_true flags. Passing --filter_memories False does not turn filtering off — argparse treats the bare presence of the flag as True and ignores the trailing token. The README's parameter table listing a "False" default is the absence-of-flag default, not a value you pass.

add vs search as separate passes

mem0 (and Zep) split ingestion and querying into two CLI invocations. add writes memories into the hosted store; search later queries them. They are decoupled because ingestion is expensive and you typically run it once, then sweep retrieval settings (top_k, graph on/off) across many search runs without re-ingesting. See Data Flow for the underlying add()/search() sequences.

Technique implementations

mem0 (hosted): MemoryADD / MemorySearch

Both classes talk to the hosted platform through mem0.MemoryClient (see Hosted Client & Proxy), not the OSS Memory engine. They authenticate with MEM0_API_KEY / MEM0_ORGANIZATION_ID / MEM0_PROJECT_ID from the environment.

  • MemoryADD first calls update_project(custom_instructions=...) with a long prompt steering memory extraction toward self-contained personal narratives (named people not "user", emotional context, exact dates). It then ingests each conversation: per speaker, batched (batch_size=2), each speaker on its own thread, with delete_all(user_id=...) first to guarantee a clean slate. User ids are namespaced per conversation index: f"{speaker}_{idx}".
  • Critically, add() is called with roles swapped between the two speakers (messages vs messages_reverse): for speaker A, A's lines are role:"user" and B's are assistant; for speaker B the reverse. Each speaker gets their own first-person memory store.
  • MemorySearch issues one search() per speaker per question with top_k (default 30) and optional filter_memories. Returned memories are reduced to {memory, timestamp, score} and rendered into ANSWER_PROMPT for a final gpt-* completion at temperature=0.
Perf: concurrency everywhere. Ingestion runs a ThreadPoolExecutor(max_workers=10) over conversations, and within each conversation the two speakers ingest on separate threading.Threads. Both add and search wrap the network call in a 3-attempt retry with a 1s backoff (add_memory, search_memory).

mem0 + graph (Mem0+)

Setting --is_graph flips ingestion to enable_graph=True and search to enable_graph=True, output_format="v1.1". The v1.1 response carries both results (semantic memories) and relations (graph triples), which MemorySearch destructures into {source, relationship, target} and threads into the graph-aware prompt ANSWER_PROMPT_GRAPH. See Graph Memory for the status of graph in OSS core (it has been removed from OSS and replaced by entity linking; this hosted-platform path is distinct).

RAG baseline & full-context

RAGManager (evaluation/src/rag.py) is a from-scratch RAG: it flattens the conversation into "{timestamp} | {speaker}: {text}" lines, tokenizes with tiktoken, splits into fixed-size chunks, embeds each chunk with the configured OpenAI embedding model, and at query time computes cosine similarity by hand (np.dot over normalized vectors) to pick the top-k chunks (default k=1). The chunks are joined with a \n<->\n separator and passed to a short answer prompt.

Decision: chunk_size == -1 is the full-context switch. In create_chunks, a chunk size of -1 short-circuits chunking and returns the entire transcript as a single "chunk" with no embeddings; process_all_conversations then skips search entirely (search_time = 0) and stuffs the whole conversation into the prompt. This is how the run-full-context target reuses the RAG code path to implement the full-context baseline.

LangMem baseline

LangMemManager (evaluation/src/langmem.py) builds a LangGraph ReAct agent per speaker (create_react_agent) backed by an InMemoryStore (1536-dim OpenAI index) and a MemorySaver checkpointer, armed with LangMem's create_manage_memory_tool and create_search_memory_tool. Each chat message is fed to the matching speaker's agent via add_memory; at query time both agents are queried and their two responses are fused by get_answer() into the same ANSWER_PROMPT used by mem0. Conversations are parallelized with a multiprocessing.Pool(processes=10).

Gotcha: LangMem is the one agentic baseline. Unlike the single-pass techniques, LangMem uses a tool-calling ReAct loop for both ingestion and retrieval. This is a property of LangMem itself, not the harness — worth noting when comparing its latency/accuracy to the single-pass numbers. Also note a latent bug: on an exception in search_memory it returns t2 - t1 where t2 was never assigned (the timer is only started, so this raises UnboundLocalError in the error path).

OpenAI baseline

OpenAIPredict (evaluation/src/openai/predict.py) is "predict-only": it reads pre-exported memory dumps from memories/{idx}.txt (one file per conversation, produced out-of-band by exporting OpenAI's ChatGPT memory feature) and feeds them straight into the answer prompt. search_memory returns the raw file contents with a hard-coded search time of 0. There is no live OpenAI memory API call in this code path.

Zep baseline

ZepAdd / ZepSearch (evaluation/src/zep/) drive Zep Cloud via the zep_cloud SDK, creating a user + session per conversation and adding each turn as a Message. They use the dedicated ANSWER_PROMPT_ZEP (single-store, no per-speaker split). Note ZepAdd.process_all_conversations only ingests idx == 0 — it is gated to the first conversation, presumably to control Zep API cost during development.

Scoring pipeline

Scoring is a separate two-step pass that consumes the runner's results JSON.

flowchart LR

question, answer, response, category] --> B[evals.py

  B --> C[calculate_metrics
token-F1]
  B --> D[calculate_bleu_scores
BLEU-1..4]
  B --> E[evaluate_llm_judge
GPT-4o-mini 0/1]
  C & D & E --> F[evaluation_metrics.json]
  F --> G[generate_scores.py
pandas groupby category]
  G --> H[per-category + overall
bleu / f1 / llm means]

evals.py — per-item scoring

evaluation/evals.py loads a results file, then for each conversation's QA list computes three numbers per item: bleu_score (the BLEU-1 component), f1_score (token-F1), and llm_score (the judge's 0/1). It fans work out across a ThreadPoolExecutor (default 10 workers, one task per conversation) and writes the augmented records to evaluation_metrics.json.

Gotcha: category 5 is always skipped. Both evals.py and the standalone metrics/llm_judge.py explicitly continue when category == "5". In LoCoMo, category 5 is the adversarial / "unanswerable" class — it is excluded from the reported accuracy. The runner still records adversarial_answer fields, but the scorer drops those questions entirely.

LLM-as-judge

evaluation/metrics/llm_judge.py defines evaluate_llm_judge(question, gold_answer, generated_answer). It calls gpt-4o-mini at temperature=0.0 with response_format={"type":"json_object"}, asking it to label the answer CORRECT or WRONG and return {"label": ...}. The function maps CORRECT → 1, everything else → 0.

  • The ACCURACY_PROMPT instructs the judge to be generous: a much longer generated answer counts as correct as long as it touches the same topic; date formats and relative time references that resolve to the same date count as correct.
  • The JSON is parsed via mem0's own extract_json (mem0/memory/utils.py) rather than a bare json.loads, hardening against fenced/markdown-wrapped model output.
  • The prompt warns the model never to emit both labels ("it will break the evaluation script") — the downstream check is a literal string equality on "CORRECT".
Insight: the judge is the headline metric. BLEU and F1 are surface-overlap metrics that punish the verbose, correct answers an LLM naturally produces. Because LoCoMo gold answers are terse (often 1–5 words) and generated answers can be longer, the generous LLM judge is the metric that actually tracks "did the system remember the right thing." The "91.6" / "94.8" headline numbers are judge accuracy, not BLEU/F1.

Surface metrics — metrics/utils.py

evaluation/metrics/utils.py (adapted from the A-Mem project, per its docstring) implements the lexical/semantic metrics. calculate_metrics returns exact-match plus a set-based token-F1 (precision/recall over deduplicated lowercased tokens). calculate_bleu_scores computes BLEU-1 through BLEU-4 with NLTK and method-1 smoothing. The module also carries ROUGE, METEOR, BERTScore, and SentenceTransformer cosine-similarity helpers (importing bert_score, rouge_score, sentence-transformers), but evals.py only uses BLEU-1 and F1.

Gotcha: heavy import side effects. Importing metrics/utils.py downloads NLTK punkt/wordnet and eagerly loads the all-MiniLM-L6-v2 SentenceTransformer at module import time. Both are wrapped in try/except, so failures degrade to warnings rather than crashing — but the first run pulls models off the network even though most of those metrics are never invoked by the standard scorer.

generate_scores.py — aggregation

evaluation/generate_scores.py loads evaluation_metrics.json, flattens it into a pandas DataFrame, coerces category to numeric, and reports mean bleu_score / f1_score / llm_score per category (with question counts) plus the overall means. It is a thin reporting layer with no CLI args — paths are hard-coded.

Answer prompts

evaluation/prompts.py holds the prompts used to turn retrieved memories into a final short answer. They share a common spine and differ only by what memory shape they consume.

ANSWER_PROMPT
Two-speaker memories, no graph. Used by mem0 (non-graph), LangMem, and as the fusion prompt in LangMem.
ANSWER_PROMPT_GRAPH
Adds per-speaker knowledge-graph relations alongside the memories; used by the Mem0+ graph path.
ANSWER_PROMPT_ZEP
Single combined memory blob (no per-speaker split), for the Zep baseline.

All three encode the same evaluation-shaping rules, which matter for interpreting the scores:

  • "The answer should be less than 5-6 words" — forces terse answers that align with LoCoMo's short gold answers.
  • Detailed temporal-reasoning instructions: prioritize the most recent memory on contradiction, and convert relative time references ("last year") to absolute dates using the memory timestamp.
  • "Do not confuse character names mentioned in memories with the actual users who created those memories" — a guard against the role-swapped ingestion described in the mem0 runner.

Note these are templated with Jinja2 ({{...}}) in the per-speaker code and rendered via jinja2.Template. RAG and the OpenAI baseline define their own minimal inline prompts rather than reusing these.

Reproducing & environment

Configuration is entirely environment-driven (.env loaded via python-dotenv):

  • OPENAI_API_KEY, MODEL (e.g. gpt-4o-mini), EMBEDDING_MODEL (e.g. text-embedding-3-small) — shared by every technique's answer LLM and the RAG embedder.
  • MEM0_API_KEY / MEM0_ORGANIZATION_ID / MEM0_PROJECT_ID — for the hosted mem0 / Mem0+ runs.
  • ZEP_API_KEY — for the Zep baseline.

End-to-end for LoCoMo:

# 1. place dataset/locomo10.json and dataset/locomo10_rag.json
# 2. ingest + retrieve
make run-mem0-add
make run-mem0-search
# 3. score
python evals.py --input_file results/mem0_results_top_30_filter_False_graph_False.json \
                --output_file evaluation_metrics.json
# 4. aggregate
python generate_scores.py

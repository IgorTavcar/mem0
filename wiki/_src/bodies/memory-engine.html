Memory Engine

The Memory Engine is the OSS core of mem0: the Memory and AsyncMemory classes in mem0/memory/main.py that orchestrate embedding, vector storage, LLM-driven extraction, entity linking, and a local SQLite change log. Both classes implement the same public surface (add, search, get, get_all, update, delete, delete_all, history, reset) on top of the abstract MemoryBase; AsyncMemory is a near line-for-line mirror that offloads every blocking call to a thread pool via asyncio.to_thread. This page documents construction, every public method's signature and semantics, the concurrency model, the SQLite history/messages schema, session scoping rules, metadata handling, the infer=False raw path, and the gotchas around required identifiers and filter placement.

Overview & placement

The engine is the in-process implementation behind from mem0 import Memory. It wires four pluggable layers together via factories and adds local persistence plus telemetry.

  • Two classes, one contract. Memory (sync) and AsyncMemory (async) both extend MemoryBase (mem0/memory/base.py) and expose identical method names. They are exported at the package root in mem0/__init__.py as Memory, AsyncMemory.
  • Composed dependencies. On construction each instance creates an embedding model, vector store, LLM, optional reranker, a lazily-built entity store, and a SQLiteManager for history. See the configuration system for how the four factories resolve providers.
  • Where it sits. The hosted MemoryClient talks to a remote API and does not use this engine; the self-hosted server and CLI wrap this engine. For the algorithmic detail of what happens inside add/search see the memory algorithm and the end-to-end data flow.

Construction

There are two ways to build an instance: pass a typed MemoryConfig, or pass a plain dict to the from_config classmethod.

Memory(config)

The constructor takes a single MemoryConfig (defaulting to MemoryConfig(), an all-defaults config) and eagerly builds every dependency:

from mem0 import Memory
m = Memory()                       # all defaults
m = Memory(MemoryConfig(...))      # typed config object

During __init__ the engine:

self.embedding_model
EmbedderFactory.create(provider, embedder_config, vector_store_config) — the vector-store config is also passed so the embedder can align dimensions.
self.vector_store
VectorStoreFactory.create(provider, vs_config). See vector stores.
self.llm
LlmFactory.create(provider, llm_config). See LLM providers.
self.db
SQLiteManager(config.history_db_path) — the local change log (default ~/.mem0/history.db).
self.reranker
None unless config.reranker is set, in which case RerankerFactory.create(...). See rerankers.
self._entity_store
Set to None; built lazily on first access (see below).
self.collection_name, self.api_version, self.custom_instructions
Cached from config; api_version defaults to "v1.1".

Memory.from_config(config_dict)

Accepts a plain dict, validates it into a MemoryConfig, and constructs the instance. This is the path used by the CLI/server and most examples.

m = Memory.from_config({
    "llm": {"provider": "openai", "config": {"model": "gpt-4o-mini"}},
    "vector_store": {"provider": "qdrant", "config": {"path": "/tmp/qd"}},
})
Gotcha from_config calls cls._process_config(config_dict) and then MemoryConfig(**config_dict) — but _process_config is currently a pass-through that simply returns its input. The real validation is the MemoryConfig(**config_dict) pydantic call, which raises (and re-raises after logging) pydantic.ValidationError on a malformed config.

The lazy entity store

The entity_store property clones the vector-store config, points it at a separate collection named {collection_name}_entities, and builds a second vector store on first use. Entities (people, places, things extracted from memory text) live here with a linked_memory_ids payload, powering the entity-boost signal in retrieval.

Decision For the qdrant provider in embedded mode the entity store reuses the primary store's client object rather than opening a second connection, explicitly to avoid RocksDB lock contention on the same on-disk path.
Deep dive: telemetry vector store & _safe_deepcopy_config

When telemetry is enabled the constructor also builds a throwaway _telemetry_vector_store bound to a collection literally named "mem0migrations" (for FAISS/Qdrant it gets its own migrations_<provider> path under ~/.mem0). Cloning the config uses _safe_deepcopy_config, which falls back to dict-based reconstruction when a plain deepcopy fails (e.g. configs holding thread locks or non-serializable auth objects). During that fallback, runtime auth fields in _RUNTIME_FIELDS (http_auth, auth, connection_class, ssl_context) are preserved, while anything matching _SENSITIVE_FIELDS_EXACT or the sensitive suffixes (_password, _secret, _token, _credential(s)) is redacted to None.

add()

Ingests messages and writes memories. messages may be a str (wrapped as a single user message), a single dict, or a list of {"role","content"} dicts; anything else raises Mem0ValidationError (VALIDATION_003). Flow:

  1. _build_filters_and_metadata(...) produces a storage metadata template and effective query filters, and requires at least one of user_id/agent_id/run_id (else Mem0ValidationError VALIDATION_001).
  2. If memory_type is set it must equal MemoryType.PROCEDURAL.value ("procedural_memory"); any other value raises VALIDATION_002. When both agent_id and procedural type are present, _create_procedural_memory runs instead of the normal pipeline.
  3. Vision parsing runs (image content is described via the LLM when enable_vision is configured).
  4. _add_to_vector_store(...) performs either the raw path (infer=False) or the full V3 phased batch pipeline.
Insight — single-pass, ADD-only extraction. The inference path issues exactly one LLM call producing a JSON {"memory": [...]} list, then batch-embeds, hash-dedupes, batch-inserts, batch-writes history, and batch-links entities. Unlike older mem0, the engine no longer asks the LLM to emit UPDATE/DELETE operations during add; it only ADDs new facts and relies on md5-hash dedup against existing memories. See the algorithm.
Deep dive: the eight phases of _add_to_vector_store
  • Phase 0 — context: reads the last 10 messages for this session scope from SQLite, and flattens the new messages with parse_messages.
  • Phase 1 — existing retrieval: embeds the parsed messages and does a top_k=10 vector search scoped by entity filters; existing memory UUIDs are remapped to integer indices ("anti-hallucination" so the LLM can't echo back real IDs).
  • Phase 2 — extraction: one LLM call with ADDITIVE_EXTRACTION_PROMPT (plus AGENT_CONTEXT_SUFFIX when the scope is agent-only), response_format={"type":"json_object"}. Robust parse: remove_code_blocks → json.loads → fallback extract_json.
  • Phase 3 — batch embed all extracted texts (embed_batch, falling back to per-item embed).
  • Phases 4–5 — per-memory metadata + md5 hash dedup against existing payload hashes and within the batch.
  • Phase 6 — batch persist to the vector store and batch_add_history as ADD events (with per-item insert fallback).
  • Phase 7 — batch entity linking: extract_entities_batch, global dedup, batch-embed entities, batch-search the entity store, and split into updates (existing match ≥ 0.95) vs new inserts.
  • Phase 8 — save messages to SQLite and fire the mem0.add telemetry event.

If the LLM call fails, or extraction yields nothing, or all candidates are deduped, the method still persists the raw messages (save_messages) and returns [] — no exception is raised.

search()

Multi-signal hybrid retrieval. After validating threshold (must be in [0,1]) and top_k (non-negative int) and confirming filters carry an entity id, it delegates to _search_vector_store, which fuses semantic similarity, normalized BM25 keyword scores, and entity boosts via score_and_rank. It over-fetches an internal pool of max(top_k*4, 60) candidates before truncating to top_k. Optional rerank=True applies the configured reranker. The query-side metadata DSL (operators like eq/ne/gt/in/contains and AND/OR/NOT) is detected by _has_advanced_operators and rewritten by _process_metadata_filters into a vector-store-agnostic shape ($or/$not for logical groups). Full scoring detail lives in the algorithm.

get() / get_all()

get(memory_id) fetches one record from the vector store and reshapes its payload into a MemoryItem dict, promoting user_id/agent_id/run_id/actor_id/role to top level and bundling everything else under metadata. Returns None if not found. get_all(*, filters, top_k=20) lists memories for a scope; both methods strip the internal text_lemmatized, hash, data keys out of the user-facing metadata.

update()

update(memory_id, data, metadata=None) re-embeds data, overwrites the vector-store record, writes an UPDATE history row carrying the previous text, and refreshes entity links. It preserves the original created_at and the session identifiers from the existing record (only filling them from the existing payload when not supplied in new metadata) and stamps a fresh updated_at. Raises ValueError if the id is missing.

delete() / delete_all()

delete(memory_id) removes the vector record, writes a DELETE history row (is_deleted=1, capturing the prior text), and strips the id from entity records. delete_all(user_id/agent_id/run_id) lists every memory in the scope and deletes them one-by-one; the async variant fans them out with asyncio.gather.

Gotcha delete_all requires at least one identifier. Calling it with no args raises ValueError directing you to use reset() instead — there is no "delete everything" shortcut on this method.

history()

history(memory_id) returns the full ordered change log for one memory directly from SQLite (db.get_history) — a list of rows with old_memory, new_memory, event, timestamps, is_deleted, actor_id, and role.

reset()

Destroys all state: drops the SQLite history table, rebuilds a fresh SQLiteManager, and resets the vector store (via VectorStoreFactory.reset if supported, else delete_col + recreate). The sync variant also resets the entity store; the async variant additionally runs gc.collect() and closes the vector-store client before recreating, to release file handles.

Perf/cleanup note Both classes also expose a non-abstract close() that closes the SQLite connection, and chat() which is an explicit NotImplementedError placeholder.

Sync vs async & concurrency

AsyncMemory is a parallel implementation, not a wrapper around Memory. Every method body is duplicated; the only structural difference is that blocking calls are dispatched to a worker thread.

  • Offloading primitive: all I/O and CPU-bound work — embedding, vector-store ops, LLM calls, SQLite reads/writes, lemmatization, entity extraction — is wrapped in await asyncio.to_thread(fn, ...). There is no native async client usage; the engine relies on a thread pool to keep the event loop unblocked.
  • Fan-out: the one place that genuinely parallelizes is async delete_all, which builds a list of _delete_memory coroutines and awaits asyncio.gather(*tasks).
  • Reranking in async search is also pushed through asyncio.to_thread so a heavy reranker doesn't stall the loop.
  • Telemetry sync_type: every capture_event call tags sync_type as "sync" or "async", the one observable behavioral marker distinguishing the two classes.

SQLite thread safety

The single shared SQLite connection is opened with check_same_thread=False and guarded by a process-local threading.Lock (self._lock) inside SQLiteManager. Every write wraps an explicit BEGIN/COMMIT with ROLLBACK on error. Because asyncio.to_thread dispatches to arbitrary worker threads, this lock is what makes concurrent async DB access safe.

Gotcha The lock is a plain in-process threading.Lock; it does not coordinate across multiple processes or multiple Memory instances pointed at the same history.db file. SQLite-level locking is your only protection in that case.

SQLite history & messages (SQLiteManager)

mem0/memory/storage.py defines SQLiteManager, the local persistence for change history and short-term conversational context. It manages two tables in the history_db_path database (default ~/.mem0/history.db; ":memory:" is the class default for ephemeral use).

history table

The append-only change log. Schema:

CREATE TABLE history (
    id           TEXT PRIMARY KEY,   # uuid4 per row
    memory_id    TEXT,               # the memory this change belongs to
    old_memory   TEXT,               # previous text (NULL for ADD)
    new_memory   TEXT,               # new text (NULL for DELETE)
    event        TEXT,               # 'ADD' | 'UPDATE' | 'DELETE'
    created_at   DATETIME,
    updated_at   DATETIME,
    is_deleted   INTEGER,            # 1 on DELETE rows
    actor_id     TEXT,
    role         TEXT
)
ADD
Written on every new memory (and the batch batch_add_history path). old_memory=NULL, new_memory=text.
UPDATE
Written by _update_memory. old_memory=prev_value, new_memory=data, preserves original created_at, new updated_at.
DELETE
Written by _delete_memory. new_memory=NULL, is_deleted=1; the prior text is retained in old_memory so deletions remain auditable.

get_history returns rows for a memory_id ordered created_at ASC, DATETIME(updated_at) ASC and converts is_deleted back to a bool. batch_add_history uses executemany for the bulk ADD path.

messages table

A rolling short-term context window keyed by session_scope:

CREATE TABLE messages (
    id TEXT PRIMARY KEY, session_scope TEXT, role TEXT,
    content TEXT, name TEXT, created_at DATETIME
)

save_messages inserts the new turn(s) and then evicts everything beyond the most recent 10 rows for that scope (a subquery materializes the ORDER BY before the outer DELETE ... NOT IN). get_last_messages fetches the latest N (default 10) and re-sorts them chronologically for Phase 0 of add.

Insight — deterministic session scope. The session_scope string is built by _build_session_scope as a sorted, joined key like agent_id=a1&user_id=u1. Sorting the keys makes the scope identifier order-independent so the same logical session always maps to the same message window.

Schema migration

On every construction, _migrate_history_table inspects the existing history table's columns. If they differ from the expected set, it renames the table to history_old, recreates the new schema, copies the intersecting columns across, and drops the old table — all inside one transaction with rollback on failure. This silently upgrades databases that still carried the old group-chat columns.

Decision Migration copies only the intersection of old and new columns, so removed columns (the legacy convo fields) are dropped and any new columns are left NULL. It is a best-effort, lossy-by-design forward migration.
Deep dive: reset semantics differ between classes

SQLiteManager.reset() drops both history and messages and recreates them. But the engine's Memory.reset() / AsyncMemory.reset() do not call db.reset(); they each drop only the history table, close the connection, and build a brand-new SQLiteManager (whose constructor recreates both tables). The net effect is the same fresh state, but note that SQLiteManager.reset is reachable mainly via its own API.

Session scoping & required identifiers

Memories are partitioned by three session identifiers plus an actor dimension. The rules are enforced by _build_filters_and_metadata and the per-method validators.

user_id
End-user scope.
agent_id
Agent scope; when present without user_id the extraction prompt switches to agent-context mode (AGENT_CONTEXT_SUFFIX). Required for procedural memories.
run_id
Run/conversation scope.
actor_id
A query-time filter, not a primary scope. On the raw infer=False path it is derived from a message's name field and stored on the memory; for inferred memories the actor for storage is set later from message content.
Required identifier rule. Every scoped operation needs at least one of user_id/agent_id/run_id. add raises Mem0ValidationError VALIDATION_001 if none are given; search and get_all raise ValueError if filters lacks all three. delete_all raises ValueError with the same requirement.
Filters vs top-level kwargs. For search and get_all the identifiers must go inside filters={...}. Passing user_id= as a top-level kwarg is explicitly rejected by _reject_top_level_entity_params with a message pointing you to filters. (add is the exception — it takes them directly.)

Identifier validation & normalization

_validate_and_trim_entity_id trims surrounding whitespace and rejects empty/whitespace-only values and any value containing internal whitespace (raising ValueError). This runs on add's ids and on the user_id/agent_id/run_id entries inside search/get_all filters.

# Correct usage
m.add("I love hiking", user_id="alice")
m.search("hobbies", filters={"user_id": "alice"})         # ids in filters
m.get_all(filters={"agent_id": "support-bot"}, top_k=50)

# Wrong — raises ValueError (entity params not allowed top-level)
m.search("hobbies", user_id="alice")

Metadata handling

The engine maintains a strict separation between internal payload keys and user metadata.

  • Stored on every memory automatically: data (the memory text), hash (md5 of text, used for dedup), created_at, updated_at, text_lemmatized (for BM25), plus whichever session ids apply, and optionally actor_id, role, attributed_to.
  • User-supplied metadata passed to add(metadata=...) is deep-copied into the storage template and merged onto every created memory.
  • Read-side shaping: get/get_all/search promote user_id/agent_id/run_id/actor_id/role to top-level fields, exclude the internal core keys (data/hash/created_at/updated_at/id/text_lemmatized/attributed_to), and place all remaining keys under a nested metadata dict in the result.
Insight text_lemmatized is computed once at write time and persisted in the payload, so keyword/BM25 search at query time reads a precomputed token field rather than re-lemmatizing every stored memory.

Results are normalized through the MemoryItem pydantic model (mem0/configs/base.py): id, memory, hash, metadata, score, created_at, updated_at. get_all drops score from its output (model_dump(exclude={"score"})) since list views have no relevance score.

The infer=False raw path

Setting infer=False on add bypasses the LLM entirely and stores each message as a verbatim memory.

  • Each non-system message is embedded directly and written via _create_memory as an ADD.
  • system messages are skipped; malformed entries (missing role or content) are logged and skipped, not fatal.
  • The message's role is stored on the memory, and a name field, if present, becomes the actor_id.
  • Returned items include the extra actor_id and role keys (the inferred path returns only id/memory/event).
m.add(
    [{"role": "user", "content": "Order #42 shipped", "name": "agent-smith"}],
    user_id="u1", infer=False,
)
# stores the literal text; no extraction, no dedup-via-LLM, no entity batch pipeline
Gotcha The raw path does not run hash dedup, the existing-memory retrieval, or the Phase 7 batch entity linking that the inferred path does. It is a low-overhead "store exactly what I give you" mode — use it for logs or pre-extracted facts, not for conversational ingestion.

Telemetry

mem0/memory/telemetry.py sends anonymized usage events to PostHog through a thread-safe lazy singleton. It is engineered to never raise into the call path — every capture is wrapped in a broad try/except that only logs at debug level.

Opt-out & sampling

MEM0_TELEMETRY
Master switch. Anything other than true/1/yes (case-insensitive) disables telemetry entirely; default is enabled.
MEM0_TELEMETRY_SAMPLE_RATE
Float in [0,1], default 0.1. Hot-path events are sampled at this rate; out-of-range or unparsable values fall back to the default without raising.
Security/privacy Captured event data never includes raw identifiers. process_telemetry_filters (mem0/memory/utils.py) reports the names of filter keys present and md5-hashes the user_id/agent_id/run_id values into encoded_ids. To disable all of it set MEM0_TELEMETRY=False.

Captured events

Each method fires a named event via capture_event(name, self, extra): mem0.init, mem0.add, mem0.search, mem0.get, mem0.get_all, mem0.update, mem0.delete, mem0.delete_all, mem0.history, mem0.reset, and mem0._create_procedural_memory. Every event carries non-PII context: collection name, vector size, the fully-qualified class names of the vector store / LLM / embedding model, the API version, and sync_type.

Decision — lifecycle events bypass sampling. mem0.init, mem0.reset, mem0._create_procedural_memory, and $identify are in _LIFECYCLE_EVENTS and always fire at 100%; only hot-path events (add/search/get/...) are subject to the sample rate. Surviving sampled events are annotated with their sample_rate so dashboards can extrapolate true counts.
Deep dive: the singleton & graceful degradation

_get_oss_telemetry builds a single AnonymousTelemetry instance with double-checked locking and registers an atexit shutdown so the background PostHog thread is closed once at interpreter exit. The PostHog client is constructed with a before_send sampling hook; if the installed posthog is older than 4.5.0 (no before_send support) it falls back to an unsampled client. A separate, unsampled client_telemetry singleton serves the hosted MemoryClient.

Setup: ~/.mem0 & the anonymous user id

mem0/memory/setup.py manages the per-machine config directory and the anonymous telemetry id; setup_config() is invoked at import time of main.py.

  • Directory: ~/.mem0 (overridable via the MEM0_DIR env var), created on import. It holds config.json and, by default, history.db.
  • setup_config() is idempotent: it ensures config.json has a top-level user_id (a uuid4), backfilling it for configs the CLI wrote with only a telemetry.anonymous_id. Without this, OSS telemetry would be silently dropped because there'd be no distinct id.
  • get_or_create_user_id(vector_store) returns the anonymous id and, when a vector store is supplied, persists a marker record (a zero-ish vector with type="user_identity") so the id is stable across the store.
Privacy mark_aliased stores an sha256 hash of anon_id\0email rather than the email itself, so the local config never contains a plaintext platform email even when anon→email $identify aliasing has occurred.

End-to-end example

from mem0 import Memory, AsyncMemory

m = Memory.from_config({"llm": {"provider": "openai", "config": {"model": "gpt-4o-mini"}}})

res = m.add(
    [{"role": "user", "content": "I'm vegetarian and allergic to peanuts"}],
    user_id="alice",
)
mem_id = res["results"][0]["id"]

m.search("what can alice eat", filters={"user_id": "alice"}, top_k=5, threshold=0.2)
m.update(mem_id, "Vegetarian; allergic to peanuts and shellfish")
m.history(mem_id)         # -> [ADD, UPDATE] rows from SQLite
m.delete(mem_id)          # writes a DELETE row (is_deleted=1)

# async mirror — identical surface, coroutines
am = AsyncMemory()
async def go():
    await am.add("Likes jazz", user_id="alice")
    return await am.get_all(filters={"user_id": "alice"})

Structured exceptions & telemetry sampling

Two cross-cutting concerns wrap the engine: a typed exception hierarchy and sampled, opt-out usage telemetry.

Structured exceptions

mem0/exceptions.py defines a rich hierarchy rooted at MemoryError — each carrying message, error_code, details, suggestion and debug_info. Subclasses cover the obvious failure modes: AuthenticationError, RateLimitError, ValidationError, MemoryNotFoundError, NetworkError, ConfigurationError, MemoryQuotaExceededError, MemoryCorruptionError, VectorSearchError, CacheError, plus OSS-specific VectorStoreError / EmbeddingError / LLMError / DatabaseError / DependencyError. A HTTP_STATUS_TO_EXCEPTION map and create_exception_from_response() turn raw HTTP responses into the right typed error (e.g. 429 → RateLimitError with a retry_after in debug_info).

Gotcha This module is largely aspirational on the OSS path. The self-hosted engine still surfaces generic provider exceptions rather than raising these typed ones; the hierarchy is most useful around the hosted client and in your own wrappers. One DependencyError docstring even references kuzu as a graph_store — a leftover from the removed graph layer.

Telemetry & sampling

Anonymous usage telemetry (mem0/memory/telemetry.py) reports event names and coarse, anonymized metadata — never memory content to PostHog via an AnonymousTelemetry client. Opt out entirely with MEM0_TELEMETRY=False.

Hot-path sampling
High-frequency events are sampled at _DEFAULT_SAMPLE_RATE = 0.1 (10%). Override with MEM0_TELEMETRY_SAMPLE_RATE (parsed defensively, clamped to [0.0, 1.0], never raises).
Lifecycle events always fire
Init/lifecycle events and PostHog’s $identify bypass sampling and fire at 100% — so person-merging is never lost to sampling.
Extrapolation
A PostHog before_send hook drops sampled events and annotates survivors with a sample_rate property, so dashboards can recover true counts via 1 / sample_rate.
Performance Sampling the hot path keeps telemetry overhead negligible at scale while preserving exact lifecycle/identity counts — a deliberate accuracy-vs-volume trade. The condition is random.random() >= rate, so rate=0 drops everything and rate=1 keeps everything.

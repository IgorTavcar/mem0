Data Flow

This page traces the two hot paths through the mem0 engine end to end: add(), which turns raw messages into stored facts via a single LLM extraction call plus a phased batch persistence pipeline, and search(), which fuses semantic similarity, BM25 keyword matching, and entity boosts into a single ranked result set. Both paths live in mem0/memory/main.py and exist in mirrored sync (Memory) and async (AsyncMemory) implementations; the async variant differs only in that every blocking call is wrapped in asyncio.to_thread. See the Memory Engine page for class internals and the Memory Algorithm page for the extraction prompt and scoring math.

Overview & orientation

Everything funnels through Memory._add_to_vector_store() and Memory._search_vector_store(). The public methods (add, search, get, get_all, update, delete, delete_all, history) are thin wrappers that validate inputs, build filters, emit telemetry, and delegate.

Three persistence stores
The vector store (memories), a sibling entity store (a second collection named {collection_name}_entities), and the SQLite database (history + messages tables via mem0/memory/storage.py). See vector stores and the engine's history section.
Session scoping
Every operation requires at least one of user_id, agent_id, run_id (validated by _build_filters_and_metadata / _validate_and_trim_entity_id). These are passed via filters= on read paths — top-level entity kwargs are rejected by _reject_top_level_entity_params. See configuration.
Telemetry
Every public method calls capture_event(...) with a sync_type of "sync" or "async". IDs are hashed via process_telemetry_filters before transmission. See surprises and the engine page.
Insight The Apr-2026 algorithm is ADD-only: the extraction LLM call never emits UPDATE or DELETE operations on the add path. Deduplication is handled mechanically by MD5 hashing and by passing existing memories to the LLM as a "do not re-extract" reference. UPDATE/DELETE only happen when a caller invokes update()/delete() directly. This is a deliberate departure from the older "fact + memory-decision two-pass" design. See the algorithm page.

The add() path

add() normalizes input, optionally parses vision content, then dispatches to _add_to_vector_store() which has two branches: a raw fast path (infer=False) and the full V3 phased batch pipeline (infer=True, the default).

Entry & normalization

Memory.add(messages, *, user_id, agent_id, run_id, metadata, infer=True, memory_type, prompt) performs, in order:

  • _build_filters_and_metadata(...) → returns (processed_metadata, effective_filters); raises Mem0ValidationError (code VALIDATION_001) if no session id is provided.
  • Validates memory_type: only MemoryType.PROCEDURAL.value ("procedural_memory") is accepted besides None.
  • Coerces messages: a str becomes [{"role": "user", "content": ...}]; a dict becomes a one-element list; anything else raises VALIDATION_003.
  • If agent_id is set and memory_type == "procedural_memory", routes to _create_procedural_memory() (a single LLM summary, stored verbatim) and returns early.
  • Runs parse_vision_messages(...) — when config.llm.config["enable_vision"] is set, image URLs are described by the LLM first; otherwise it just passes messages through.
  • Calls _add_to_vector_store(messages, processed_metadata, effective_filters, infer, prompt=...) and wraps the result as {"results": [...]}.

The infer=False fast path

When infer=False, no LLM is called and no entities are extracted. Each message is stored verbatim as its own memory:

  • Messages with missing role/content are skipped with a warning; role == "system" messages are dropped.
  • Per-message metadata copies the template, sets role, and promotes a message's name field to actor_id.
  • Each content string is embedded (embedding_model.embed(content, "add")) and persisted via _create_memory(...), which assigns a UUID, computes the MD5 hash, sets created_at/updated_at, lemmatizes into text_lemmatized, upserts the vector, and writes a single ADD history row.
  • Returns one result dict per message including actor_id and role.
Perf The fast path skips the existing-memory search, the extraction LLM call, hash dedup against existing memories, batch embedding, and entity linking. It is the right choice when the caller already has clean atomic facts (e.g. an ETL job) and wants to avoid LLM latency and cost entirely.

The infer=True V3 phased batch pipeline

The default path is organized into numbered phases inside _add_to_vector_store(). A single LLM call does all the reasoning; everything else is mechanical batching.

Phase 0 — Context gathering
session_scope = _build_session_scope(filters) (a deterministic sorted string like user_id=u1&run_id=r1). db.get_last_messages(session_scope, limit=10) pulls the last 10 raw turns from the SQLite messages table; parse_messages(messages) flattens the new turns into a string.
Phase 1 — Existing-memory retrieval
The parsed messages are embedded with action "search" and a vector_store.search(top_k=10, filters=search_filters) finds up to 10 related existing memories. Their UUIDs are mapped to sequential integer string ids ("0", "1", ...) in uuid_mapping — an anti-hallucination measure so the LLM references short ids, never raw UUIDs.
Phase 2 — Single LLM extraction call
System prompt is ADDITIVE_EXTRACTION_PROMPT; if the session is agent-scoped (agent_id present and no user_id), AGENT_CONTEXT_SUFFIX is appended. The user prompt is built by generate_additive_extraction_prompt(existing_memories, new_messages, last_k_messages, custom_instructions). The call requests response_format={"type": "json_object"}. On any exception the whole add returns []. The response is cleaned with remove_code_blocks and parsed; if json.loads fails it falls back to extract_json. Extracted items live under the "memory" key, each {"text": ..., "attributed_to": ...}.
Phase 3 — Batch embed extracted texts
All non-empty text fields are embedded in one embedding_model.embed_batch(mem_texts, "add") call, producing embed_map: text → vector. On failure it falls back to per-text embed().
Phase 4/5 — CPU processing + hash dedup
For each extracted memory: compute md5(text). Skip if the hash already exists in the Phase-1 results (existing_hashes) or earlier in this batch (seen_hashes). Survivors get a UUID, a metadata dict carrying data, text_lemmatized (lemmatize_for_bm25), hash, created_at/updated_at, and optionally attributed_to. Records accumulate as (memory_id, text, embedding, payload) tuples.
Phase 6 — Batch persist (vector + history)
One vector_store.insert(vectors, ids, payloads) call (falling back to per-record insert on error). Then one db.batch_add_history(records) writing all ADD rows in a single SQLite transaction (falling back to per-row add_history).
Phase 7 — Batch entity linking
extract_entities_batch(all_texts) (spaCy nlp.pipe) yields entities per memory. Entities are globally deduplicated by lowercased text (7a), batch-embedded once (7b), batch-searched against the entity store via entity_store.search_batch(top_k=1) (7c), then split (7d): matches with score >= 0.95 get their linked_memory_ids union-updated; the rest are collected and inserted in one entity_store.insert(...) (7e). The whole phase is wrapped in try/except and is non-fatal — a linking failure never breaks the add.
Phase 8 — Persist raw messages + telemetry
db.save_messages(messages, session_scope) stores the raw turns (evicting all but the most recent 10 for the scope), then capture_event("mem0.add", ...) fires. Returns [{"id", "memory", "event": "ADD"}, ...].
Gotcha If the LLM extracts nothing, or every extraction is a hash duplicate, the pipeline still calls db.save_messages(...) and returns [] — so the conversation context is preserved for the next turn even when no new facts were stored. The early returns at "no extracted memories" and "no records" both do this.
Decision Lemmatized text is stored at write time (text_lemmatized in the payload) so that BM25/keyword search at query time can match against pre-normalized tokens without re-running spaCy over the whole corpus. See query preprocessing and the algorithm page.

Deep dive: AsyncMemory differences on the add path

AsyncMemory._add_to_vector_store is a line-for-line mirror with every blocking call wrapped in asyncio.to_thread(...): get_last_messages, embedding_model.embed, vector_store.search, llm.generate_response, embedding_model.embed_batch, vector_store.insert, db.batch_add_history, extract_entities_batch, entity_store.search_batch, entity_store.insert, and db.save_messages all run on the default thread-pool executor. The phases stay sequential (each await completes before the next) — there is no asyncio.gather fan-out inside a single add. The async add() also accepts an extra llm= kwarg used only by _create_procedural_memory (LangChain ChatModel support).

The search() path

search() validates and (optionally) translates advanced metadata filters, emits telemetry, then delegates to _search_vector_store(), which runs a three-signal hybrid retrieval — semantic, BM25 keyword, entity boost — and fuses the scores additively in score_and_rank(). Optional reranking runs last.

Entry & filter processing

search(query, *, top_k=20, filters=None, threshold=0.1, rerank=False):

  • Rejects top-level entity kwargs (_reject_top_level_entity_params); validates threshold ∈ [0,1] and non-negative integer top_k (_validate_search_params); requires one session id in filters.
  • If _has_advanced_operators(filters) detects logical (AND/OR/NOT), comparison (eq, ne, gt, gte, lt, lte, in, nin, contains, icontains), or wildcard ("*") operators, _process_metadata_filters rewrites them into a vector-store-neutral form ($or/$not for logical groups). See the vector store interface.
  • Fires capture_event("mem0.search", ...), then calls _search_vector_store(query, effective_filters, limit, threshold).
  • If rerank=True and a reranker is configured, the result list is reranked (see reranking).

Multi-signal retrieval inside _search_vector_store

The signals are computed in a fixed sequence of steps. In the sync implementation they run one after another on the calling thread; the parallelism is logical, not concurrent.

Step 1 — Query preprocessing
query_lemmatized = lemmatize_for_bm25(query) (spaCy lemmatizer, drops stopwords/punctuation, also keeps original -ing forms) and query_entities = extract_entities(query) (spaCy NER / noun-compound extraction). See entity extraction.
Step 2 — Embed query
embeddings = embedding_model.embed(query, "search").
Step 3 — Semantic search (over-fetch)
internal_limit = max(limit * 4, 60) — the store is queried for a much larger candidate pool than top_k so that the BM25 and entity signals have room to re-rank. vector_store.search(query, vectors=embeddings, top_k=internal_limit, filters=filters).
Step 4 — Keyword / BM25 search
vector_store.keyword_search(query=query_lemmatized, top_k=internal_limit, filters=filters). The base implementation in mem0/vector_stores/base.py returns None — only stores that override it participate, so BM25 is opportunistic.
Step 5 — Normalize BM25
If keyword results exist, get_bm25_params(query, lemmatized=...) picks a sigmoid (midpoint, steepness) by query length, and each raw score is squashed into [0,1] via normalize_bm25 (logistic sigmoid). Stored as bm25_scores: id → score.
Step 6 — Entity boosts
If the query yielded entities, _compute_entity_boosts(query_entities, filters) embeds each (de-duplicated, max 8) entity, searches the entity store (top_k=500), keeps matches with similarity >= 0.5, and for each linked memory accumulates a max boost. The boost is similarity * ENTITY_BOOST_WEIGHT * memory_count_weight where ENTITY_BOOST_WEIGHT = 0.5 and memory_count_weight = 1 / (1 + 0.001 * (num_linked - 1)²) — a spread-attenuation that down-weights promiscuous entities linked to many memories.
Step 7 — Candidate set
Semantic results become candidate dicts {"id", "score", "payload"}. The candidate pool is seeded only from semantic results — a memory that matches BM25/entity but is absent from the semantic top-internal_limit cannot surface.
Step 8 — Fuse & rank
score_and_rank(semantic_results=candidates, bm25_scores, entity_boosts, threshold, top_k) (in mem0/utils/scoring.py).
Step 9 — Format
Each survivor is shaped into a MemoryItem dict (id, memory, hash, created_at, updated_at, score), with promoted keys (user_id, agent_id, run_id, actor_id, role) lifted out and remaining payload fields nested under metadata. Candidates whose payload lacks data are dropped.

Score fusion math

score_and_rank gates on the semantic score first — any candidate with semantic_score < threshold is excluded before combining, so BM25/entity boosts cannot rescue a sub-threshold semantic match. The combined score is additive over an adaptive divisor:

# mem0/utils/scoring.py
max_possible = 1.0
if has_bm25:   max_possible += 1.0          # → 2.0
if has_entity: max_possible += 0.5          # ENTITY_BOOST_WEIGHT

raw_combined = semantic_score + bm25_score + entity_boost
combined = min(raw_combined / max_possible, 1.0)
Active signalsmax_possible divisor
Semantic only1.0
Semantic + entity (no BM25)1.5
Semantic + BM252.0
Semantic + BM25 + entity2.5

The divisor is global per query (determined by whether any BM25/entity scores exist), not per candidate. Results are sorted by combined score descending and truncated to top_k.

Correctness note: no temporal ranking in search Despite the algorithm's heavy emphasis on temporal reasoning, score_and_rank performs no recency/temporal weighting — it fuses semantic + BM25 + entity only. Temporal reasoning is entirely an extraction-time concern: the ADDITIVE_EXTRACTION_PROMPT instructs the LLM to ground relative references ("last week" → a concrete date) against the Observation Date before storing the fact. So time-awareness is baked into the stored data text, not applied as a ranking signal at query time. See the algorithm page.

Optional reranking

When rerank=True and self.reranker is set (configured via RerankerFactory), reranker.rerank(query, original_memories, limit) reorders the fused results. Failures are caught and the original order is kept. Providers live under mem0/reranker/ (Cohere, HuggingFace, sentence-transformer, LLM, ZeroEntropy). See the rerankers page.

Deep dive: AsyncMemory differences on the search path

AsyncMemory._search_vector_store wraps each of the three signal computations in asyncio.to_thread: lemmatize_for_bm25, extract_entities, embedding_model.embed, vector_store.search, and vector_store.keyword_search each run on the executor. Entity boosts use _compute_entity_boosts_async, which awaits embedding_model.embed and entity_store.search per entity via asyncio.to_thread. The steps are still issued sequentially (each awaited in turn) — the diagram's par block is the logical signal model, not literal concurrency. The fusion (score_and_rank) is pure CPU and runs inline. Reranking, when enabled, is dispatched with await asyncio.to_thread(self.reranker.rerank, ...) so a slow reranker does not block the event loop. The one place asyncio.gather appears is AsyncMemory.delete_all, which fans out _delete_memory coroutines concurrently.

get / get_all / update / delete / history

The remaining public methods are direct CRUD over the vector store and SQLite, each emitting telemetry and (for mutations) writing a history row and cleaning up the entity store.

Reads: get & get_all

get(memory_id)
vector_store.get(vector_id=...); returns None if missing. Builds a MemoryItem dict, promotes session/actor/role keys, nests the rest under metadata. No scoring. Async wraps the get in asyncio.to_thread.
get_all(*, filters, top_k=20)
Validates filters and top_k, then _get_all_from_vector_store calls vector_store.list(filters, top_k). It defensively unwraps the result because stores return either a flat list or a (list, ...) tuple. Same MemoryItem formatting as get, but score is excluded.

Mutations: update, delete, delete_all

update(memory_id, data, metadata=None)
Embeds data with action "update" and calls _update_memory: fetches the existing memory, preserves created_at and any session/actor/role ids not overridden, recomputes hash and text_lemmatized, sets a fresh updated_at, calls vector_store.update(...), writes an UPDATE history row, then re-links entities: _remove_memory_from_entity_store(...) strips the id from stale entity records and _link_entities_for_memory(...) re-extracts entities from the new text and links them back.
delete(memory_id)
Fetches the memory (raises ValueError if absent), then _delete_memory: deletes the vector, writes a DELETE history row with is_deleted=1 (preserving created_at normalized to UTC and the prior data as old_memory), then strips the id from the entity store.
delete_all(user_id, agent_id, run_id)
Requires at least one filter (otherwise points the caller to reset()). Lists matching memories and deletes each via _delete_memory. Sync loops serially; AsyncMemory.delete_all builds a list of _delete_memory coroutines and runs them via asyncio.gather(*delete_tasks).

history(memory_id)

Returns db.get_history(memory_id) — the full ADD/UPDATE/DELETE audit trail for one memory, ordered by created_at ASC, DATETIME(updated_at) ASC. The SQLite history table (see mem0/memory/storage.py) carries id, memory_id, old_memory, new_memory, event, created_at, updated_at, is_deleted, actor_id, role. SQLiteManager guards all writes with a threading.Lock and explicit BEGIN/COMMIT/ROLLBACK; the connection is opened with check_same_thread=False so it is usable from asyncio.to_thread worker threads.

Gotcha The entity-store cleanup helpers are no-ops when self._entity_store is None — the entity store is lazily created on first use. If a process only ever calls delete() without having added/searched (which would have initialized the entity store), the cleanup short-circuits harmlessly. Entity cleanup errors are always swallowed (debug/warning level) so they never break the primary delete/update.

SQLite storage layer

mem0/memory/storage.py defines SQLiteManager, backing two tables that serve the data flow: history (the audit trail surfaced by history()) and messages (the short-term conversation buffer feeding Phase 0 of add).

History writes
add_history(...) inserts one row; batch_add_history(records) uses executemany for the V3 pipeline's bulk ADD. Both assign a fresh UUID per row and wrap the insert in a transaction.
Messages buffer
save_messages(messages, session_scope) inserts the raw turns, then evicts everything beyond the most recent 10 for that scope using a derived-table subquery (forcing SQLite to materialize the ORDER BY before the outer NOT IN). get_last_messages(scope, limit=10) reads the latest N and re-sorts them chronologically for the prompt.
Schema migration
_migrate_history_table detects a legacy group-chat schema, renames the old table, recreates the current schema, copies the intersecting columns, and drops the old table — all inside one transaction with rollback on error.
Perf The 10-message cap on the messages table keeps the Phase-0 context bounded and the table small. Combined with get_last_messages's subquery (latest-N DESC, then ASC re-sort), the engine always feeds the extraction LLM a fixed-size, chronologically ordered recent-history window regardless of how long a session runs.

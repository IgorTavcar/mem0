Memory Algorithm

The April-2026 (SDK v2.0.0 / v3.0.0) rewrite of mem0's memory pipeline replaces the old two-call extract-then-diff algorithm with a single-pass, ADD-only extractor and a multi-signal hybrid retriever. One LLM call extracts every distinct fact from a conversation; memories accumulate and nothing is overwritten or deleted. Retrieval fuses three independently-scored signals — dense semantic similarity, BM25 keyword matching over lemmatized text, and an entity-linking boost — into a single combined score. The benchmarked result is a ~20-26 point accuracy jump (LoCoMo 71.4 to 91.6, LongMemEval 67.8 to 93.4) at roughly 3-4x fewer tokens per operation.

Decision The previous algorithm spent one LLM call extracting candidate facts and a second deciding ADD/UPDATE/DELETE/NONE against existing state. The new algorithm collapses both into a single ADD-only call. The model spends its full capacity on understanding the input rather than diffing against stored memories — which is what drove the accuracy and token-cost wins. See the benchmark results.

Pipeline at a glance

Two halves: an add pipeline that extracts and persists facts, and a search pipeline that scores and fuses retrieval signals. Both live in mem0/memory/main.py on the Memory / AsyncMemory classes; the end-to-end sequences are documented separately, and the class plumbing (factories, history DB, telemetry) in the Memory Engine.

Single-pass ADD-only extraction

One LLM call per add() turn extracts all distinct facts; every result carries event: "ADD". There is no UPDATE, DELETE, or NONE path in the active pipeline.

The phased batch pipeline

The inference path is Memory._add_to_vector_store(messages, metadata, filters, infer=True). It runs eight numbered phases:

Phase 0 — Context gathering
Loads up to 10 prior session messages via db.get_last_messages(session_scope, limit=10) and flattens the new turn with parse_messages().
Phase 1 — Existing-memory retrieval
Embeds the parsed conversation and runs a vector_store.search(top_k=10) scoped to user_id/agent_id/run_id. These memories are context for deduplication and linking only — they are never overwritten.
Phase 2 — LLM extraction (single call)
System prompt is ADDITIVE_EXTRACTION_PROMPT; the user prompt is assembled by generate_additive_extraction_prompt(). Response is forced to {"type": "json_object"} and parsed for a memory array.
Phase 3 — Batch embed
embedding_model.embed_batch(mem_texts, "add") with per-text fallback on failure.
Phase 4-5 — CPU processing + hash dedup
Each fact is lemmatized (text_lemmatized), MD5-hashed, and dropped if its hash already exists (either in the retrieved existing set or earlier in this same batch).
Phase 6 — Batch persist
One vector_store.insert(vectors, ids, payloads) for all new facts, with a one-by-one fallback. A matching batch_add_history() records each as an ADD event in the SQLite history.
Phase 7 — Batch entity linking
See entity linking below.
Phase 8 — Save messages + return
Raw messages are saved to the session store; results are returned as {"id", "memory", "event": "ADD"}.
Insight — anti-hallucination ID mapping The retrieved existing memories are presented to the LLM with sequential integer IDs ("0", "1", ...), and a separate uuid_mapping dict maps those back to real UUIDs. The model never sees raw UUIDs in the dedup context, so it cannot fabricate or corrupt an identifier — it can only reference an index that the code resolves. The model's own output IDs ("0", "1", ...) are throwaway sequence numbers; persisted memories always get a fresh uuid.uuid4().

Why ADD-only — accumulation, not mutation

Information that changes is not reconciled at write time. The new fact is stored alongside the old one, and retrieval ranking is responsible for surfacing the current state. This is the central design bet of the rewrite:

  • Token efficiency — one extraction call instead of extract + diff. The published figure is under 7K tokens per retrieval vs 25K+ for full-context approaches, roughly 3-4x fewer tokens.
  • Accuracy — letting the model focus on comprehension rather than state-diffing yielded +20 (LoCoMo), +26 (LongMemEval), and a jump from 51% to 93% on temporal "where did I live before X" queries. See Evaluation & Benchmarks.
  • No destructive edits — a bad diff decision can no longer delete a correct memory; the worst case is a redundant memory, which the downstream hash dedup and ranking absorb.
Gotcha add() now returns only event: "ADD". Code that branched on UPDATE or DELETE events (pre-v3) will silently never hit those branches. The custom_update_memory_prompt config key is deprecated and ignored — use custom_instructions instead. (Per docs/migration/oss-v2-to-v3.mdx.)
Deep dive: the legacy two-call prompts still ship but are dormant

mem0/configs/prompts.py still defines the old extraction prompt (FACT_RETRIEVAL_PROMPT, USER_MEMORY_EXTRACTION_PROMPT, AGENT_MEMORY_EXTRACTION_PROMPT) and the diff prompt (DEFAULT_UPDATE_MEMORY_PROMPT + get_update_memory_messages()). These are referenced only by mem0/memory/utils.py (get_fact_retrieval_messages, get_fact_retrieval_messages_legacy) and are not wired into the active _add_to_vector_store path, which exclusively uses ADDITIVE_EXTRACTION_PROMPT. Treat the legacy prompts as historical / unused by the OSS core add pipeline. PROCEDURAL_MEMORY_SYSTEM_PROMPT remains live for procedural memories.

The extraction prompt

The active system prompt is ADDITIVE_EXTRACTION_PROMPT (ported from the platform's V3 prompt). Its role definition is explicit: "Your sole operation is ADD." Key behaviors encoded in the prompt:

  • Dual-source extraction — extract from BOTH user and assistant messages. User messages reveal personal facts; assistant messages contribute recommendations, plans, and researched facts (but echoes of what the user already said are skipped).
  • Contextually rich, not atomic — "User has a dog named Poppy and their morning walks are the highlight of their day", not "User has a dog". Transitions must capture old-and-new ("switched from almond milk to oat milk after an almond sensitivity").
  • Self-contained & meaning-preserving — replace pronouns with names/"User"; preserve proper nouns, exact counts, titles. 15-80 words per memory.
  • Deduplication references — the prompt receives Recently Extracted Memories and Existing Memories sections so the model skips already-captured facts.
  • Memory linking — when a new fact relates to an existing one, the model emits the existing memory's real UUID in a linked_memory_ids array.

Agent-generated facts as first-class

The prompt and pipeline treat assistant/agent content as genuinely memorable. The dispatch helper _should_use_agent_memory_extraction() returns true when an agent_id is present and the turn contains assistant messages. When the add is agent-scoped (agent_id set, no user_id), the code appends AGENT_CONTEXT_SUFFIX to the system prompt, which reframes memories from the agent's perspective ("Agent learned that...", "Agent recommended..."). Every extracted memory also carries an attributed_to field ("user" or "assistant") that is promoted into the stored payload.

Insight Multi-speaker conversations are handled too: a named speaker in the "assistant" role (e.g. "Maria: I just got a cat named Bailey") has their personal facts extracted with full rigor and attributed by name. The benchmark for agent/assistant recall went from 46% to 100% under the new algorithm.

Temporal grounding in the prompt

The prompt distinguishes two dates supplied by generate_additive_extraction_prompt(): Observation Date (when the conversation happened) and Current Date (today). Relative references ("yesterday", "last week", "next month") are resolved only against the Observation Date and rewritten to absolute dates, because "User went to Paris last week" is useless six months later while "the week of May 15, 2023" is meaningful forever. _resolve_dates() defaults both to today's UTC date when not provided.

Entity extraction, embedding, and cross-memory linking

Entity linking is the OSS replacement for graph memory (which was removed from the core, ~4000 lines deleted). Instead of an external graph DB, entities are stored in a parallel vector collection and consumed indirectly as a retrieval boost.

Extraction — spaCy, four entity types

mem0/utils/entity_extraction.py exposes extract_entities(text) and a batched extract_entities_batch(texts) (using spaCy's nlp.pipe()). It produces deduplicated (entity_type, entity_text) tuples of four types:

PROPER
Capitalized multi-word sequences with a mid-sequence capital (person names, places, brands).
QUOTED
Single- or double-quoted spans (titles, specific terms) longer than 2 chars.
COMPOUND
Multi-word noun phrases from doc.noun_chunks, lemmatizing noun heads, with extensive filtering of generic heads (_GENERIC_HEADS), non-specific adjectives (_NON_SPECIFIC_ADJ), and generic endings.
NOUN
Single-noun fallback from circumstantial compound patterns (e.g. "solo trip" to "trip").

A type-priority pass keeps the best type per surface form (PROPER > COMPOUND > QUOTED > NOUN), and a final substring pass drops entities fully contained in a longer entity. If spaCy is unavailable, extract_entities returns [] — entity linking silently degrades to off.

Linking — the parallel entity store

The entity store is a lazily-created vector collection named {collection_name}_entities (the entity_store property in main.py clones the main vector-store config and renames the collection; for Qdrant embedded mode it shares the client to avoid RocksDB lock contention). During add Phase 7, _add_to_vector_store:

  1. Batch-extracts entities for all new memory texts.
  2. Globally dedups entities across the batch by normalized lowercase key, tracking which memory IDs each entity appears in.
  3. Batch-embeds the unique entity texts.
  4. entity_store.search_batch(top_k=1) to find existing entities; a match at score >= 0.95 is treated as the same entity, and the new memory IDs are merged into its linked_memory_ids. Otherwise a new entity record is created.
  5. One batch insert for all genuinely-new entities.

So an entity record is effectively an adjacency list: one entity text mapping to every memory it appears in. This is the "graph" — built implicitly, consumed only at search time.

Perf Both the add and search entity paths are aggressively batched: embed_batch for facts and entities, search_batch for entity matching, and a single insert/batch_add_history per turn. AsyncMemory wraps the CPU-bound spaCy calls in asyncio.to_thread so they don't block the event loop.

Multi-signal retrieval and score fusion

Search is implemented in Memory._search_vector_store(query, filters, limit, threshold), called from the public search(). It computes three signals in parallel and fuses them additively.

The three signals

1. Semantic (dense vector)
The query is embedded and searched against the main collection with an over-fetched pool: internal_limit = max(limit * 4, 60). The candidate's similarity becomes semantic_score. This is the only mandatory signal and the only one gated by threshold.
2. BM25 keyword
The query is lemmatized (lemmatize_for_bm25) and passed to vector_store.keyword_search(). Raw BM25 scores are normalized to [0,1] via normalize_bm25. If the store doesn't support keyword search, keyword_search returns None and the signal is simply absent.
3. Entity matching
Query entities are embedded and matched against the entity store; matched entities propagate a bounded boost to their linked memories via _compute_entity_boosts.

BM25 normalization — query-length-adaptive sigmoid

Raw BM25 scores are unbounded and grow with query length, so mem0/utils/scoring.py maps them through a logistic sigmoid whose midpoint/steepness adapt to the number of lemmatized terms (get_bm25_params):

def normalize_bm25(raw_score, midpoint, steepness):
    return 1.0 / (1.0 + math.exp(-steepness * (raw_score - midpoint)))

# get_bm25_params by lemmatized term count:
#   <= 3 terms -> (5.0, 0.7)      7..9 terms  -> (9.0, 0.5)
#   4..6 terms -> (7.0, 0.6)     10..15 terms -> (10.0, 0.5)
#   > 15 terms -> (12.0, 0.5)

Lemmatization for keyword matching

mem0/utils/lemmatization.py normalizes verb forms, comparatives, and plurals (attending/attends/attended to attend; memories to memory) using a lemmatizer-only spaCy pipeline. It also appends the original -ing form alongside the lemma to absorb noun/verb ambiguity ("meeting" vs "meet"). Stored memories are lemmatized at write time into text_lemmatized; queries are lemmatized at search time so both sides of BM25 share a vocabulary. Without spaCy, it falls back to the raw text.

Gotcha — cross-language collection The Python SDK writes the lemmatized field as text_lemmatized (snake_case); the TypeScript SDK writes textLemmatized (camelCase). If a Qdrant collection is shared between the two SDKs, lemma-based BM25 will not resolve across languages — keep collections language-scoped.

Entity boost — spread attenuation

_compute_entity_boosts(query_entities, filters) dedups query entities (max 8), embeds each, and searches the entity store with top_k=500. Only matches with similarity >= 0.5 contribute. The boost for a matched entity is attenuated by how many memories it links to, so a hyper-connected entity (e.g. the user's own name) doesn't dominate:

num_linked = max(len(linked_memory_ids), 1)
memory_count_weight = 1.0 / (1.0 + 0.001 * ((num_linked - 1) ** 2))
boost = similarity * ENTITY_BOOST_WEIGHT * memory_count_weight   # ENTITY_BOOST_WEIGHT = 0.5
# each linked memory takes the MAX boost across all matching entities
memory_boosts[mem_id] = max(memory_boosts.get(mem_id, 0.0), boost)

The boost is therefore capped at 0.5 and shrinks quadratically with link count.

Fusion — additive scoring with an adaptive divisor

score_and_rank(semantic_results, bm25_scores, entity_boosts, threshold, top_k) performs the actual fusion. The threshold gates the semantic score before combining — a candidate below threshold is dropped even if BM25/entity would have boosted it. The combined score is a sum normalized by an adaptive max_possible divisor that reflects which signals are active:

max_possible = 1.0
if has_bm25:   max_possible += 1.0          # semantic + bm25 -> 2.0
if has_entity: max_possible += 0.5          # + entity        -> 2.5

# per candidate:
if semantic_score < threshold: continue     # threshold gates semantic ONLY
raw_combined = semantic_score + bm25_score + entity_boost
combined = min(raw_combined / max_possible, 1.0)

Semantic only1.0
Semantic + BM252.0

Candidates are sorted by the combined score descending and truncated to top_k. The combined value lands on each result's score field.

Insight — the divisor keeps scores comparable Because the normalizer adapts to which signals fired (not a fixed weighting), a semantic-only store and a full hybrid store both produce scores in the same [0,1] range. A memory that scores 0.9 semantically alone and one that scores 0.9 across three fused signals are directly comparable — the entity/BM25 contributions are additive bonuses, never a re-weighting of the baseline semantic relevance.

Reranking sits on top

If search(rerank=True) and a reranker is configured, reranker.rerank(query, original_memories, limit) runs after fusion and re-orders the fused top-K. Reranking failures are caught and the fused order is used as fallback. See Rerankers for where this fits.

Temporal reasoning

Temporal handling is primarily an extraction-time concern, not a separate ranking stage. Because facts are grounded to absolute dates during extraction (Observation Date resolution in ADDITIVE_EXTRACTION_PROMPT), dated instances become independent, individually-retrievable memories rather than a single mutated value.

  • "I moved to SF in 2021, then to Austin in 2023" produces two separate, absolutely-dated memories — neither overwrites the other (ADD-only).
  • A query like "where did I live before SF?" can therefore match the past instance directly via semantic + entity signals, instead of finding only the current-state value. This is exactly the case the benchmarks measured rising from 51% to 93%.
  • Every stored memory carries created_at / updated_at ISO-8601 UTC timestamps (set in _create_memory / the batch payload builder and normalized by _normalize_iso_timestamp_to_utc), available for downstream metadata filtering and for callers that want explicit recency ordering.
Insight The temporal win is a consequence of the ADD-only design plus absolute-date grounding, not a dedicated time-decay ranking function. Current-state vs past vs upcoming queries are disambiguated by the dates baked into each memory's text and resolved by the LLM at extraction time, then surfaced by ordinary multi-signal retrieval.

The optional [nlp] extra and spaCy model

Entity extraction and BM25 lemmatization both depend on spaCy, which is an optional dependency, not a core one. pyproject.toml declares:

# entity linking + BM25 lemmatization
pip install "mem0ai[nlp]"     # installs spacy>=3.7.0

# Qdrant users also need fastembed to enable BM25 sparse vectors
pip install fastembed

mem0/utils/spacy_models.py is the shared, thread-safe loader. It lazily loads two pipelines so entity extraction and lemmatization share one on-disk model instance:

get_nlp_full()
Full pipeline (NER, tagger, parser) for entity extraction.
get_nlp_lemma()
Lemmatizer-only (disable=["ner", "parser"]) for BM25.

_ensure_model_available() auto-downloads en_core_web_sm on first use if spaCy is installed but the model is missing (or instructs python -m spacy download en_core_web_sm on failure). If spaCy itself is absent, both loaders set a sticky failure flag and return None.

Graceful degradation Without the [nlp] extra, mem0 still works — extract_entities returns [] (no entity linking, no entity boost) and lemmatize_for_bm25 returns the raw text. Retrieval falls back to semantic-only with max_possible = 1.0. The Qdrant backend additionally logs "fastembed not installed — BM25 keyword search disabled" on first search and skips the BM25 signal.

Vector-store support for the algorithm

The hybrid retriever leans on a single optional method on the vector store interface: keyword_search(query, top_k, filters). The base class (mem0/vector_stores/base.py) returns None (unsupported) by default; stores that support native full-text / BM25 override it. Backends that implement it include Qdrant, Elasticsearch, OpenSearch, pgvector, Pinecone, Milvus, Weaviate, Redis, MongoDB, Databricks, Azure (AI Search + MySQL), Vertex AI, Baidu, and Upstash. The entity store is just a second collection in the same backend, so no extra infrastructure is needed.

Gotcha Qdrant is unique in encoding sparse BM25 vectors alongside dense vectors in one collection via fastembed (queried with using="bm25"). Other stores use their own native full-text indexes. Either way, if the store cannot do keyword search the algorithm simply drops the BM25 term — no error, scores just renormalize.

Rerankers

The reranker layer is an optional, opt-in second-stage scorer that re-orders the candidate memories returned by mem0's retrieval pipeline before they are handed back to the caller. Every provider implements one method, rerank(query, documents, top_k), which attaches a rerank_score to each document and returns them in descending relevance order. Five concrete providers ship in mem0/reranker/ — cohere, sentence_transformer, huggingface, llm_reranker, and zero_entropy — spanning hosted APIs, local cross-encoders, and LLM-as-judge scoring. Reranking is disabled by default and only runs when both a reranker is configured and the caller passes rerank=True to search().

Where reranking sits in retrieval

Reranking is the last optional step of search(). It consumes the already-scored, already-truncated candidate list produced by the multi-signal retrieval stage and re-orders it.

  • Stage 1 — multi-signal retrieval. Memory._search_vector_store in mem0/memory/main.py runs semantic (vector) search, optional BM25 keyword search, and entity boosts, then fuses them via score_and_rank. See the memory algorithm for the fusion math.
  • Stage 2 — formatting. Each surviving candidate becomes a MemoryItem dict with a memory text field, an id, a fused score, timestamps, and promoted metadata keys.
  • Stage 3 — reranking (optional). If rerank=True and self.reranker is set, the formatted list is passed to self.reranker.rerank(query, original_memories, limit). The reranked list replaces the original and is returned under {"results": [...]}.
Insight The reranker never touches the vector store or embeddings. It receives the already-materialised memory dicts (with full text in the memory field) and only re-orders them. This makes the layer completely orthogonal to which vector store or embedder you use.

Deep dive: the exact invocation in search()

In the synchronous Memory.search (mem0/memory/main.py):

original_memories = self._search_vector_store(query, effective_filters, limit, threshold)

# Apply reranking if enabled and reranker is available
if rerank and self.reranker and original_memories:
    try:
        reranked_memories = self.reranker.rerank(query, original_memories, limit)
        original_memories = reranked_memories
    except Exception as e:
        logger.warning(f"Reranking failed, using original results: {e}")

return {"results": original_memories}

The async AsyncMemory.search is identical except the call is offloaded with await asyncio.to_thread(self.reranker.rerank, query, original_memories, limit) — the providers are synchronous (some are CPU/GPU-bound, some make blocking HTTP calls), so they are run in a thread to avoid blocking the event loop. See the memory engine for the sync/async split.

Gotcha There are two guards. Configuring a reranker is not enough — if the caller does not pass rerank=True, the reranker is silently skipped. Conversely, passing rerank=True with no configured reranker is a no-op (the self.reranker check fails). Reranking also short-circuits on an empty result set (and original_memories).

The base contract: BaseReranker

All providers subclass the abstract BaseReranker in mem0/reranker/base.py, which declares exactly one abstract method.

class BaseReranker(ABC):
    @abstractmethod
    def rerank(self, query: str,
               documents: List[Dict[str, Any]],
               top_k: int = None) -> List[Dict[str, Any]]:
        """Rerank documents based on relevance to the query.
        documents: each with a 'memory' field
        Returns: reranked documents with an added 'rerank_score' field"""
query
The raw search string. Passed through unchanged from search(query=...).
documents
The list of memory dicts from stage 2. Providers extract scorable text by probing memory, then text, then content, falling back to str(doc). In practice mem0 always supplies memory.
top_k
How many documents to keep. search() always passes the request's limit (the top_k argument of search, default 20). Each provider falls back to config.top_k if the argument is None.
Return value
A re-ordered (descending) list of copies of the input dicts, each with a new float rerank_score key.
Design decision: rerank_score is additive, not replacing. Providers do a doc.copy() and set rerank_score without removing the original fused score from stage 1. Downstream consumers therefore see both the retrieval score and the rerank score; the ordering of the returned list reflects rerank_score.
Gotcha — score scales are not comparable across providers. The rerank_score means different things per provider: Cohere/ZeroEntropy return an API-defined relevance score, the LLM reranker returns a 0.0–1.0 judged score, SentenceTransformer returns raw cross-encoder logits (unbounded), and HuggingFace optionally min–max normalises to [0,1]. Do not assume a common scale.

Shared resilience pattern: graceful fallback

Every provider wraps its scoring call in try/except Exception and, on any failure, falls back to the original order with rerank_score = 0.0 rather than raising.

# Pattern shared by cohere / sentence_transformer / huggingface / zero_entropy
except Exception:
    for doc in documents:
        doc['rerank_score'] = 0.0
    return documents[:top_k] if top_k else documents
  • The LLMReranker is finer-grained: it catches per-document scoring errors and assigns a neutral 0.5 to the failing document, so one bad call does not blank the whole list.
  • This provider-level fallback is in addition to the try/except in search() itself, which logs a warning and reverts to the unreranked results if rerank() raises entirely.
Performance / correctness note The bare-except fallbacks mean reranking failures are silent at the provider level (no log) and produce uniform 0.0 scores. If you see every result carrying rerank_score == 0.0, reranking failed and you are looking at the original retrieval order, not a relevance ordering. The two non-fallback providers that do sort even in the happy path differ in whether they re-sort the API response (see ZeroEntropy below).

Providers

Five concrete rerankers live in mem0/reranker/. Each lazily imports its heavy/optional dependency at module load and raises a helpful ImportError only when instantiated without the package installed.

Cohere — CohereReranker

Hosted reranking via Cohere's rerank API. File: mem0/reranker/cohere_reranker.py; config: CohereRerankerConfig.

  • Dependency: cohere (pip cohere). Guarded by COHERE_AVAILABLE.
  • Default model: rerank-english-v3.0.
  • Auth: config.api_key or the COHERE_API_KEY env var; raises ValueError if neither is set.
  • API call: client.rerank(model, query, documents=doc_texts, top_n=top_k or config.top_k or len(documents), return_documents=..., max_chunks_per_doc=...). The API returns results already sorted by relevance; the provider maps result.index back to the original dict and copies result.relevance_score into rerank_score. No client-side re-sort needed.
  • Extra config knobs: return_documents (default False), max_chunks_per_doc (default None).

SentenceTransformer — SentenceTransformerReranker

Local cross-encoder reranking via sentence-transformers. File: mem0/reranker/sentence_transformer_reranker.py; config: SentenceTransformerRerankerConfig.

  • Dependency: sentence-transformers (imports CrossEncoder). Guarded by SENTENCE_TRANSFORMERS_AVAILABLE.
  • Default model: cross-encoder/ms-marco-MiniLM-L-6-v2.
  • Scoring: builds [query, doc_text] pairs, calls model.predict(pairs, batch_size, show_progress_bar), then sorts descending by raw score (numpy arrays are converted with .tolist()). Scores are not normalised — they are raw cross-encoder outputs.
  • Config knobs: device (auto via CrossEncoder if None), batch_size (32), show_progress_bar (False).
  • Exported by package: yes — one of only two names re-exported from mem0/reranker/__init__.py.

HuggingFace — HuggingFaceReranker

Local cross-encoder reranking driven directly through Transformers + Torch. File: mem0/reranker/huggingface_reranker.py; config: HuggingFaceRerankerConfig.

  • Dependency: transformers + torch (imports AutoTokenizer, AutoModelForSequenceClassification). Guarded by TRANSFORMERS_AVAILABLE.
  • Default model: BAAI/bge-reranker-base.
  • Device: auto-detects cuda vs cpu via torch.cuda.is_available() when config.device is None; model is moved to device and put in .eval() mode at init.
  • Scoring: batches [query, doc] pairs, tokenises with padding/truncation and max_length, runs the model under torch.no_grad(), squeezes logits to scores. Handles the single-item (0-dim tensor) edge case explicitly.
  • Normalisation: if config.normalize (default True), applies min–max scaling (s - min)/(max - min + 1e-8) to map scores into [0,1].
  • Config knobs: device, batch_size (32), max_length (512), normalize (True).
Insight — HuggingFace vs SentenceTransformer overlap. Both are local cross-encoders. SentenceTransformer wraps the higher-level CrossEncoder abstraction (handles tokenisation/batching internally), while HuggingFace drives the raw Transformers model and adds explicit batching, min–max normalisation, and device handling. Choose HuggingFace for finer control / normalised [0,1] scores; SentenceTransformer for the simpler, well-trodden path.

LLM-as-judge — LLMReranker

Uses an LLM to score each document's relevance on a 0.0–1.0 scale. File: mem0/reranker/llm_reranker.py; config: LLMRerankerConfig; provider key is llm_reranker.

  • Dependency: none extra — reuses the existing LLM provider layer via LlmFactory.create(...) from mem0/utils/factory.py.
  • Default model / provider: gpt-4o-mini on openai, temperature=0.0 (deterministic), max_tokens=100.
  • Nested LLM config: supports a llm dict with provider/config keys so non-OpenAI backends (e.g. Ollama needing ollama_base_url) can be configured; it overrides the top-level provider/model/api_key when present.
  • Prompt: a fixed _SYSTEM_PROMPT instructs the model to return a single number 0.0–1.0 with a banded rubric (1.0 = perfectly relevant ... 0.0–0.3 = not relevant). The query and document are sent as a separate user message.
  • Score extraction: _extract_score regex-matches the first [01](?:\.\d+)? token, clamps to [0,1], and defaults to 0.5 if no number is found.
  • Sorting: scores every document (one LLM call each), sorts descending, then truncates to top_k (arg) or config.top_k.
Security — prompt-injection hardening. The reranker truncates both query and document to _MAX_INPUT_LEN = 4000 chars and sends instructions in the system role with user data in the user role, so memory text cannot override the scoring instructions. This was a deliberate change from an earlier single-prompt design.
Performance — N LLM calls per search. LLMReranker makes one synchronous LLM call per candidate document. With the default over-fetch this can be dozens of round-trips, making it by far the slowest and most expensive provider. It is best reserved for small candidate pools or offline/eval use (see evaluation).
Deprecation LLMRerankerConfig.scoring_prompt is deprecated. If supplied it is used as the system message but emits a DeprecationWarning ("will be removed in a future version. The prompt is now used as the system message."). Prefer the built-in rubric.

ZeroEntropy — ZeroEntropyReranker

Hosted reranking via the ZeroEntropy API. File: mem0/reranker/zero_entropy_reranker.py; config: ZeroEntropyRerankerConfig; provider key zero_entropy.

  • Dependency: zeroentropy (imports ZeroEntropy client). Guarded by ZERO_ENTROPY_AVAILABLE.
  • Default model: zerank-1 (config also documents zerank-1-small).
  • Auth: config.api_key or ZERO_ENTROPY_API_KEY env var; raises ValueError if neither is present.
  • API call: client.models.rerank(model, query, documents=doc_texts). Maps result.index back to the source dict, copies result.relevance_score, then explicitly re-sorts descending client-side and applies top_k — unlike the Cohere provider, which trusts the API's order and top_n.

Provider key vs filename mismatch. The factory key for the LLM reranker is llm_reranker (not llm), and for the cross-encoder it is sentence_transformer (singular, no trailing s). Using the wrong key raises ValueError: Unsupported reranker provider: ....
Package export vs registry. mem0/reranker/__init__.py only re-exports BaseReranker, CohereReranker, and SentenceTransformerReranker. The other three providers are not in __all__ but are still fully usable — the RerankerFactory imports them lazily by dotted path, so the package __all__ is incomplete, not authoritative. Always count the *_reranker.py files (five) for the true provider set.

Configuration

Reranking is wired through the same provider-config pattern as the rest of mem0 (see the configuration system).

Config shape

  • MemoryConfig.reranker (in mem0/configs/base.py) is an Optional[RerankerConfig] defaulting to None — so reranking is off unless explicitly configured.
  • RerankerConfig (mem0/configs/rerankers/config.py) has just two fields: provider (default "cohere") and config (a provider-specific dict). It sets model_config = {"extra": "forbid"}, so unknown top-level keys are rejected.
  • Each provider has its own Pydantic config subclassing BaseRerankerConfig (mem0/configs/rerankers/base.py), which defines the common fields provider, model, api_key, top_k.

The factory

RerankerFactory in mem0/utils/factory.py is the fourth-and-a-bit factory in the codebase (alongside LLM, embedder, vector-store factories). Its provider_to_class registry maps each key to a (dotted_class_path, config_class) tuple:

provider_to_class = {
    "cohere":               ("mem0.reranker.cohere_reranker.CohereReranker", CohereRerankerConfig),
    "sentence_transformer": ("mem0.reranker.sentence_transformer_reranker.SentenceTransformerReranker", SentenceTransformerRerankerConfig),
    "zero_entropy":         ("mem0.reranker.zero_entropy_reranker.ZeroEntropyReranker", ZeroEntropyRerankerConfig),
    "llm_reranker":         ("mem0.reranker.llm_reranker.LLMReranker", LLMRerankerConfig),
    "huggingface":          ("mem0.reranker.huggingface_reranker.HuggingFaceReranker", HuggingFaceRerankerConfig),
}

RerankerFactory.create(provider_name, config) validates the provider key, coerces a dict into the right config class (forwarding extra **kwargs), lazily imports the class with load_class, and instantiates it. An unknown key raises ValueError; a failed import (missing optional dependency) raises ImportError. The Memory constructor calls it once at init time: RerankerFactory.create(config.reranker.provider, config.reranker.config).

Example configurations

from mem0 import Memory

# Local cross-encoder, no API key needed
m = Memory.from_config({
    "reranker": {
        "provider": "sentence_transformer",
        "config": {"model": "cross-encoder/ms-marco-MiniLM-L-6-v2", "top_k": 10},
    }
})

# Must still opt in per call:
m.search("dietary preferences", filters={"user_id": "alice"}, top_k=10, rerank=True)
# Hosted Cohere reranker
{"reranker": {"provider": "cohere",
              "config": {"model": "rerank-english-v3.0", "api_key": "..."}}}

# LLM-as-judge over a local Ollama model via nested llm config
{"reranker": {"provider": "llm_reranker",
              "config": {"llm": {"provider": "ollama",
                                 "config": {"model": "llama3", "ollama_base_url": "http://localhost:11434"}}}}}
Default provider quirk. RerankerConfig.provider defaults to "cohere", but this default only applies if you supply a reranker block without a provider. Omitting the reranker block entirely leaves MemoryConfig.reranker = None and no reranker is created.

Document shape and text extraction

The documents handed to rerank() are the MemoryItem dicts built in _search_vector_store. Their text lives in the memory key:

{
  "id": "…",
  "memory": "User is allergic to peanuts",
  "hash": "…",
  "created_at": "…",
  "updated_at": "…",
  "score": 0.82,
  "user_id": "alice",
  "metadata": { /* non-core payload keys */ }
}

Every provider uses the same defensive text-extraction ladder: memory → text → content → str(doc). Only memory is ever produced by mem0's own pipeline; the other branches make the rerankers reusable with foreign document shapes.

Reranking on the hosted client

The hosted MemoryClient also exposes a rerank flag: SearchOptions.rerank: Optional[bool] in mem0/client/types.py and the documented rerank kwarg on MemoryClient.search / AsyncMemoryClient.search (mem0/client/main.py). On the hosted path the flag is forwarded to the platform API; the OSS reranker classes in this layer run only inside the self-hosted Memory engine.

Adding a new reranker

  1. Create mem0/reranker/<name>_reranker.py with a class subclassing BaseReranker and implementing rerank(self, query, documents, top_k=None); guard any optional import and add the graceful-fallback except.
  2. Create mem0/configs/rerankers/<name>.py with a config subclassing BaseRerankerConfig for provider-specific fields.
  3. Register the (dotted_path, ConfigClass) tuple in RerankerFactory.provider_to_class and import the config in mem0/utils/factory.py.
  4. (Optional) re-export the class from mem0/reranker/__init__.py for direct import.

This is the same provider-plugin pattern used throughout the codebase — see the architecture overview.

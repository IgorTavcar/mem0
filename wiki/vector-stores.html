Vector Stores

The vector store layer is the persistence and retrieval backbone of mem0: every memory is a dense embedding plus a JSON payload, written to and queried from one of 24 pluggable backends behind a single abstract interface, VectorStoreBase. Stores share a common insert / search / get / list / delete / update contract plus collection lifecycle ops, and an enhanced filter dialect (comparison, list, string, and AND/OR/NOT logical operators) that each provider translates into its native query language. Qdrant is the default and the richest implementation (hybrid dense + BM25 sparse search); pgvector ships rich SQL filter operators; about two-thirds of providers add native keyword/BM25 search used by the hybrid retrieval algorithm.

Role in the system

The vector store is one of the four pluggable provider families wired by the configuration system, alongside LLMs, embeddings, and rerankers. The Memory engine owns exactly one vector store instance (self.vector_store) and calls into it during both add() and search().

  • On add: the engine extracts memory facts, embeds them via the embedding model, builds a payload, and calls vector_store.insert(vectors, payloads, ids). See the data flow.
  • On search: the engine embeds the query and calls vector_store.search(query, vectors, top_k, filters), optionally also vector_store.keyword_search(...) for the BM25 leg of hybrid retrieval, then fuses scores. See the algorithm.
  • Lifecycle: get, list, update, delete, and reset back the corresponding public Memory methods and the history table.
Insight The store is responsible only for vectors + payloads. There is no LLM, no extraction, no scoring logic inside a provider class — those live in the engine. A provider's entire job is to faithfully translate the common interface into one backend's API and return results in a shape the engine can read (.id, .score, .payload).

The common interface: VectorStoreBase

Defined in mem0/vector_stores/base.py as an ABC. Every provider subclasses it and must implement the abstract methods; two methods have default (overridable) implementations.

Abstract methods (must implement)

create_col(self, name, vector_size, distance)
Create a collection/index/table. Signatures vary per provider (Qdrant uses create_col(vector_size, on_disk, distance); PGVector takes no args and reads instance state) — the base signature is nominal, not enforced at the type level.
insert(self, vectors, payloads=None, ids=None)
Bulk upsert: three parallel lists. The engine always supplies all three.
search(self, query, vectors, top_k=5, filters=None)
Dense ANN search. Note both query (raw text) and vectors (the embedding) are passed; pure vector stores ignore query, while hybrid-capable stores may use it.
get(self, vector_id) / delete(self, vector_id) / update(self, vector_id, vector=None, payload=None)
Single-record CRUD by id. update supports vector-only, payload-only, or both.
list(self, filters=None, top_k=None)
Enumerate memories matching filters (no query vector). Used for unfiltered "get all" style reads and the engine's bookkeeping.
list_cols() / delete_col() / col_info()
Collection-level metadata operations.
reset(self)
Documented as "delete the collection and recreate it" — the canonical implementation calls self.delete_col() then self.create_col(...).

Default methods (optional override)

keyword_search(self, query, top_k=5, filters=None) -> None
BM25 / full-text keyword search. The base returns None, signalling "not supported." Stores that override it return results in the same shape as search(). The docstring notes the query "should be lemmatized for best results" — the engine pre-lemmatizes via lemmatize_for_bm25.
search_batch(self, queries, vectors_list, top_k=1, filters=None)
Batch multi-query search. The base loops over search() sequentially. Only Qdrant overrides it with a native batched call (query_batch_points).
Gotcha keyword_search returning None is a deliberate sentinel, not an error. The engine checks if keyword_results is not None before computing BM25 scores — so a store without keyword support silently degrades to pure semantic search, no exception raised. Don't return [] from an unsupported store; that would falsely claim "supported, zero hits."

Registration and instantiation

There is no plugin auto-discovery. Two hand-maintained maps must agree for a provider to work:

  1. Config map — VectorStoreConfig._provider_configs in mem0/vector_stores/configs.py maps a provider string to its Pydantic config class (e.g. "qdrant" -> "QdrantConfig"), which lives under mem0/configs/vector_stores/<provider>.py.
  2. Class map — VectorStoreFactory.provider_to_class in mem0/utils/factory.py maps the same string to a fully-qualified implementation class path (e.g. "qdrant" -> "mem0.vector_stores.qdrant.Qdrant"), loaded lazily via load_class.
Gotcha — keep both maps in sync The two maps must list the same provider keys (they currently agree on all 24). Note the keys point at different naming conventions: the config map gives a bare class name resolved relative to mem0.configs.vector_stores.<provider> (e.g. "neptune" -> "NeptuneAnalyticsConfig"), while the factory gives a fully-qualified implementation path (e.g. "neptune" -> "mem0.vector_stores.neptune_analytics.NeptuneAnalyticsVector"). Adding a provider means editing both maps plus creating the config module; forgetting the config entry yields "Unsupported vector store provider," forgetting the factory entry yields the same error from VectorStoreFactory.create.
Deep dive: how VectorStoreConfig validates and constructs

The @model_validator(mode="after") hook validate_and_create_config does the work: it rejects unknown providers, dynamically __import__s the provider config module, and — for file-backed stores — auto-injects a default path of /tmp/<provider> if the config class declares a path annotation and none was supplied. It then replaces the raw dict with a typed config instance. The factory later does config.model_dump() and splats it as kwargs into the provider constructor, so every provider's __init__ parameters must mirror its config fields.

# configs.py (paraphrased)
if "path" not in config and "path" in config_class.__annotations__:
    config["path"] = f"/tmp/{provider}"
self.config = config_class(**config)

The 24 providers

Counted directly from mem0/vector_stores/ (excluding base.py, configs.py, __init__.py). All 24 appear in VectorStoreFactory.provider_to_class:

qdrant (default), chroma, pgvector, pinecone, milvus, mongodb, redis, valkey, elasticsearch, opensearch, weaviate, faiss, azure_ai_search, azure_mysql, databricks, vertex_ai_vector_search, supabase, upstash_vector, s3_vectors, baidu, cassandra, neptune (Neptune Analytics), langchain, turbopuffer.

Design Two providers are "meta" adapters rather than direct backends: langchain wraps any LangChain VectorStore object (delegating to similarity_search_by_vector), and s3_vectors targets Amazon S3 Vectors. valkey is a Redis-compatible fork with its own dedicated implementation (~32 KB, the largest provider file). turbopuffer (PR #4428) and the rich-operator pgvector rework are among the most recent additions.

Provider import strategy

Every provider does a top-level import of its client SDK and raises a clear ImportError with the right pip install hint if the optional dependency is missing (e.g. turbopuffer, langchain, qdrant). This keeps the core install slim — you only pull the SDK for the store you actually use.

The payload / metadata model

mem0 stores a flat JSON payload alongside each vector. The engine builds it in memory/main.py at insert time. The canonical core keys are:

data
The memory text itself (the human-readable fact).
hash
MD5 of data, used for batch and cross-run dedup before insert.
text_lemmatized
Lemmatized form of data (via lemmatize_for_bm25). This is the field BM25 / full-text indexes are built on — Qdrant encodes it into a sparse vector, pgvector builds a GIN to_tsvector index over it.
created_at / updated_at
ISO-8601 timestamps (UTC).
user_id / agent_id / run_id / actor_id / attributed_to
Scoping/partition identifiers. Several stores (Qdrant, Redis) index these specifically for fast filtering.

Arbitrary user metadata is merged into the same flat dict. The engine tracks a set of core_and_promoted_keys (data, hash, created_at, updated_at, id, text_lemmatized, attributed_to + promoted keys) to separate first-class fields from free-form metadata when reconstructing results.

Performance Because text_lemmatized is precomputed at write time, keyword search never has to re-tokenize the corpus at query time — it only lemmatizes the incoming query. This is what makes hybrid search cheap enough to run on every search().
Deep dive: Redis's non-flat storage

Redis is the notable exception to "flat payload." Its insert promotes a fixed schema (memory_id, hash, memory, created_at, user_id/agent_id/run_id, embedding) and JSON-encodes everything else into a single metadata text field, excluding the keys in excluded_keys (user_id, agent_id, run_id, hash, data, created_at, updated_at). On read it reverses this: rebuilds data from memory, converts the integer timestamps back to ISO strings, and spreads the decoded metadata back into the payload. Timestamps are stored as integer Unix epochs in numeric fields, which is why Redis must convert in both directions.

The result shape: OutputData and friends

The engine reads results duck-typed by attribute: result.id, result.score, result.payload. There is no single shared result class — instead each provider defines its own lightweight container that exposes those three attributes:

  • Many providers define a local class OutputData(BaseModel) with id: Optional[str], score: Optional[float], payload: Optional[dict] (pgvector, faiss, turbopuffer, pinecone, milvus, weaviate, mongodb, supabase, elasticsearch, opensearch, baidu, cassandra, azure_ai_search, azure_mysql, s3_vectors, upstash_vector, langchain, neptune, vertex_ai_vector_search, valkey).
  • Redis defines a plain class MemoryResult with the same three attributes.
  • Qdrant returns native qdrant_client point objects directly (which already carry .id, .score, .payload) — no wrapper class at all.
Gotcha — list() return nesting list() is inconsistent across providers. Several (pgvector, turbopuffer, redis) return a doubly-nested list [[OutputData, ...]], while Qdrant's list() returns the raw scroll() tuple (points, next_offset). search() by contrast returns a flat list. Callers must know which method they're using; the engine handles the unwrapping.
Score sign convention score is provider-defined and not normalized. pgvector returns cosine distance (vector <=> %s, lower is closer); turbopuffer converts distance to similarity as 1 - dist; Redis returns raw vector_distance. The engine's score fusion accounts for this, but raw .score values are not comparable across stores.

How filters work

mem0 exposes an enhanced, store-agnostic filter dialect. The engine normalizes user filters in Memory._process_metadata_filters() (in memory/main.py), then each provider translates the normalized dict into its backend's native query.

Supported operators

Equality / shorthand
{"user_id": "alice"} — scalar equality. A bare list {"field": ["a","b"]} is treated as an in by some stores (e.g. Qdrant, pgvector).
Comparison
eq, ne, gt, gte, lt, lte — e.g. {"created_at": {"gte": "2026-01-01"}}.
List membership
in, nin — e.g. {"category": {"in": ["a","b"]}}.
String matching
contains, icontains (case-insensitive).
Wildcard / existence
{"field": "*"} — field exists / match any.
Logical
AND, OR, NOT — each takes a list of sub-filter dicts.

Engine-side normalization

_process_metadata_filters maps the operator names through an operator_map, flattens top-level AND into a merged dict (deep-merging same-key operator dicts), and rewrites OR -> "$or" and NOT -> "$not" as pass-through lists for the store to interpret. _has_advanced_operators detects whether a filter needs this richer processing at all.

Gotcha — the OR/$or casing duality The engine renames OR ->$or / NOT ->$not, but the engine also keeps original-cased keys in some effective_filters built from deepcopy(input_filters). Qdrant's _create_filter therefore normalizes both spellings ($or/$and/$not -> OR/AND/NOT) and deduplicates, explicitly to avoid evaluating the same sub-condition twice. pgvector keys off the $or/$not spelling.

Per-store translation: two reference implementations

Qdrant — typed conditions

_build_field_condition maps each operator to a Qdrant primitive: eq -> MatchValue, ne -> MatchExcept, in -> MatchAny, nin -> MatchExcept, range ops -> Range (or DatetimeRange when all values match an ISO-8601 regex), contains/icontains -> MatchText. _create_filter assembles must (AND), should (OR), must_not (NOT) clauses recursively. Mixing range and non-range operators on one field raises ValueError; the wildcard "*" is dropped (matches all).

pgvector — SQL fragment builder

_build_filter_conditions compiles filters into parameterized SQL via the OPERATOR_SQL_MAP table, all keyed off JSONB payload->> extraction:

OPERATOR_SQL_MAP = {
    "eq":  ("payload->>%s = %s", False),
    "gt":  ("(payload->>%s)::numeric > %s", True),   # numeric coercion
    "in":  ("payload->>%s = ANY(%s)", False),
    "contains":  ("payload->>%s LIKE %s",  False),
    "icontains": ("payload->>%s ILIKE %s", False),
    # ... ne, gte, lt, lte, nin
}

It handles $or (OR of AND-groups) and $not recursively, and uses payload ? %s (JSONB key-exists) for the "*" wildcard.

Recent hardening (PR #5264, #5263, #4997) The pgvector filter path was repeatedly fixed for: boolean filter casing — booleans are now serialized with json.dumps(value) (yielding "true"/"false" to match how JSONB stores them) instead of Python's "True"/"False"; LIKE escaping — contains/icontains values escape \, %, _ and append ESCAPE '\' so user input can't inject wildcards; and SQL injection — all identifiers use psycopg.sql.Identifier and all values are bound parameters, never string-interpolated.
Deep dive: FAISS does in-memory post-filtering

FAISS has no server-side filter engine. Its search over-fetches (fetch_k = top_k * 2 when filters are present) and then calls _apply_filters(payload, filters) on each candidate's payload in Python, keeping only matches. This is correct but means filtered FAISS searches can under-return if the true matches fall outside the over-fetch window — a fundamental limitation of brute-force local indexes.

Hybrid & keyword search

The April-2026 OSS pipeline (ported in PR #4805) added native keyword/BM25 search to the store layer so the engine can fuse semantic + lexical signals. See score fusion in the algorithm.

How the engine drives it

Inside _search_vector_store, the engine: (1) lemmatizes the query, (2) embeds it, (3) over-fetches semantic results with internal_limit = max(limit*4, 60), (4) calls keyword_search(query=query_lemmatized, ...), and (5) if that returns non-None, normalizes the BM25 scores and folds them into the additive scoring pool alongside entity boosts and recency. The async engine wraps each blocking store call in asyncio.to_thread.

Which stores implement keyword_search

15 providers override the default (verified by grepping def keyword_search, excluding base.py):

qdrant, pgvector, redis, milvus, mongodb, elasticsearch, opensearch, pinecone, weaviate, databricks, baidu, upstash_vector, azure_ai_search, azure_mysql, vertex_ai_vector_search. The remaining 9 (including faiss, chroma, valkey, supabase, turbopuffer, cassandra, s3_vectors, langchain, neptune) inherit the None default and run semantic-only.

Mechanisms differ by store

Qdrant
True sparse-vector hybrid. Each collection (v3+) gets a named bm25 sparse-vector slot with IDF modifier. On insert, text_lemmatized is encoded to a BM25 sparse vector via fastembed (Qdrant/bm25); keyword_search queries using="bm25".
pgvector
PostgreSQL full-text search: a GIN index over to_tsvector('simple', payload->>'text_lemmatized'), ranked by ts_rank_cd with plainto_tsquery.
Redis
RediSearch TextQuery over the memory text field.
Gotcha — Qdrant collections predating v3 Collections created before the hybrid-search work lack the bm25 sparse slot. Writing a BM25 vector into them is rejected ("Not existing vector name error: bm25"), so Qdrant detects this on init (_has_bm25_slot), logs a warning, and disables BM25 for that collection — semantic search still works. To get hybrid, use a fresh collection. The fastembed dependency is also optional and lazy-loaded; if it's not installed, BM25 is silently disabled with an install hint.

The default store: Qdrant

VectorStoreConfig.provider defaults to "qdrant" and with no other config it runs an embedded local instance writing to a path (auto-defaulted to /tmp/qdrant). It is the most feature-complete provider:

  • Hybrid by default: collections are created with both dense (VectorParams, cosine) and named bm25 sparse slots.
  • Native batch search: the only store overriding search_batch, using query_batch_points with a sequential fallback on error.
  • Payload indexes: on remote servers it auto-creates keyword indexes for user_id, agent_id, run_id, actor_id to accelerate filtering. Local (embedded) Qdrant skips index creation — it isn't supported there.
  • Datetime-aware ranges: range filters whose values are ISO-8601 strings use DatetimeRange instead of numeric Range.
Partial-update caveat Qdrant's update with only a payload uses set_payload, which cannot refresh the BM25 sparse vector — so a payload-only update leaves any existing BM25 vector stale. The code notes this is acceptable in practice because the v3 engine re-embeds (full update) whenever memory text changes.

Reset and collection lifecycle

Each store's reset() drops and recreates its collection — the canonical destructive "start fresh." VectorStoreFactory.reset(instance) provides a factory-level reset entry point used by the engine's Memory.reset().

Gotcha — Redis create_col(overwrite=True) Redis calls index.create(overwrite=True) on every __init__. With overwrite=True on RediSearch this drops the index definition (not necessarily the underlying keys depending on version) — be careful pointing two processes at the same collection name.

Adding a new provider (checklist)

  1. Create mem0/vector_stores/<name>.py with a class subclassing VectorStoreBase; implement all abstract methods. Lazy/guarded-import the client SDK with a helpful ImportError.
  2. Define a result container exposing .id, .score, .payload (reuse the local OutputData pattern).
  3. Implement filter translation from the normalized dialect ($or/$not + operator dicts). Match on text_lemmatized if you want hybrid; override keyword_search.
  4. Create mem0/configs/vector_stores/<name>.py with a Pydantic config whose fields mirror your __init__ params.
  5. Register in both maps: VectorStoreConfig._provider_configs and VectorStoreFactory.provider_to_class.

This mirrors the provider plugin pattern used by LLMs and embeddings, described in the architecture overview. For where this all sits in the request path see data flow and the memory engine.

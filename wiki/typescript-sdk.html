TypeScript SDK

The mem0ai npm package ships two independent surfaces from one repo (mem0-ts/): a thin hosted-platform client (import { MemoryClient } from "mem0ai") and a full self-contained OSS memory engine (import { Memory } from "mem0ai/oss"). The OSS side is a faithful port of the Python Memory engine — same config-driven provider factories, same April-2026 single-pass additive extraction algorithm, same entity-linking retrieval — built dual-format (CJS + ESM) with tsup and tested with Jest. The most consequential divergences from Python: the TS SDK has no async/await-duplicated AsyncMemory classes (everything is already promise-based), no LLM proxy wrapper, and no graph-memory store on the OSS side.

Package layout & two surfaces

One npm package, two entry points wired through the exports map in mem0-ts/package.json.

"." → src/client/index.ts
The hosted platform client. Re-exports MemoryClient (also as default), all request/response types, the Feedback/WebhookEvent enums, and the structured exception classes from src/common/exceptions.ts. This is the surface most users import.
"./oss" → src/oss/src/index.ts
The OSS memory engine. Re-exports the Memory class, all provider classes (LLMs, embedders, vector stores) and their base interfaces, the types, and the four factories. Equivalent to from mem0 import Memory in Python.
Gotcha The package name is mem0ai, not mem0-ts. The OSS README.md still shows import { Memory } from "mem0-ts" and a stale memory.add("text", "user123") positional signature — both are out of date. The real OSS import is mem0ai/oss and add() takes (messages, { userId }). Trust the code, not that README.

Two additional source areas sit alongside:

  • src/common/ — shared exceptions.ts (the structured error hierarchy used by both the client and the OSS engine via re-export).
  • src/community/ — a separately published package @mem0/community (own package.json, version 0.0.1) holding the LangChain integration (src/community/src/integrations/langchain/). It is marked external in the main tsup config so it is never bundled into mem0ai.

Hosted client — MemoryClient

A thin REST wrapper around the mem0 platform (https://api.mem0.ai by default), defined as the default export of src/client/mem0.ts. Mirrors the Python hosted client.

Construction & auth

  • Constructor takes { apiKey, host? }; sends Authorization: Token <apiKey>. An axios instance (60s timeout) is created for a couple of calls, but most requests go through a private _fetchWithErrorHandling() that uses the global fetch.
  • The constructor fires _initializeClient() which calls ping() (GET /v1/ping/) to validate the key and learn orgId/projectId/userEmail. Every public method lazily re-pings if telemetryId is still empty.
Perf / case translation All outbound payloads pass through camelToSnakeKeys() and all responses through snakeToCamelKeys() (src/client/utils.ts). TS users write camelCase (userId, pageSize, latestOnly) and the wire stays snake_case. camelToSnake() deliberately skips all-uppercase keys so logical operators AND/OR/NOT survive untouched.

Method surface

The client speaks a mix of API versions — note add/getAll/search target v3 while CRUD targets v1:

latestOnly & deleteLinked Both v3-algorithm features are wired on the TS client. latestOnly?: boolean on SearchMemoryOptions and GetAllMemoryOptions flows through camelToSnakeKeys and serializes to latest_only (verified by memoryClient.search.test.ts). deleteLinked?: boolean on DeleteMemoryOptions is the delete-side counterpart — it is off by default and serialized as the delete_linked query param (verified by memoryClient.crud.test.ts); it cascades deletion of the older memories a memory superseded in the v3 linked chain.
Entity params must go in filters Both the client and the OSS engine call rejectTopLevelEntityParams(): passing user_id/agentId/etc. at the top level of search()/getAll() throws. The correct shape is { filters: { user_id: "u1" } }. (The hosted client checks both snake and camel spellings, including app_id.)

OSS engine — Memory

A complete local memory engine in src/oss/src/memory/index.ts — no platform account needed. It owns an embedder, a vector store, an LLM, a history store, and (lazily) an entity store, all created by the four factories from a single config object. This is the TS twin of the Python Memory class.

Construction & deferred initialization

  • new Memory(config?) validates & merges via ConfigManager.mergeConfig() against a Zod schema (MemoryConfigSchema in src/oss/src/types/index.ts). Embedder, LLM and history store are created synchronously in the constructor; the vector store is deferred.
  • A private _initPromise runs _autoInitialize(): if no dimension was configured, it embeds a probe string ("dimension probe") to auto-detect the embedding dimension, then constructs and initialize()s the vector store. Every public method first awaits _ensureInitialized().
  • static fromConfig(dict) mirrors Python's Memory.from_config.
Insight: init self-heals _ensureInitialized() stores the first failure in _initError instead of throwing from the constructor, then retries _autoInitialize() on the next method call — so a transiently-down embedder/vector store at startup doesn't permanently brick the instance.

Public methods

add(messages, { userId? | agentId? | runId?, metadata?, infer?, filters? })
Returns { results: MemoryItem[] }. At least one of userId/agentId/runId is required. Entity IDs are trimmed and validated (no whitespace, non-empty) by validateAndTrimEntityId() and folded into both filters and metadata as snake_case. With infer: false each message is stored verbatim; with infer: true it runs the phased pipeline below.
search(query, { filters, topK?, threshold? })
Multi-signal retrieval (semantic + BM25 keyword + entity boost). Validates threshold ∈ [0,1] and integer topK ≥ 0. Defaults topK = 20, threshold = 0.1.
get / getAll / update / delete / deleteAll / history / reset
getAll defaults topK = 20; reset() clears history + drops the vector collection (skipped for the langchain provider) + drops the entity store, then re-initializes.
No AsyncMemory in TS Python exposes both a synchronous Memory and an AsyncMemory with duplicated method bodies. TypeScript needs neither: every method on the single Memory class already returns a Promise, so there is exactly one class. This is a structural divergence, not a feature gap.

The v3 add() pipeline (algorithm parity)

When infer: true, addToVectorStore() runs the same single-pass ADD-only additive extraction the Python side uses — see the algorithm page for the full design. The TS implementation is an explicit phased batch pipeline:

flowchart TD
  P0[Phase 0: fetch last-K session messages from history] --> P1[Phase 1: embed input, search vector store for ~10 existing memories]
  P1 --> P2["Phase 2: ONE LLM call — ADDITIVE_EXTRACTION_PROMPT + existing memories (UUIDs masked as integers)"]
  P2 --> P3[Phase 3: batch-embed extracted memory texts]
  P3 --> P4[Phase 4-5: md5 hash dedup vs existing + within-batch]
  P4 --> P6[Phase 6: batch insert vectors + batch history ADD]
  P6 --> P7[Phase 7: batch entity extraction + linking into entity store]
  P7 --> P8[Phase 8: persist raw messages]
  • Prompt parity: ADDITIVE_EXTRACTION_PROMPT in src/oss/src/prompts/index.ts is explicitly commented "Ported from mem0/configs/prompts.py"; an AGENT_CONTEXT_SUFFIX is appended when the call is agent-scoped (agent_id set, no user_id).
  • Anti-hallucination: existing memory UUIDs are replaced with integer indices in a uuidMapping before being shown to the LLM, exactly as Python does.
  • Single LLM call: the model is asked for { type: "json_object" }; the response is robustly parsed with extractJson() and validated against AdditiveExtractionSchema (Zod), with a fallback re-extract on parse failure.
  • Dedup: md5 hash of each extracted text is checked against existing payload hashes and a within-batch seenHashes set; textLemmatized (for BM25) is precomputed on insert.
  • Every phase degrades gracefully: batch embed/insert/history each fall back to per-item loops on failure; entity linking is wrapped so a failure only warns.
Insight: history store doubles as conversation memory Phase 0 calls db.getLastMessages(sessionScope, 10) and Phase 8 calls db.saveMessages(...) — capabilities probed with typeof this.db.X === "function", so a history backend lacking them just skips that context without error.

search() — multi-signal retrieval

The TS search() reproduces the Python multi-signal fusion (it is not a plain vector search) — see retrieval:

  1. Preprocess — lemmatize query (lemmatizeForBm25), extract query entities (extractEntities).
  2. Semantic — embed query, over-fetch max(topK*4, 60) from the vector store.
  3. Keyword — if the store implements the optional keywordSearch(), run BM25; raw scores are sigmoid-normalized to [0,1] via normalizeBm25() with query-length-adaptive params from getBm25Params().
  4. Entity boost — for each (deduped, max 8) query entity, search the entity store; matched entities propagate a spread-attenuated boost (ENTITY_BOOST_WEIGHT = 0.5, attenuated by how many memories the entity links) to every linkedMemoryIds.
  5. Fuse & rank — scoreAndRank() (src/oss/src/utils/scoring.ts) combines semantic + BM25 + entity boost, applies the threshold against the dynamic max-possible score, and truncates to topK.
Filter normalization avoids "undefined" footguns search()/getAll() trim entity IDs and drop keys whose value resolves to undefined, because otherwise Qdrant rejects the malformed match, pgvector binds NULL, and Redis emits a literal "undefined" string in TAG filters. The engine also supports advanced operators (eq/ne/gt/gte/lt/lte/in/nin/contains/icontains and AND/OR/NOT) via _processMetadataFilters(), translating OR→$or and NOT→$not.

Entity store (the graph replacement)

There is no graph database, no Neo4j/Memgraph, no graph provider in the OSS TS engine. The directory src/oss/src/ has no graphs/ subdir; the only occurrences of the word "graph" are a conceptual mention in a prompt example and one LLM test. Relationship awareness instead comes from a lightweight entity store, matching the Python OSS direction documented on the graph-memory page.

Lazy second collection
getEntityStore() creates a <collectionName>_entities collection on first use, reusing the same vector-store provider/config. For the file-based memory provider it forces a separate *_entities.db file.
Entity records
Each record stores { data, entityType, linkedMemoryIds: string[], user_id?/agent_id?/run_id? }. On add, entities are extracted in batch, globally deduped by lowercased text, batch-embedded, and either merged into an existing entity (cosine ≥ 0.95) or inserted new.
Lifecycle cleanup
update() strips the old memory's id from entities then re-links from the new text; delete() removes the id from all linked entities, deleting the entity record entirely once its linkedMemoryIds empties.
Insight: NLP extraction with graceful fallback Entity extraction (src/oss/src/utils/entity_extraction.ts) uses the compromise NLP package (a peer dependency) for noun-phrase extraction, but dynamically requires it and falls back to a pure-regex extractor if it isn't installed — so the engine still runs without the optional NLP deps.

Exported providers

The OSS index re-exports every provider class. Counts below are the actual implementation files (base interfaces excluded), and every provider is dispatched by name in src/oss/src/utils/factory.ts through one of the four factories (EmbedderFactory, LLMFactory, VectorStoreFactory, HistoryManagerFactory) — the same config-driven factory pattern as Python.

LLM providers — 11

openai, openai_structured, anthropic, groq, mistral, ollama, lmstudio, google (alias gemini), azure_openai, deepseek, langchain. All implement the LLM interface (src/oss/src/llms/base.ts): generateResponse(messages, response_format?, tools?) and generateChat(messages). See LLM providers.

Embedding providers — 6

openai, ollama, lmstudio, google/gemini, azure_openai, langchain. The Embedder interface (src/oss/src/embeddings/base.ts) is just embed(text) and embedBatch(texts) — the batch method is what makes the add/search pipelines efficient. See embeddings.

Vector stores — 8

memory (in-process, the default), qdrant, redis, supabase, pgvector, azure-ai-search, vectorize (Cloudflare), langchain. All implement the VectorStore interface (src/oss/src/vector_stores/base.ts) — insert/search/get/update/delete/deleteCol/list/initialize plus an optional keywordSearch() (the BM25 hook) and getUserId/setUserId (telemetry). See vector stores.

History stores — 3

sqlite (default, via better-sqlite3; :memory: when no path), supabase, memory (in-process). Plus a DummyHistoryManager used when disableHistory: true.

Build & test

tsup — dual CJS + ESM

The build is driven by tsup.config.ts (the inline tsup block in package.json is superseded by the config file). Two entries are built:

defineConfig([
  { entry: ["src/client/index.ts"], format: ["cjs", "esm"], dts: true, ... },
  { entry: ["src/oss/src/index.ts"], outDir: "dist/oss",
    format: ["cjs", "esm"], dts: true, ... },
]);
  • Each entry emits .js (CJS), .mjs (ESM), .d.ts types, and sourcemaps — matching the require/import/types conditions in the exports map.
  • The SDK version is injected at build time via a define replacing __MEM0_SDK_VERSION__ with the package.json version.
  • All heavy/optional deps (OpenAI, Anthropic, Groq, pg, redis, qdrant, supabase, azure, cloudflare, langchain, better-sqlite3, compromise, natural, …) are marked external so they stay peerDependencies and are never bundled. A dedicated test (tsup-externals.test.ts) guards this.
  • build = clean → prettier --check . → tsup: a formatting violation fails the build.
Optional peers, lazy loading Every provider's heavy client is a peer dependency, and providers import them lazily — so installing mem0ai and using only the in-memory store + OpenAI doesn't pull Qdrant/Redis/pg/etc. better-sqlite3 is in pnpm.onlyBuiltDependencies because it has a native build step.

Jest

Tests run under ts-jest (Node env) per jest.config.js, rooted at src/ and tests/, ignoring node_modules/dist.

Unit tests
~38 spec files. OSS engine coverage in src/oss/tests/ (27 files: per-provider LLM/embedder tests, vector-store compat, pgvector filters, factory, config manager, dimension autodetect, telemetry sampling, tsup externals, JSON extraction) and src/oss/src/tests/ (3 SQLite migration/compat/path tests). Hosted client coverage in src/client/tests/ (8 files: init, crud, search, batch, project, users, webhooks, telemetry aliasing).
Integration tests
jest.integration.config.js targets **/integration/**/*.test.ts (5 files under src/client/tests/integration/), runs maxWorkers: 1 (serial, to dodge platform rate limits/races), with a global setup/teardown. Invoked via npm run test:integration (with --forceExit).

Scripts of note: test (all), test:unit (coverage, excludes integration), test:ci (coverage + CI), test:integration, test:watch.

Telemetry, config files & community

  • Telemetry: both surfaces emit anonymous events (captureClientEvent). The OSS engine resolves a stable anonymous id via getOrCreateMem0UserId() (in src/client/config.ts, shared with the client) persisted in the vector store; the hosted client hashes the API key and, when a real email is known, performs an anon→email alias (_maybeAliasAnonToEmail). Telemetry honors an enable/disable flag and is best-effort (failures only log).
  • Defaults: DEFAULT_MEMORY_CONFIG (src/oss/src/config/defaults.ts) = OpenAI text-embedding-3-small embeddings, in-memory vector store (dim 1536), OpenAI gpt-5-mini LLM, SQLite history at memory.db, version v1.1.
  • Community (@mem0/community): a separate package re-exporting only the LangChain integration (src/community/src/integrations/langchain/). It depends on mem0ai and is excluded from the main bundle. See integrations.
Deprecations to watch (1) MemoryClient.deleteUser() is marked @deprecated (removal in 2.2.0) — use deleteUsers(). (2) The OSS README.md claims "Optional graph-based memory relationships" — stale; the engine uses the entity store, no graph DB. (3) FactRetrievalSchema / getUpdateMemoryMessages / getFactRetrievalMessages remain exported from prompts/index.ts but the live pipeline uses the additive path; the legacy fact-retrieval prompts are vestigial.

Usage at a glance

// Hosted platform
import { MemoryClient } from "mem0ai";
const client = new MemoryClient({ apiKey: process.env.MEM0_API_KEY! });
await client.add([{ role: "user", content: "I love sci-fi" }],
                 { userId: "alex" });
const hits = await client.search("genres?",
                 { filters: { user_id: "alex" }, latestOnly: true });

// OSS engine (fully local)
import { Memory } from "mem0ai/oss";
const memory = new Memory();             // OpenAI defaults
await memory.add("I prefer window seats", { userId: "alex" });
const res = await memory.search("seating preference",
                 { filters: { user_id: "alex" } });
// res.results: Array<{ id, memory, score, metadata, ... }>

For the wider picture — the two usage modes, the add/search data flow, and the config + factory pattern these mirror — see the linked pages. Cross-cutting quirks (stale README, missing async/proxy/graph) are also collected on surprises.

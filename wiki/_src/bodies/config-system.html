Configuration System

mem0 is configuration-driven: a single Pydantic v2 MemoryConfig object selects which LLM, embedder, vector store, and (optional) reranker back the memory engine, while four string-keyed factories turn {provider, config} pairs into live provider instances via lazy importlib dispatch. Every subsystem can be supplied either as a nested Python dict or as typed config objects; both paths converge on the same validated model. The default stack is OpenAI for both the LLM and embedder plus a local Qdrant vector store, so a bare Memory() works with nothing but an OPENAI_API_KEY.

Overview & role in the architecture

The configuration layer is the wiring harness described in the architecture overview: it is the seam where the provider plugin pattern is realised. Nothing in mem0/memory/main.py hard-codes a provider class; instead the Memory engine reads self.config and asks the factories to build the pieces.

  • Schema lives in mem0/configs/ — the top-level MemoryConfig (in mem0/configs/base.py) plus the four sub-config wrappers and the per-provider config classes under mem0/configs/llms/, mem0/configs/embeddings/, mem0/configs/vector_stores/, and mem0/configs/rerankers/.
  • Wrappers (LlmConfig, EmbedderConfig, VectorStoreConfig, RerankerConfig) each hold a provider string and a free-form config dict, and validate that the provider is recognised.
  • Factories live in mem0/utils/factory.py: LlmFactory, EmbedderFactory, VectorStoreFactory, RerankerFactory. Each maps a provider string to an implementation class path and instantiates it.
Decision The two-level split — a thin {provider, config} Pydantic wrapper at the schema layer plus a separate string→class map at the factory layer — means the schema never imports heavy provider SDKs. The wrapper only validates that the provider name is allowed; the actual class (and its dependency, e.g. qdrant_client) is imported lazily by load_class() only when the factory runs.

MemoryConfig: the root model

One-sentence summary: MemoryConfig is a Pydantic v2 BaseModel aggregating four provider sub-configs plus a handful of scalar settings, all with safe defaults.

Fields

vector_store: VectorStoreConfig
default_factory=VectorStoreConfig → defaults to provider "qdrant".
llm: LlmConfig
default_factory=LlmConfig → defaults to provider "openai".
embedder: EmbedderConfig
default_factory=EmbedderConfig → defaults to provider "openai".
reranker: Optional[RerankerConfig]
Defaults to None. When unset, the engine sets self.reranker = None and skips the rerank step entirely. See the rerankers page.
history_db_path: str
Path to the SQLite audit/history DB. Defaults to os.path.join(mem0_dir, "history.db") where mem0_dir is $MEM0_DIR or ~/.mem0. Consumed by the engine's SQLiteManager (see memory engine).
version: str
API version string, default "v1.1". Stored as self.api_version and steers result shaping in add/search flows.
custom_instructions: Optional[str]
User-supplied fact-extraction guidance, default None. Stored as self.custom_instructions and threaded into the extraction prompt by the algorithm.
Gotcha Despite older docs/wikis referring to custom_fact_extraction_prompt / custom_update_memory_prompt on MemoryConfig, the model in mem0/configs/base.py exposes a single custom_instructions field. The update-memory prompt has its own parameter (custom_update_memory_prompt) but only inside get_update_memory_messages() in mem0/configs/prompts.py — it is not a MemoryConfig field. At add() time a per-call prompt= argument can override custom_instructions (custom_instr = prompt or self.custom_instructions in mem0/memory/main.py).
Gotcha There is no graph_store field on MemoryConfig. Graph memory has been removed from the OSS core — see graph memory (deprecated); entity linking via a per-collection entity store ({collection}_entities) replaces it, built lazily through VectorStoreFactory.

AzureConfig

mem0/configs/base.py also defines AzureConfig (a Pydantic model with api_key, azure_deployment, azure_endpoint, api_version, default_headers). It is reused by Azure LLM/embedder provider configs and nested under azure_kwargs in BaseEmbedderConfig.

Deep dive: MemoryItem is also in base.py

mem0/configs/base.py additionally defines MemoryItem — the Pydantic shape of a single returned memory (id, memory, hash, metadata, score, created_at, updated_at). It is a result/DTO type, not part of the configuration tree, but it lives in the same module.

The four sub-config wrappers

One-sentence summary: each subsystem is configured by a thin {provider: str, config: dict} wrapper that validates the provider name and (for vector stores) eagerly materialises a typed provider-config object.

WrapperFileprovider defaultconfig defaultValidation style
LlmConfigmem0/llms/configs.py"openai"{}@field_validator("config") — checks provider is in an allow-list, returns config dict unchanged
EmbedderConfigmem0/embeddings/configs.py"openai"{}@field_validator("config") — provider allow-list check, returns dict unchanged
VectorStoreConfigmem0/vector_stores/configs.py"qdrant"None@model_validator(mode="after") — imports & instantiates the provider config class
RerankerConfigmem0/configs/rerankers/config.py"cohere"Nonenone on the wrapper; model_config = {"extra": "forbid"}
Insight The wrappers are asymmetric. LlmConfig and EmbedderConfig leave config as a raw dict and defer all typing to factory time. VectorStoreConfig is the odd one out: its @model_validator(mode="after") immediately turns the dict into a typed provider config object (e.g. QdrantConfig) at construction time. That is why the engine can read self.config.vector_store.config.collection_name as an attribute, while LLM/embedder configs remain dicts until their factory runs.

LlmConfig & EmbedderConfig validation

Both use a Pydantic v2 @field_validator("config") that reads the sibling provider via values.data.get("provider") and raises ValueError(f"Unsupported ... provider: {provider}") if it is not in a hard-coded allow-list. The LLM allow-list contains 18 names (the same set as LlmFactory.provider_to_class keys); the embedder list contains 11. The validator does not inspect the contents of config — provider-specific keys are validated later, when the factory builds the config object.

VectorStoreConfig: eager class resolution

VectorStoreConfig carries a private _provider_configs dict mapping provider name → config class name (e.g. "qdrant" → "QdrantConfig", "pgvector" → "PGVectorConfig"). Its post-validator:

  1. Rejects unknown providers (ValueError: Unsupported vector store provider).
  2. __import__("mem0.configs.vector_stores.{provider}", fromlist=[ClassName]) and getattrs the class.
  3. If config is None, treats it as {}.
  4. If a dict and the class declares a path annotation but none was supplied, injects a default path = f"/tmp/{provider}".
  5. Replaces self.config with config_class(**config) — a typed, validated object.
Gotcha If you pass an already-constructed provider-config object (not a dict), the validator only checks isinstance(config, config_class) and returns; it skips the /tmp/{provider} path injection. So object-style and dict-style configs are not perfectly interchangeable for file-backed stores — a dict gets a free /tmp/qdrant path, a bare object does not. For Qdrant specifically the QdrantConfig default is path="/tmp/qdrant" anyway, and its own validator requires one of: path, (host, port), or (url, api_key).

Provider-specific config classes

One-sentence summary: each provider that needs more than the common parameters ships a dedicated config class; the rest fall back to a shared base config.

LLM configs — mem0/configs/llms/

BaseLlmConfig (in base.py) is a plain ABC (not Pydantic) holding the parameters common to every LLM: model, temperature (0.1), api_key, max_tokens (2000), top_p (0.1), top_k (1), enable_vision, vision_details ("auto"), reasoning_effort, and http_client_proxies (which becomes an httpx.Client). Nine providers subclass it for extra fields: anthropic, aws_bedrock, azure, deepseek, lmstudio, minimax, ollama, openai, vllm. For example OpenAIConfig adds openai_base_url, OpenRouter fields (models, route, openrouter_base_url, site_url, app_name), store, and a response_callback. Providers without a dedicated class (groq, together, litellm, gemini, xai, sarvam, langchain) use BaseLlmConfig directly. Full detail on the LLM layer is in LLM providers.

Embedder config — mem0/configs/embeddings/

This directory contains only base.py (plus __init__.py): every embedder shares one BaseEmbedderConfig (an ABC). It is a "kitchen-sink" config — a single class with provider-tagged fields for all backends: ollama_base_url, openai_base_url, model_kwargs/huggingface_base_url, azure_kwargs (an AzureConfig), vertex_credentials_json, output_dimensionality (Gemini), lmstudio_base_url, and AWS Bedrock keys. It also exposes memory_add_embedding_type / memory_update_embedding_type / memory_search_embedding_type so different actions can request different embedding modes. See embedding providers.

Gotcha BaseEmbedderConfig.__init__ sets self.azure_kwargs = AzureConfig(**azure_kwargs) or {}, with azure_kwargs defaulting to a mutable {}. So every embedder always gets an AzureConfig instance constructed (with all-None fields) even when Azure is not in use.

Vector store configs — mem0/configs/vector_stores/

24 provider config files, one per backend (e.g. qdrant.py → QdrantConfig, pgvector.py → PGVectorConfig, pinecone.py → PineconeConfig, …). Unlike LLM/embedder configs these are full Pydantic BaseModels, frequently with their own validators. QdrantConfig, for instance, declares collection_name (default "mem0"), embedding_model_dims (1536), connection fields, and a strict validate_extra_fields validator that raises if you pass any key outside model_fields. The common runtime interface these back is documented under vector stores.

Reranker configs — mem0/configs/rerankers/

BaseRerankerConfig (Pydantic BaseModel) holds provider, model, api_key, top_k. Five provider subclasses add specifics: cohere.py (CohereRerankerConfig, default model rerank-english-v3.0, return_documents, max_chunks_per_doc), sentence_transformer.py, zero_entropy.py, llm.py, huggingface.py. Note these are distinct from the wrapper RerankerConfig in config.py. See rerankers.

The four factories

One-sentence summary: each factory in mem0/utils/factory.py owns a provider_to_class map and a create() classmethod that resolves the implementation via load_class() and feeds it a config.

load_class(class_type) is the shared mechanism: it splits a dotted path on the last ., importlib.import_modules the module, and getattrs the class. This is what keeps provider SDK imports lazy.

  A["MemoryConfig\n(validated)"] --> B["Memory.__init__"]
  B --> C["EmbedderFactory.create\n(provider, config, vector_config)"]
  B --> D["VectorStoreFactory.create\n(provider, config)"]
  B --> E["LlmFactory.create\n(provider, config)"]
  B --> F["RerankerFactory.create\n(provider, config)\nonly if reranker set"]
  C --> G["load_class -> Embedder"]
  D --> H["load_class -> VectorStore"]
  E --> I["load_class -> LLM"]
  F --> J["load_class -> Reranker"]

LlmFactory.create — the richest dispatch

LlmFactory.provider_to_class maps each provider to a tuple of (impl_path, config_class), e.g. "openai" → ("mem0.llms.openai.OpenAILLM", OpenAIConfig), "groq" → (..., BaseLlmConfig). create(provider_name, config=None, **kwargs):

  • Raises ValueError("Unsupported Llm provider: ...") for unknown providers.
  • config is None → config_class(**kwargs) (build from kwargs/defaults).
  • config is a dict → config.update(kwargs); config = config_class(**config).
  • config is a BaseLlmConfig and the target config_class differs → it copies a fixed set of common attributes (model, temperature, api_key, max_tokens, top_p, top_k, enable_vision, vision_details, and notably http_client_proxies=config.http_client) into a dict and rebuilds it as the provider class. If the class is already BaseLlmConfig, the object is used as-is.
  • Finally return llm_class(config).
Gotcha When re-projecting a BaseLlmConfig into a provider class, only the fixed common-parameter list is carried over. reasoning_effort is not in that copy list even though BaseLlmConfig defines it — so passing a base config object (rather than a dict) can silently drop reasoning_effort. The dict path does not have this problem because it spreads the whole dict.

LlmFactory also exposes register_provider(name, class_path, config_class=None) (defaulting to BaseLlmConfig) and get_supported_providers() — an extension point for third-party LLMs without touching the source map.

EmbedderFactory.create — vector-store-aware

create(provider_name, config, vector_config) takes a third argument: the vector store's config. There is one special case at the top:

if provider_name == "upstash_vector" and vector_config and vector_config.enable_embeddings:
    return MockEmbeddings()

i.e. when Upstash Vector is doing the embedding itself, mem0 substitutes a no-op MockEmbeddings rather than calling a real embedder. Otherwise it does BaseEmbedderConfig(**config) and instance(base_config). Unknown providers raise ValueError("Unsupported Embedder provider: ..."). The engine calls it as EmbedderFactory.create(self.config.embedder.provider, self.config.embedder.config, self.config.vector_store.config).

VectorStoreFactory.create — kwargs, not config object

The vector store factory is the only one that passes **config as keyword arguments to the implementation constructor rather than handing it a config object. If config is not already a dict (it normally is a typed object after VectorStoreConfig's post-validator), it calls config.model_dump() first. It also has a reset(instance) classmethod that calls instance.reset() — used when the engine recreates a collection.

RerankerFactory.create — strict typing

Like LlmFactory it uses (class_path, config_class) tuples. A dict config becomes config_class(**config, **kwargs); a config that is neither dict nor BaseRerankerConfig raises ValueError. Class import failures are re-raised as ImportError with the provider name. Crucially the implementation paths point at mem0.reranker.* (singular), e.g. "cohere" → "mem0.reranker.cohere_reranker.CohereReranker".

Dict vs. object configuration

One-sentence summary: you can build a MemoryConfig from a nested dict via Memory.from_config(dict) or assemble typed objects directly — both produce the same validated tree.

Dict form (most common)

from mem0 import Memory

config = {
    "llm": {
        "provider": "openai",
        "config": {"model": "gpt-4o-mini", "temperature": 0.1, "max_tokens": 2000},
    },
    "embedder": {
        "provider": "openai",
        "config": {"model": "text-embedding-3-small"},
    },
    "vector_store": {
        "provider": "qdrant",
        "config": {"collection_name": "mem0", "host": "localhost", "port": 6333},
    },
    "reranker": {                       # optional; omit to skip reranking
        "provider": "cohere",
        "config": {"model": "rerank-english-v3.0", "top_k": 5},
    },
    "history_db_path": "/data/mem0/history.db",
    "version": "v1.1",
    "custom_instructions": "Only remember durable user preferences.",
}

m = Memory.from_config(config)

Memory.from_config(config_dict) (in mem0/memory/main.py) calls a pass-through _process_config then MemoryConfig(**config_dict), catching ValidationError and re-raising after logging. The same exists for AsyncMemory. The dict keys are the wrapper fields; Pydantic recursively builds LlmConfig, EmbedderConfig, etc.

Equivalent object form

from mem0 import Memory
from mem0.configs.base import MemoryConfig
from mem0.llms.configs import LlmConfig
from mem0.embeddings.configs import EmbedderConfig
from mem0.vector_stores.configs import VectorStoreConfig

config = MemoryConfig(
    llm=LlmConfig(provider="openai",
                  config={"model": "gpt-4o-mini", "temperature": 0.1}),
    embedder=EmbedderConfig(provider="openai",
                            config={"model": "text-embedding-3-small"}),
    vector_store=VectorStoreConfig(provider="qdrant",
                                   config={"collection_name": "mem0",
                                           "host": "localhost", "port": 6333}),
    custom_instructions="Only remember durable user preferences.",
)

m = Memory(config)
Insight Note that even in "object form" the innermost config= stays a plain dict for LLM and embedder — those wrappers keep it as a dict. Only the vector store's inner config is upgraded to a typed object by its post-validator. So "fully typed config objects" is partly a fiction: the deepest LLM/embedder parameters are always dicts until factory time.

Defaults: the zero-config path

from mem0 import Memory
m = Memory()   # == Memory(MemoryConfig())

With no arguments the engine signature is def __init__(self, config: MemoryConfig = MemoryConfig()). Defaults resolve to: OpenAI LLM, OpenAI embedder, local Qdrant (path="/tmp/qdrant", collection "mem0", 1536-dim), no reranker, history at ~/.mem0/history.db, version v1.1. Only OPENAI_API_KEY is required.

Gotcha MemoryConfig() is evaluated once as a default-argument value at function-definition time, but because each field uses default_factory/immutable defaults and the engine treats self.config as read-mostly, the usual mutable-default pitfall is largely avoided. Still, prefer passing an explicit config object when running multiple Memory instances with divergent settings.

Pydantic v2 validation semantics

One-sentence summary: validation is layered — provider-name allow-lists at the wrapper level, full field validation at the factory/provider-config level.

  • Wrapper level: LlmConfig/EmbedderConfig use @field_validator("config") reading values.data.get("provider") (the Pydantic v2 way to access sibling fields). VectorStoreConfig uses @model_validator(mode="after") to import and build the typed config. RerankerConfig sets model_config = {"extra": "forbid"} so unknown top-level keys are rejected.
  • Provider-config level: vector-store config classes like QdrantConfig add their own @model_validator(mode="before") rules (connection-coordinate completeness, no-extra-fields). LLM/embedder base configs are plain ABCs — they do not validate via Pydantic; bad keys surface as TypeError from __init__ at factory time.
  • Error surface: Memory.from_config catches pydantic.ValidationError, logs, and re-raises, so configuration mistakes fail fast at construction.
Performance Because provider SDK imports are deferred to load_class(), importing mem0 and constructing a MemoryConfig is cheap regardless of how many backends are installed; you only pay the import cost for the providers you actually instantiate.
Security API keys flow through plain config dicts/objects. Provider configs accept api_key directly but every provider also falls back to environment variables when it is None (e.g. OPENAI_API_KEY, AWS_REGION for Bedrock embeddings). Prefer env vars over embedding keys in config dicts that may be logged or serialised — and note the engine builds a telemetry vector store whose config is deep-copied from yours.

Enums

One-sentence summary: mem0/configs/enums.py defines a single small enum used for memory typing, not for provider selection.

class MemoryType(Enum):
    SEMANTIC   = "semantic_memory"
    EPISODIC   = "episodic_memory"
    PROCEDURAL = "procedural_memory"

Provider selection is done with plain strings (validated against the factory maps), not enums. MemoryType classifies stored memories and is consumed by the memory algorithm rather than the configuration layer; it is documented here only because it lives under mem0/configs/.

How the engine consumes the config

One-sentence summary: Memory.__init__ (and AsyncMemory.__init__) read self.config and call the factories in a fixed order, then derive a few cached attributes.

  • self.embedding_model = EmbedderFactory.create(embedder.provider, embedder.config, vector_store.config)
  • self.vector_store = VectorStoreFactory.create(vector_store.provider, vector_store.config)
  • self.llm = LlmFactory.create(llm.provider, llm.config)
  • self.db = SQLiteManager(config.history_db_path)
  • self.collection_name = config.vector_store.config.collection_name — relies on the vector-store config being a typed object with that attribute
  • self.api_version = config.version; self.custom_instructions = config.custom_instructions
  • self.reranker only if config.reranker is set, else None
  • A telemetry-only vector store (collection "mem0migrations") is built from a deep-copied config when MEM0_TELEMETRY is on; for faiss/qdrant it is pointed at a migrations_{provider} dir under ~/.mem0
  • An entity_store (collection {collection}_entities) is built lazily on first use, sharing the Qdrant client where possible to avoid RocksDB lock contention

Full setup/lifecycle detail is on the memory engine page; the end-to-end request paths are on data flow. Cross-cutting config gotchas are aggregated on surprises & gotchas.

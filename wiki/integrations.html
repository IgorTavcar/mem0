Integrations & Ecosystem

mem0 ships a fleet of first-party clients and editor plugins that all route through the same memory layer. Two command-line tools (mem0-cli Python and @mem0/cli Node) provide terminal access and an unattended Agent Mode signup that mints an API key in under five seconds; the mem0-plugin wires Claude Code / Cursor / Codex / OpenCode / Antigravity to the hosted MCP server with lifecycle hooks for automatic capture; @mem0/openclaw-mem0 adds skills-based recall, filtering, isolation and dream consolidation to OpenClaw agents; @mem0/vercel-ai-provider wraps the Vercel AI SDK; and a set of reference and pipeline skills teach assistants how to write correct mem0 code. This page surveys each surface, its package, and exactly how it connects to mem0.

The ecosystem at a glance

Every integration is a thin client over either the hosted MemoryClient / Platform API (api.mem0.ai), the remote MCP endpoint (mcp.mem0.ai), or the OSS Memory engine. They share the same scoping vocabulary (user_id / agent_id / app_id / run_id) defined in the config system.

Insight — one bootstrap, every surface The recurring marketing line "mints an evaluation API key in <5 seconds — no email, no OTP, no browser" appears verbatim in the mem0-plugin and openclaw READMEs, but the machinery lives in one place: mem0 init --agent. The plugins simply tell the agent to shell out to the CLI. See Agent Mode.

Python CLI — mem0-cli

A Typer app (cli/python/src/mem0_cli/app.py, entrypoint mem0_cli.app:main) that talks to the hosted Platform over HTTPS. Install via pipx install mem0-cli (recommended) or pip install mem0-cli; requires Python 3.10+.

Command surface

Memory panel
add, search, get, list, update, delete — all accept the four scope flags (-u/--user-id, --agent-id, --app-id, --run-id) and read text from an argument, --file, --messages JSON, or piped stdin.
Management
init, status, import, help, plus config (show/get/set), entity (list/delete), and event (list/status) sub-apps.
Setup / game
identify, whoami, and the agent-rush sub-app (add/search).

Implementation highlights

  • Lazy command imports. Every app.command body imports its handler from mem0_cli.commands.* at call time, keeping --help and tab completion fast.
  • Upfront key validation. _get_backend_and_config() calls backend.ping(timeout=5.0) against /v1/ping/; a 401/403 (AuthError) aborts, while network blips print a warning and proceed. The resolved user_email is cached for telemetry and written back to config.
  • Scope resolution. _resolve_ids() uses CLI flag > config default; crucially, any explicit ID switches off all config defaults so you don't accidentally over-filter (see the docstring in app.py).
  • Agent mode output. The global --agent / --json flag (parsed in main() before Typer, so it works positionally) sets agent mode, suppresses spinners/colours, and wraps results in a JSON envelope; errors become {"status":"error", ...} with a non-zero exit. mem0 help --json emits the full command tree from _build_help_json() for self-discovering agents.
Gotcha — --agent means two different things As a global flag it toggles JSON-envelope output. But mem0 init --agent is a subcommand flag that bootstraps an Agent Mode account. main() special-cases this: when init is in argv it leaves --agent in place (for init_cmd) and only strips --json as the output toggle.
Gotcha — the [oss] extra is declared but unwired cli/python/pyproject.toml declares oss = ["mem0ai>=0.1.0"], and the README/help advertise --graph flags and an OSS path. But the current backend factory get_backend() in backend/base.py unconditionally returns PlatformBackend — there is no OssBackend in cli/python/src/mem0_cli/backend/ (only base.py and platform.py). The --graph/--no-graph flags appear only in the static _build_help_json() dict, not on the live add/search commands. Treat OSS-mode-in-CLI and graph as reserved/not-yet-implemented in this revision.

Agent Mode & the <5-second key

mem0 init --agent --agent-caller <name> bootstraps an unattended evaluation account with no email, OTP or browser — the headline UX for autonomous agents. The logic lives in commands/init_cmd.py (dispatch) and commands/agent_mode_cmd.py (HTTP).

Dispatch rules (run before the overwrite guard)

  1. Reuse env key. If MEM0_API_KEY is set and pings OK (_ping_key, which only treats 401/403 as invalid), reuse it — no new key minted.
  2. Reuse config key. Else if ~/.mem0/config.json holds a valid key, reuse it.
  3. Mint a shadow. Else bootstrap_via_backend() POSTs to /api/v1/auth/agent_mode/ and persists api_key, default_user_id (a user_<slug> the backend returns), agent_mode=true, created_via="agent_mode".

An agent context is detected by --agent, the global JSON flag, or an env var sniffed by agent_detect.detect_agent_caller() (recognises CLAUDECODE, CURSOR_AGENT, CODEX_CLI, CLINE, CONTINUE, AIDER_SESSION, GOOSE_AGENT, WINDSURF_AGENT, …).

Decision — env vars trigger, but never name the agent agent_detect.py is explicit: env-var detection is a context trigger only. The canonical agent identity is self-declared via --agent-caller (Proof-Editor style) or backfilled later with mem0 identify <name>. The detector list is "curated, not exhaustive" — honest reporting depends on the flag, not sniffing.

Claiming & identity

mem0 init --email <addr> (on an agent-mode config)
Runs claim_via_otp(): reuses the email-code flow but adds agent_mode_api_key to the verify body so the backend upgrades the key in place. The API key value never changes; memories transfer; agent_mode flips to false and claimed_at is stamped.
mem0 whoami
Prints platform.default_user_id — the AGENTRUSH identifier (whoami_cmd.run_whoami).
mem0 identify <name>
Idempotent PATCH to /api/v1/auth/agent_mode/caller/ tagging the active key with the agent name.
mem0 agent-rush add|search
A public memory game wrapping /v1/agent-rush/memories/. agent_rush_cmd.py enforces a one-time PII warning, surfaces typed error codes (e.g. agentrush_search_first, lifetime quotas), and marks requests with header X-Mem0-Mode: agent-rush.
Security — AGENTRUSH memories are PUBLIC _PII_WARNING_LINES blocks the first interactive add until the user types y (persisted as agent_rush.acknowledged_at). For non-TTY agent runs the warning is printed to stderr and the add proceeds — agents can't answer a y/N prompt.

Plugin sync

plugin_sync.sync_api_key() propagates a freshly minted key into existing touchpoints only: the env.MEM0_API_KEY entry in ~/.claude/settings.json and any export MEM0_API_KEY= line in ~/.zshrc/~/.bashrc/~/.bash_profile. Writes are atomic (tmp + rename) and never create new entries — it solves the "config.json updated but the MCP server still reads the stale env key" surprise without clobbering unrelated config.

Node CLI — @mem0/cli

A Commander-based port (cli/node/src/index.ts, bin mem0, Node ≥18). It is a near line-for-line mirror of the Python CLI and shares the same version number (0.2.7 at time of writing).

  • Full command parity: cli/node/src/commands/ contains init, memory, config, entities, events, identify, whoami, agent-rush, agent-mode, and utils — i.e. Agent Mode bootstrap (bootstrapViaBackend), OTP claim (claimViaOtp), and env-based agent detection (detectAgentCaller) all exist on the Node side too.
  • Same backend abstraction: backend/index.ts → getBackend() returns PlatformBackend; the 5-second ping validation is implemented with Promise.race against a timeout.
  • Dependencies: commander, chalk, cli-table3, ora (spinners), boxen; built with tsup, linted with Biome.

Both CLIs publish identical READMEs and the mem0-cli skill covers them jointly. See the TypeScript SDK for the underlying client.

mem0-plugin — MCP server + lifecycle hooks

The mem0-plugin/ directory is a multi-editor plugin (Claude Code, Claude Cowork, Cursor, Codex, OpenCode, Antigravity). Its core is the remote MCP server at https://mcp.mem0.ai/mcp/ — no local Python/Node runtime is required for memory operations. Manifests: plugin.json, .claude-plugin/plugin.json (v0.2.8), .codex-plugin/, .cursor-plugin/, .opencode-plugin/.

MCP wiring

Every editor variant points at the same endpoint with a bearer/token header interpolated from the environment at session start (not install time), so a restart re-reads the key automatically:

// mem0-plugin/.mcp.json (Claude Code)
{ "mcpServers": { "mem0": {
    "type": "http",
    "url": "https://mcp.mem0.ai/mcp/",
    "headers": { "Authorization": "Token ${MEM0_API_KEY}" } } } }

Codex uses TOML with bearer_token_env_var = "MEM0_API_KEY" (.codex-mcp.json → config.toml); Cursor uses .cursor-mcp.json / a deeplink; mcp_config.json uses the serverUrl shape for Antigravity.

Lifecycle hooks (automatic capture)

hooks.json registers shell scripts on five editor events. The variants hooks/cursor-hooks.json and hooks/codex-hooks.json mirror it; Codex hooks are opt-in via scripts/install_codex_hooks.py (Codex doesn't auto-wire plugin hooks).

SessionStart*ensure_deps.sh, on_session_start.shInstall SDK deps; emit the "Mem0 Active" status banner with live memory count; kick off background auto_import.py and auto_setup_categories.py
UserPromptSubmit—on_user_prompt.sh → auto_capture.pyInject relevant memories; every 3rd message capture recent exchanges (8 s timeout)
PreToolUseWrite|Edit|MultiEditblock_memory_write.shBlock the agent from writing to native memory files (use mem0 instead)
PreToolUsemcp__mem0__.*enforce_metadata_defaults.shInject default user_id/app_id metadata into MCP calls

Perf — hooks never block Every hook command ends with 2>/dev/null || true and the scripts exit 0 unconditionally with tight timeouts (3–8 s). auto_capture.py reads only the transcript tail (200 lines, capped at 8000 chars) and posts with infer=True so the platform extracts facts asynchronously — a slow or failing capture can never stall the editor.

Coding-tuned categories

scripts/setup_coding_categories.py replaces the default consumer taxonomy with 17 development categories (architecture_decisions, bug_fixes, coding_conventions, security_constraints, …) via project.update(custom_categories=[...]). It runs idempotently in the background on session start, cached in ~/.mem0/categories_setup.json, and requires the mem0ai Python SDK plus MEM0_API_KEY.

Plugin skills (slash commands)

16 skill directories under mem0-plugin/skills/ surface as /mem0: commands: remember, tour, peek, stats, dream, pin, forget, health, export, import, list-projects, switch-project, memory-reviewer, context-loader, onboard, and the SDK-reference mem0 skill. /mem0:onboard is the idempotent setup wizard run after install. (The README's "17 skills" count includes the auto-prompted memory-reviewer/context-loader pair counted twice across tables — the directory count is 16.)

Gotcha — restart to reconnect after an update The MCP config interpolates ${MEM0_API_KEY} at session start, so updating the plugin leaves the running session holding a stale server handle. The README instructs a client restart (/restart in Claude Code) — the key is re-read, not re-entered.

OpenClaw — @mem0/openclaw-mem0

A native OpenClaw memory-slot plugin (openclaw/, npm @mem0/openclaw-mem0 v1.0.11) built directly on the mem0ai@3.0.3 package. Unlike the MCP plugin it embeds the SDK, so it supports both platform mode (cloud) and a fully self-hosted open-source mode (local SQLite vector store at ~/.mem0/vector_store.db, OpenAI/Ollama/Anthropic LLMs, Qdrant/PGVector). It loads through an exclusive slot — install alone does nothing until plugins.slots.memory: "openclaw-mem0" is set in openclaw.json.

The entrypoint index.ts uses definePluginEntry({ id: "openclaw-mem0", ... }), reads auth from openclaw.json via readPluginAuth(), parses config with mem0ConfigSchema, builds a provider (createProvider → platform or OSS), and registers eight agent tools through registerAllTools(): memory_search, memory_add, memory_get, memory_list, memory_update, memory_delete, memory_event_list, memory_event_status (the last two are platform-only).

Recall — token-budgeted, category-ranked

recall.ts replaces a naive "dump all results" with a four-stage pipeline:

  1. Search long-term memories (over-fetch maxMemories * 2) plus an optional session-scoped search by run_id, deduplicated by ID.
  2. Rank by a fixed category priority (identity > configuration > rule > preference > decision > …), then by importance, then by relevance score.
  3. Budget to a token cap (default 1500, ~4 chars/token) and a max count (15); identity/configuration memories bypass the budget when identityAlwaysInclude is on.
  4. Format grouped by category into a <recalled-memories> block for context injection.

sanitizeQuery() strips OpenClaw's "Sender (untrusted metadata)" JSON prefix before searching but deliberately does not rewrite the query — query formulation is the agent's job under the skill protocol. Recall is wrapped in try/catch so a search failure degrades gracefully and never blocks the turn.

Filtering — pre-extraction noise removal

filtering.ts cleans messages before they reach extraction so junk never becomes a memory:

  • NOISE_MESSAGE_PATTERNS drops whole messages (heartbeats, timestamps, JSON-only tool results, one-word acks like "ok"/"thanks", single emoji).
  • SESSION_SPECIFIC_PATTERNS rejects "in this session"-style capability chatter (e.g. discussions of which tools are exposed) that would be misleading if stored.
  • NOISE_CONTENT_PATTERNS strips embedded metadata/JSON blocks from otherwise-valid messages.
  • Surviving messages are truncated to MAX_MESSAGE_LENGTH (2000 chars) with a [...truncated] marker, then deduplicated. The pipeline is exported as filterMessagesForExtraction().

Isolation — per-agent namespaces

isolation.ts gives every agent its own memory namespace via session-key routing, with zero breaking changes for single-agent setups:

  • extractAgentId() parses OpenClaw keys (agent:main:main, agent:<id>:<session>, agent:main:subagent:<uuid>); main returns undefined (use the configured userId).
  • effectiveUserId(base, key) maps a named agent to <base>:agent:<id>; resolveUserId() applies priority explicit agentId > explicit userId > session-derived > configured.
  • isNonInteractiveTrigger() skips cron/heartbeat/automation sessions (by trigger or :cron:/:heartbeat: key pattern) so system jobs don't pollute the store; isSubagentSession() flags ephemeral subagent UUIDs whose namespaces are always empty on recall.

Dream-gate — guarded auto-consolidation

dream-gate.ts decides when the periodic "dream" consolidation runs (merge duplicates, resolve conflicts, prune stale entries). It is a cost-aware, lock-protected gate persisted to dream-state.json in the plugin state dir:

Cheap gates first
checkCheapGates() reads only local files: at least 24 h since last run (minHours) and at least 5 interactive sessions (minSessions). Session counts are deduped by sessionId via incrementSessionCount().
Expensive gate last
Only if the cheap gates pass does checkMemoryGate() require ≥20 stored memories — avoiding an API call on most turns.
Lock
acquireDreamLock() writes dream.lock with the exclusive wx flag so racing processes can't double-run; locks older than 1 h are reclaimed. recordDreamCompletion() resets the session counter.
Perf — gate ordering is the whole point The dream-gate deliberately orders checks cheapest-first (two local file reads) before the one network round-trip for the memory count. On a typical turn the gate short-circuits with zero API calls, so consolidation overhead is amortised to roughly once per day per user.

Skills mode

Default after openclaw mem0 init. skill-loader.ts loads two SKILL prompts shipped in openclaw/skills/ — memory-triage (structured fact extraction with importance gates and a domain overlay, default companion) and memory-dream (consolidation). It injects user config (categories, importanceThreshold, credential patterns, custom rules) into the triage prompt. In code, autoRecall and autoCapture both default to true (only disabled when explicitly set false in config.ts) and run alongside skills mode; the built-in OpenClaw session-memory hook is disabled to avoid conflicts.

The plugin shares the openclaw mem0 CLI namespace (init / add / search / list / get / update / delete / status / config / event / dream), with an interactive 4-step OSS wizard (cli/oss-wizard.ts) and full --json output for agents.

Vercel AI provider — @mem0/vercel-ai-provider

A memory provider for the Vercel AI SDK v5 (vercel-ai-sdk/, npm v2.0.5). It wraps the underlying LLM provider so that generateText/streamText automatically retrieve relevant memories and (optionally) store new ones — turning a stateless model call into a memory-augmented one.

Two ways to use it

import { createMem0 } from "@mem0/vercel-ai-provider";
const mem0 = createMem0({ provider: "openai", mem0ApiKey: "m0-...", apiKey: "..." });

// Drop-in model wrapper — memory woven in transparently
const { text } = await generateText({
  model: mem0("gpt-4-turbo", { user_id: "borat" }),
  prompt: "Suggest me a good car to buy!",
});

The provider implements the AI SDK's ProviderV2 interface (src/mem0-provider.ts); createMem0() returns a callable that builds a Mem0GenericLanguageModel (LanguageModelV2). Internally Mem0ClassSelector (mem0-provider-selector.ts) dispatches to one of ["openai", "anthropic", "cohere", "groq", "google"] via the matching @ai-sdk/* package — so memory works across all five model families. Streaming uses the provider's native doStream (no buffering middleware).

Standalone memory utilities

For use with a plain @ai-sdk/openai model (no wrapper), src/mem0-utils.ts exports four helpers (re-exported from src/index.ts):

addMemories(messages, config)
Converts an AI SDK prompt to mem0 format (convertToMem0Format, handling text/image/pdf/mdx parts) and POSTs to the platform.
retrieveMemories(prompt, config)
Returns memories formatted as a system-prompt string to inject.
getMemories(prompt, config)
Returns the raw memory array for custom processing.
searchMemories(prompt, config)
Thin search wrapper.

Search builds an OR filter over user_id/app_id/agent_id/run_id and hits POST /v2/memories/search/ with version: "v2", output_format: "v1.1", plus org/project filters. The API key is resolved by loadApiKey from config.mem0ApiKey or MEM0_API_KEY.

Decision — community provider, hosted-only The README labels this a "community-maintained" library (author Saket Aryan), pinned to AI SDK v5 (ai@5.0.2). It talks exclusively to api.mem0.ai (or a host override) — there is no OSS-engine path here, unlike the OpenClaw plugin.

Skills — reference vs pipeline

The skills/ directory ships skill definitions conforming to the skills standard. They split into two categories (per skills/README.md).

Reference skills — always on

Loaded into assistant context so it writes correct mem0 code. Each has a precise TRIGGER/DO NOT TRIGGER block in its SKILL.md to route ambiguous queries:

mem0
The default skill — Python + TypeScript SDKs (Platform + OSS Memory class) and framework integrations (LangChain, CrewAI, OpenAI Agents SDK, LlamaIndex, AutoGen, LangGraph). Has references/ docs and a scripts/mem0_doc_search.py.
mem0-cli
Terminal workflows for both the Node and Python CLIs; triggers on flags like --user-id, --json, --agent.
mem0-vercel-ai-sdk
@mem0/vercel-ai-provider / createMem0 usage; covers retrieveMemories, addMemories, getMemories, searchMemories.

Pipeline skills — run on demand

Invoked as slash commands; these do real work (branches, tests, code) and are designed to run in sequence on the same workspace:

/mem0-integrate
Detects the repo language, asks Platform vs OSS, writes failing tests first (TDD), then implements — producing a mem0-integrate/<slug> branch and .mem0-integration/ artifacts.
/mem0-test-integration
Loosely coupled verifier: installs deps, runs the repo's native suite, then a real end-to-end smoke test against the user's API key, emitting a scorecard. By design it catches only compile/runtime bugs — logical scoping errors are left to the human reviewer.
Insight — skills are duplicated, not shared A mem0 SDK-reference skill exists in three places with three version numbers: skills/mem0 (v3.0.0), mem0-plugin/skills/mem0 (v0.1.1), and OpenClaw's own memory-triage/memory-dream prompts. They serve different host packaging conventions rather than a single shared source — verify which one a given install ships.

The CLIs and Vercel provider speak the hosted REST API directly; the editor plugin uses the remote MCP server; OpenClaw embeds the mem0ai SDK and can target either the hosted platform or a fully local Memory engine. All paths converge on the same extraction/retrieval algorithm and the scoping model from the configuration system. For the hosted API surface these clients call, see Hosted Client & Proxy and the self-hosted server; for the OSS storage layer OpenClaw can use, see vector stores; the related self-hosted platform with its own MCP is OpenMemory.

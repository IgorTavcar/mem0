LLM Providers

The LLM layer is a plugin family: every provider subclasses LLMBase and implements a single generate_response(messages, tools, tool_choice, response_format) method that returns either a plain string or a normalised tool-call dict. There are 18 provider implementations spanning OpenAI-compatible APIs, native Anthropic/Gemini/Bedrock SDKs, local runtimes (Ollama, LM Studio, vLLM), and aggregators (LiteLLM, LangChain). A LlmFactory maps provider names to classes; the default is the openai provider on model gpt-5-mini. The memory algorithm drives all of these through one method, passing response_format={"type": "json_object"} to force structured extraction.

The LLMBase contract

One abstract base, one abstract method. Everything provider-specific lives in subclasses.

Defined in mem0/llms/base.py, LLMBase(ABC) handles config coercion and parameter shaping; subclasses own client construction, message reformatting, the API call, and response parsing.

__init__(config)
Accepts a BaseLlmConfig, a dict (coerced via BaseLlmConfig(**config) for backward compatibility), or None (builds a default BaseLlmConfig). Then calls _validate_config().
generate_response(messages, tools=None, tool_choice="auto", **kwargs) — abstract
The sole contract every provider must implement. messages is a list of {"role", "content"} dicts; tools is an optional list of OpenAI-style tool schemas; tool_choice defaults to "auto". Returns str (no tools) or a normalised dict (with tools). Note: most concrete providers add a response_format parameter to the signature even though the abstract method does not declare it — see the gotcha below.
_get_common_params(**kwargs)
Builds {temperature, max_tokens, top_p} from config and merges in caller kwargs. Subclasses override it where the wire format differs (Anthropic drops one of temperature/top_p; Ollama remaps to num_predict inside an options block).
_is_reasoning_model(model) / _get_supported_params(**kwargs)
Reasoning-model guard. For models in the set {o1, o1-preview, o3-mini, o3, gpt-5, gpt-5o, ...} (and prefixes o1-, o3-, after stripping a provider prefix like openai/), _get_supported_params returns only messages, response_format, tools, tool_choice, plus reasoning_effort if configured — it strips temperature/max_tokens/top_p which these models reject. Otherwise it falls through to _get_common_params.
Gotcha: the abstract signature is narrower than reality LLMBase.generate_response declares (messages, tools, tool_choice, **kwargs) — no response_format. But the engine always calls generate_response(messages=..., response_format={"type": "json_object"}) (see mem0/memory/main.py). Concrete providers therefore add response_format explicitly. A provider that implemented only the abstract signature would still accept it via **kwargs, but every real provider declares it for clarity. SarvamLLM is the outlier: its generate_response(messages, response_format=None) drops tools/tool_choice entirely and accepts response_format only to ignore it.
Deep dive: the gpt-5/o-series reasoning guard, line by line

_is_reasoning_model lower-cases the model, strips any provider/ prefix, then matches an exact set plus the prefixes o1-, o1., o3-, o3.. The comment notes it deliberately does not match gpt-5.x variants like gpt-5.4-mini via prefix, because those do support temperature — only the exact gpt-5/gpt-5o family names are treated as reasoning models. This matters because the default model is gpt-5-mini, which is not in the exact set and not matched by an o-prefix, so it goes through _get_common_params with full sampling params.

BaseLlmConfig: the shared parameter surface

One non-Pydantic config base holds the parameters common to every provider; provider-specific fields live in sibling config classes under mem0/configs/llms/.

mem0/configs/llms/base.py defines BaseLlmConfig(ABC) (a plain class, not a Pydantic model) with these defaults:

FieldDefaultNotes
modelNoneFilled by each provider's own default if unset
temperature0.1Low for deterministic extraction
api_keyNoneFalls back to provider env var
max_tokens2000
top_p0.1
top_k1Not used by all providers
enable_vision / vision_detailsFalse / "auto"Vision-model toggles
reasoning_effortNone"low"/"medium"/"high" for reasoning models
http_client_proxiesNoneIf set, builds httpx.Client(proxies=...) stored as self.http_client

Provider config subclasses (e.g. OpenAIConfig, AnthropicConfig, OllamaConfig, AWSBedrockConfig, VllmConfig, DeepSeekConfig, MinimaxConfig, LMStudioConfig, AzureOpenAIConfig) add fields like openai_base_url, openrouter_base_url, ollama_base_url, azure_kwargs, and so on. See the configuration system for the full class hierarchy and how the four factories wire them.

Decision: per-provider config coercion Most providers begin __init__ with a coercion ladder — if given None build the provider config, if a dict expand it, if a bare BaseLlmConfig copy its fields into the provider config. This lets users pass either a plain base config or a typed provider config and get the same behaviour, and is the seam where provider-specific fields (base URLs, Azure kwargs) become available.

How the engine selects and configures an LLM

The provider name is a string; the factory resolves it to a class and a config class.

mem0/llms/configs.py defines the Pydantic LlmConfig with provider (default "openai") and config (a dict). Its validate_config validator rejects any provider not in the allow-list of 18 names. The LlmFactory (mem0/utils/factory.py) then maps each name to (class_path, config_class) and lazily imports the class via importlib:

# mem0/utils/factory.py (excerpt)
provider_to_class = {
    "openai":      ("mem0.llms.openai.OpenAILLM",        OpenAIConfig),
    "anthropic":   ("mem0.llms.anthropic.AnthropicLLM",  AnthropicConfig),
    "aws_bedrock": ("mem0.llms.aws_bedrock.AWSBedrockLLM", AWSBedrockConfig),
    "openai_structured": ("mem0.llms.openai_structured.OpenAIStructuredLLM", OpenAIConfig),
    ...  # 18 entries total
}
Insight: lazy import = optional dependencies The factory stores class paths as strings and imports them only when a provider is actually requested. That is why anthropic.py, ollama.py, groq.py, together.py, litellm.py, aws_bedrock.py, gemini.py all wrap their SDK import in a try/except ImportError that re-raises with a pip install hint. You only pay for the SDKs of providers you use.

mem0/llms/__init__.py is empty — providers are never re-exported there; the factory is the single entry point. The Memory engine builds its LLM once in __init__ via LlmFactory.create(self.config.llm.provider, self.config.llm.config) and reuses it for every extraction/update call.

OpenAI-compatible family

The largest cluster. openai, deepseek, xai, minimax, vllm, and lmstudio all instantiate openai.OpenAI with a provider-specific base_url and reuse the same chat.completions.create call and the same _parse_response shape. OpenAILLM additionally supports OpenRouter: if OPENROUTER_API_KEY is set it swaps the base URL to https://openrouter.ai/api/v1 and threads through models/route/HTTP-Referer/X-Title headers.

Gotcha: store is opt-in for compatibility OpenAILLM only sends OpenAI's store parameter when self.config.store is not None, with an explicit comment that OpenAI-compatible backends (Gemini, Groq, vLLM via the OpenAI client) reject unknown fields. Sending store unconditionally would break those backends.

Anthropic

AnthropicLLM uses the native anthropic.Anthropic client and the Messages API. Two adaptations: (1) it splits out the system message into the top-level system parameter and passes the rest as messages; (2) it overrides _get_common_params to never send both temperature and top_p — Anthropic rejects that, so it keeps temperature and drops top_p. It returns response.content[0].text. Default model claude-3-5-sonnet-20240620.

AWS Bedrock

AWSBedrockLLM is by far the most complex provider (~700 lines) because Bedrock multiplexes many model families behind one runtime. It detects the family from the model id via extract_provider() against a PROVIDERS list (ai21, amazon, anthropic, cohere, meta, mistral, stability, writer, deepseek, gpt-oss, perplexity, snowflake, titan, command, j2, llama, minimax) and then sets capability flags and a per-family message formatter.

Two API paths
converse() for tool-capable / modern models (Anthropic, Amazon Nova, MiniMax) and legacy invoke_model() with per-family JSON body shapes (maxTokenCount/topP for Amazon, max_gen_len for Meta, etc.) for the rest.
Capability gating
supports_tools is only true for anthropic, cohere, amazon. generate_response routes to _generate_with_tools only when tools and self.supports_tools, else falls back to standard generation. MiniMax M2.x is intentionally excluded from tool support (tool use is only available via the OpenAI-compatible bedrock-mantle endpoint, not the Converse API used here).
top_p / temperature conflict
_build_inference_config omits topP for anthropic and minimax because both raise a ValidationException when temperature and topP are both present — mirroring the native Anthropic provider's rule.
Connection test on init
_test_connection calls list_foundation_models and warns (does not fail) if the configured model isn't found in the region.
Perf: Bedrock pings the control plane at startup Constructing AWSBedrockLLM performs a live list_foundation_models call to validate the region/model. Since the engine builds the LLM eagerly in its constructor, this adds a network round-trip to Memory(...) setup for Bedrock users (failures are caught and downgraded to a warning).

Google Gemini

GeminiLLM uses google.genai. It reshapes messages into types.Content objects, lifts the system message to system_instruction, and converts OpenAI-style tool schemas into types.FunctionDeclaration — recursively stripping additionalProperties, which Gemini's schema validator rejects. tool_choice maps to FunctionCallingConfigMode (AUTO/ANY/NONE); "any" also restricts allowed_function_names. JSON mode is requested via response_mime_type="application/json" (plus an optional response_schema). It guards against blocked responses where candidate.content is None.

Azure (and the *_structured variants)

Both Azure classes use openai.AzureOpenAI, read LLM_AZURE_* env vars via config.azure_kwargs, and fall back to DefaultAzureCredential + bearer-token provider when no API key (or the placeholder "your-api-key") is given. Both rewrite the last user message, replacing the literal word "assistant" with "ai" before sending — a workaround documented inline in the code.

Local runtimes

ollama
Native ollama.Client. Remaps sampling params into an options block (num_predict instead of max_tokens), and for JSON mode sets format="json" and appends a "respond with valid JSON only" instruction as a belt-and-braces fallback. Its _parse_response handles both dict and object response shapes.
lmstudio
OpenAI-compatible client against the local LM Studio server. Notable: it always sends a response_format — config override, then the caller's value, else defaults to {"type": "json_object"}.
vllm
OpenAI-compatible client against a self-hosted vLLM server; api key defaults to the literal "vllm-api-key" if none provided.

Aggregators

litellm
Routes through litellm.completion, reaching ~100 providers. It pre-checks litellm.supports_function_calling(model) and raises a ValueError if the model can't do function calling — relevant because the extraction path may pass tools.
langchain
Wraps an arbitrary LangChain BaseChatModel instance passed as config.model (it validates the instance type and raises if it's a string). Converts roles to LangChain tuples (system/human/ai), uses bind_tools for tool calling, and ignores response_format entirely.

Other hosted providers

groq (native groq.Groq), together (native together.Together), deepseek / xai / minimax (OpenAI-compatible base URLs), and sarvam (a hand-rolled requests.post to /chat/completions). sarvam requires its API key at construction (raises otherwise) and can pull extra params like frequency_penalty/seed when model is given as a dict.

Gotcha: xai and sarvam silently ignore tools XAILLM.generate_response and SarvamLLM.generate_response do not accept or forward tools/tool_choice — XAI's signature has no tool params and Sarvam's signature is just (messages, response_format=None). With the current ADD-only extraction algorithm the engine relies on response_format JSON rather than tools, so these still work for memory extraction, but any caller expecting tool calls from them will get plain text.

Structured output and tool calling

The engine prefers JSON-mode extraction over tool calls; the two *_structured providers exist for stricter schema-validated parsing on OpenAI/Azure.

Two mechanisms, one normalised output

JSON response format
The dominant path. The add/search flow calls generate_response(..., response_format={"type": "json_object"}) and parses the returned string as JSON. Each provider maps this onto its native JSON mode: OpenAI/Azure pass it through, Gemini sets response_mime_type, Ollama sets format="json".
Tool / function calling
When tools is supplied, providers append tools + tool_choice to the request and run _parse_response, returning a normalised dict {"content": ..., "tool_calls": [{"name", "arguments"}, ...]}. Several providers carry a # TODO: Remove tools if no issues found with new memory addition logic comment, signalling that tool-based extraction is on its way out in favour of the JSON path.

The normalised tool-call shape

Every OpenAI-compatible _parse_response produces the same structure, decoding arguments with mem0.memory.utils.extract_json before json.loads:

# shared pattern across openai/azure/litellm/groq/together/deepseek/vllm/lmstudio/minimax
{
  "content": response.choices[0].message.content,
  "tool_calls": [
    {"name": tc.function.name,
     "arguments": json.loads(extract_json(tc.function.arguments))}
  ],
}
Insight: extract_json hardens against fenced/dirty JSON Tool arguments and JSON-mode bodies are run through extract_json (in mem0/memory/utils.py) before parsing. This salvages JSON wrapped in markdown code fences or surrounded by prose — a recurring failure mode with smaller/local models. Bedrock even round-trips through it (json.loads(extract_json(json.dumps(tool_use["input"])))) to normalise dict input.

Why the *_structured variants exist

openai_structured and azure_openai_structured are dedicated providers, not flags, because they use a different OpenAI SDK call:

OpenAIStructuredLLM
Calls client.beta.chat.completions.parse(**params) (the schema-parsing beta endpoint) instead of chat.completions.create. It accepts a Pydantic/schema object as response_format and lets the SDK validate the response against it. It is a minimal class — no reasoning-model param filtering, no OpenRouter, no callback — just model/messages/temperature plus optional response_format and tools.
AzureOpenAIStructuredLLM
Confusingly, this one still calls chat.completions.create (not .parse) — it is effectively the same wire call as AzureOpenAILLM but a leaner implementation. It carries the same assistant→ai last-message rewrite and the DefaultAzureCredential fallback.
Decision: structured = separate provider key Rather than overloading a config flag, the team registered openai_structured / azure_openai_structured as first-class provider keys in LlmFactory.provider_to_class (both reusing OpenAIConfig). Users opt in by setting llm.provider = "openai_structured". This keeps the standard providers' hot path on the stable create endpoint while isolating the beta parse API.
Deep dive: how a single extraction call fans out across providers

The Memory engine issues one provider-agnostic call: self.llm.generate_response(messages=[system, user], response_format={"type": "json_object"}). Each provider translates that uniformly:

  • OpenAI/Azure/Groq/Together/DeepSeek/vLLM/MiniMax: response_format passed straight to chat.completions.create; returns message.content (a JSON string).
  • Anthropic: response_format is accepted but Anthropic's Messages API has no JSON-mode field, so the JSON shape relies on the prompt; returns content[0].text.
  • Gemini: converts to response_mime_type="application/json".
  • Ollama: sets format="json" and appends a JSON instruction.
  • LM Studio: forces {"type": "json_object"} even if none requested.
  • LangChain / Sarvam / XAI: ignore response_format — rely on prompt-level JSON instructions.

The engine then JSON-parses the returned string. This is why the algorithm tolerates providers without native JSON mode.

Where the LLM layer sits in the system

The LLM is one of the four config-driven plugin layers, alongside embeddings, vector stores, and rerankers.

flowchart LR
  MC[MemoryConfig.llm] --> LF[LlmFactory.create]
  LF --> P[provider_to_class lookup]
  P --> I[LLMBase subclass]
  I -->|generate_response| ENG[Memory engine extraction/update]
  ENG -->|response_format json| I
  I -->|str or tool_call dict| ENG
  • Configured through MemoryConfig.llm (LlmConfig) — see configuration.
  • Constructed once by the Memory/AsyncMemory constructor via LlmFactory.create.
  • Invoked in the single-pass extraction algorithm and during procedural-memory summarisation (generate_response(messages=...) with no JSON format).
  • Distinct from the hosted proxy LLM wrapper, which intercepts an outbound chat completion to inject memories — that lives in the client SDK, not this provider layer.
  • The LLM reranker reuses this same provider layer to score candidates with an LLM.
Security: API keys via env fallback Every provider resolves its key as config.api_key or os.getenv("<PROVIDER>_API_KEY") (e.g. OPENAI_API_KEY, ANTHROPIC_API_KEY, GROQ_API_KEY). Keys can be supplied in code or left to the environment; nothing is logged. Azure additionally supports keyless auth through DefaultAzureCredential when no key is set.

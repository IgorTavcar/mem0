Graph Memory (deprecated)

Graph Memory was an optional, relationship-aware retrieval layer that layered a property graph (Neo4j, Memgraph, Kuzu, Apache AGE, or Amazon Neptune) on top of mem0's vector store. It has been removed entirely from both the Python OSS package and the TypeScript OSS package in the v3 rewrite. Its job — surfacing memories connected through shared entities — is now handled natively by entity linking, a parallel vector collection plus a retrieval-time score boost that needs no external graph database. This page records what graph memory was, why it was dropped, what code (if any) survives, and how to migrate.

Status: REMOVED, not merely deprecated. As of the v3 pipeline, there is no mem0/graphs/ directory, no graph_memory.py, no graph references in mem0/memory/main.py, and no mem0-ts/src/oss/src/graphs/. The config flags enable_graph / enableGraph and the graph_store / graphStore block are gone and are no longer read. Removal was finalized in commit 59880a6f ("feat: TS SDK v3 port, graph store removal, client v3 API migration") and the docs were cleaned up in eaca45dc ("docs: remove deprecated Graph Memory references #5277").

Verification: what no longer exists

Every removal claim below was checked against the working tree at the time of writing, not against documentation.

No graphs package (Python)
ls mem0/graphs/ returns "No such file or directory". The whole subtree — mem0/graphs/__init__.py, configs.py, tools.py, utils.py, and mem0/graphs/neptune/ — is gone. So are the per-backend memory adapters mem0/memory/graph_memory.py, mem0/memory/memgraph_memory.py, and mem0/memory/kuzu_memory.py (13 graph-related .py files removed in total).
No graph wiring in the engine
grep -i graph mem0/memory/main.py returns nothing. The Memory engine no longer constructs a self.graph attribute, no longer branches on self.config.graph_store.config, and add/search results no longer contain a "relations" key.
No graphs package (TypeScript)
mem0-ts/src/oss/src/graphs/ does not exist; mem0-ts/src/oss/src/memory/graph_memory.ts was deleted. The TypeScript OSS Memory class has no graph code path. Six graph-related .ts files were removed.
No graph database service
Neither server/docker-compose.yaml (the self-hosted server) nor openmemory/docker-compose.yml (the OpenMemory platform) declares a Neo4j, Memgraph, Kuzu, or Apache AGE service. There is no shipped graph backend to point at.
No graph feature page in docs
docs/open-source/features/graph-memory.mdx was deleted. The old documentation routes (e.g. /open-source/graph_memory/overview, /platform/features/graph-memory, /features/graph-memory) now exist only as redirects in docs/docs.json, all pointing at /migration/oss-v2-to-v3.

What graph memory was

Graph memory ran alongside vector storage: every add() extracted entity–relationship–entity triples via the LLM and wrote them into a property graph, and every search() / get_all() could optionally return those relationships in a relations field next to the vector hits.

Configuration shape (historical)

It was opt-in through a graph_store section on MemoryConfig (in the old mem0/configs/base.py) plus a runtime enable_graph flag. The config validated into one of five backend configs:

# HISTORICAL — removed. Old mem0/graphs/configs.py

    config: Union[Neo4jConfig, MemgraphConfig, NeptuneConfig,
                  KuzuConfig, ApacheAgeConfig]
    # validator dispatched on provider -> concrete config class
Do not write this today. The snippet above reflects pre-v3 code recovered from git history (commit 59880a6f^). Supplying graph_store or enable_graph to current mem0 has no effect — the keys are silently unused, not honored.

How it ran inside the engine (historical)

When a graph store was configured, the old Memory.add() ran the vector write and the graph write concurrently in a ThreadPoolExecutor, then merged the two outputs into a single dict with results and relations keys. Search and get_all did the same fan-out, submitting self.graph.search(...) / self.graph.get_all(...) alongside the vector query.

The concurrency itself hinted at the cost. Commit a6130c54 ("perf: skip ThreadPoolExecutor when graph store is disabled") exists precisely because the graph path added LLM calls and thread overhead. The graph write needed its own LLM extraction pass on top of the vector pass — roughly doubling token spend per add() when enabled.
Deep dive: the relationship lifecycle bugs that accumulated

The git history shows graph memory needing repeated correctness fixes as it matured — a signal of inherent complexity:

  • 884e740b — soft-delete relationships instead of hard DELETE.
  • 53327419 — clean up graph store data on Memory.delete() (#4505).
  • 7213e1b1 — reset graph database in Memory.reset() (#4185).
  • 06c25eb0 — use the root LLM config as the graph-store LLM fallback instead of a hardcoded OpenAI default (#4466).
  • e95090e1 — add a missing json keyword to graph prompts (#4249).
  • 72e2c5c2 — handle malformed entity dicts and None LLM responses in memgraph_memory.

Each fix kept three or four backend adapters in sync — the maintenance surface that v3 retired.

Why it was removed

The single-pass extraction + entity-linking design of the v3 algorithm recovers the practical benefit of graph memory — pulling in memories connected through shared people, places, and things — at a fraction of the cost and with zero external infrastructure.

Relationship retrieval was subsumed, not lost
The value users got from a graph was mostly "when I ask about X, also surface memories about entities related to X." V3 achieves this with an entity boost folded into the fused retrieval score (see score fusion), not a graph traversal. Entities extracted from the query match entities indexed against stored memories, and matching memories get a ranking bump.
Cost
A configured graph store meant a second LLM extraction pass on every add() to mint triples. V3's entity extraction uses local spaCy NLP (mem0/utils/entity_extraction.py) — no LLM call, no tokens.
Operational simplicity
Graph memory required running and credentialing a separate database (Neo4j/Memgraph/etc.). Entity linking lives inside the vector store you already configured (see vector stores), as a sibling collection.
Maintenance burden
Five backends, each with its own Cypher/SQL dialect quirks and lifecycle edge cases (see the deep dive above), against one shared entity-linking code path.
Measured wins justified the swap
Per the README, v3 reports 91.6 on LoCoMo (+20 over the previous algorithm) and 94.8 on LongMemEval (+27) with single-pass retrieval — these gains came from the new pipeline, not from a graph layer. See Evaluation & Benchmarks.
Naming legacy. The v3 entity boost is still nicknamed an "entity graph boost" in docs/migration/oss-v2-to-v3.mdx and the prompt text in mem0/configs/prompts.py still describes building "a graph of related memories." That language is conceptual — there is no graph database and no graph traversal behind it. It refers to memory-to-memory links carried in payload fields, scored at retrieval time.

The replacement: entity linking

Entity linking is not a graph store with a new name — it is a second vector-store collection plus a retrieval boost, implemented entirely inside mem0/memory/main.py.

The entity store

The Memory.entity_store property lazily creates a parallel collection named {collection_name}_entities using the same vector store provider via VectorStoreFactory.create(...). There is no separate provider to configure.

# mem0/memory/main.py  (current)
@property
def entity_store(self):
    if self._entity_store is None:
        entity_config = _safe_deepcopy_config(self.config.vector_store.config)
        entity_collection = f"{self.collection_name}_entities"
        # set collection_name on the cloned config ...
        # Qdrant: reuse the existing client to avoid embedded RocksDB lock contention
        self._entity_store = VectorStoreFactory.create(
            self.config.vector_store.provider, entity_config)
    return self._entity_store

On add(), _upsert_entity() embeds each extracted entity, searches the entity collection for an existing match, and either appends the new memory_id to that entity's linked_memory_ids payload (when similarity ≥ 0.95) or inserts a fresh entity record. On delete, _remove_memory_from_entity_store() strips the id from every entity scoped to the same session and deletes entity records that become orphaned.

Same store, sibling collection. Because the entity store reuses the configured vector provider, "the database" you operate is unchanged. Compare this to graph memory, which demanded a wholly separate engine. The only operational note (from the migration guide): the vector store credentials must be allowed to create a new collection, or you must pre-create {collection}_entities with matching embedding dimensions.

Retrieval boost

At search time, entities are extracted from the query and matched against the entity collection (entity_store.search_batch(...)), producing per-memory boosts. mem0/utils/scoring.py fuses three signals — semantic similarity, BM25 keyword score, and the entity boost (ENTITY_BOOST_WEIGHT = 0.5) — into one combined score. The fusion adapts to which signals are available (semantic-only, semantic+BM25, or all three when spaCy and the entity store are active). Crucially, BM25 and entity scores only re-rank semantic candidates; they do not expand recall.

flowchart LR
  Q[query] --> P[preprocess: lemmatize + extract entities]
  P --> S1[semantic vector search]
  P --> S2[BM25 keyword score]
  P --> S3["entity match vs entities collection"]
  S1 --> F["score fusion -> combined score"]
  S2 --> F
  S3 --> F
  F --> K[top-K]

For the full pipeline including temporal reasoning and the ADD-only extraction prompts, see Memory Algorithm and the end-to-end traces in Data Flow.

Surviving graph references (and what they mean)

A few graph-flavored strings remain in the tree. None of them is a live graph store; they are vestigial or repurposed.

mem0/memory/utils.py — Cypher helpers
sanitize_relationship_for_cypher() and remove_spaces_from_entities(..., sanitize_relationship=...) still exist and are exercised by tests/memory/test_memory_utils.py, whose docstrings reference "Neo4j / Memgraph (sanitize=True)" and "Kuzu / Neptune (sanitize=False)" paths. However, no non-test caller in mem0/ invokes remove_spaces_from_entities — its only in-package caller is itself. These are effectively dead/legacy utilities retained with tests; they are not wired into any current backend.
mem0/exceptions.py — kuzu in a docstring
DependencyError's example mentions details={"package": "kuzu", "feature": "graph_store"}. This is documentation text inside a docstring, not active code.
mem0/configs/prompts.py — "graph of related memories"
Conceptual wording for entity linking, as noted above. No graph DB involved.
mem0/vector_stores/neptune_analytics.py + mem0/configs/vector_stores/neptune.py
Neptune Analytics survives as a vector store provider, distinct from the removed Neptune graph adapters that lived under mem0/graphs/neptune/. See Vector Stores — this is a vector index, not relationship storage.
docs/integrations/langgraph.mdx and similar
"LangGraph" is an unrelated LangChain orchestration library; matches on the substring "graph" are coincidental and not about mem0 graph memory.
Do not mistake Neptune Analytics for graph memory. The vector_stores Neptune Analytics provider stores embeddings and answers vector queries. The removed mem0/graphs/neptune/ adapters stored entity triples. Same vendor, different feature — only the vector-store side remains.

Migrating off graph memory

The canonical guide is docs/migration/oss-v2-to-v3.mdx (linked from the README as oss-v2-to-v3), which has a dedicated "Graph Memory → Entity Linking" section. The essentials:

  • Remove enable_graph / enableGraph from your config.
  • Remove the graph_store / graphStore block — it is no longer read.
  • Uninstall graph drivers (neo4j, memgraph, etc.) if you installed them only for mem0.
  • No data migration is required. Entity linking activates automatically on the next add() call, populating {collection}_entities on first use.
  • Client SDK callers: enable_graph / enableGraph was also removed from add(), search(), get_all(), and project.update() on the hosted MemoryClient (commit 9d6b79a1; org/project options dropped in 88f696a6).
Breaking: the relations field is gone. Search and get_all results no longer populate the old relations key. Entity relationships are consumed indirectly through retrieval ranking — they are not exposed as a queryable graph structure. Any application that traversed graph relationships directly must be redesigned against the new API; there is no drop-in equivalent that returns triples.

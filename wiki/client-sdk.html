Hosted Client & Proxy

mem0.client.main ships two thin HTTP clients — MemoryClient (sync, on httpx.Client) and AsyncMemoryClient (async, on httpx.AsyncClient) — that talk to the hosted Mem0 platform at https://api.mem0.ai. They expose the same memory verbs as the self-hosted engine (add / search / get / get_all / update / delete / history / users / batch / feedback / export) but run zero local LLM, embedding, or vector-store code — all extraction and retrieval happens server-side. Alongside them, mem0.client.project manages organizations/projects/members, and mem0.proxy.main wraps an OpenAI-compatible chat completion to transparently retrieve relevant memories and write new ones around each call.

Where this fits

mem0 has two usage modes: the OSS engine you run yourself, and the hosted platform you call over HTTP. This page covers the hosted side and the LLM proxy. The clients are intentionally dumb — they marshal arguments, POST/GET/PUT/DELETE JSON, raise structured errors, and emit telemetry. Everything intelligent (fact extraction, the retrieval algorithm, vector indexing, graph/entity linking) lives behind the API.

Files
mem0/client/main.py (both clients), mem0/client/project.py (project/member management), mem0/client/types.py (Pydantic option models), mem0/client/utils.py (the api_error_handler decorator), mem0/proxy/main.py (the chat-completion proxy). mem0/exceptions.py defines the structured exception hierarchy. Both clients are re-exported from mem0/__init__.py as from mem0.client.main import AsyncMemoryClient, MemoryClient.
Auth
API key from the api_key argument or the MEM0_API_KEY environment variable; a missing key raises ValueError("Mem0 API Key not provided...") at construction.
Decision The hosted client is a separate, dependency-light surface (only httpx + requests + pydantic) — it does not import the OSS Memory engine, its providers, or any vector store. Importing MemoryClient pulls in none of the LLM/embedding stack, which is why a hosted-only install stays small.

Construction, auth, and identity resolution

Both clients share the same __init__ shape: MemoryClient(api_key=None, host=None, client=None).

  • host defaults to "https://api.mem0.ai"; overridable for self-hosted platform deployments or testing.
  • client lets you inject a pre-built httpx.Client / httpx.AsyncClient (e.g. for custom transports, proxies, mocking). When passed, the client's base_url and auth headers are overwritten to the correct values.
  • When no client is injected, a fresh one is created with a 300-second timeout and headers Authorization: Token <api_key> and Mem0-User-ID: <hash>.

The Mem0-User-ID header

user_id is initially seeded from get_user_id() (the OSS anon-id) but is then overwritten with the MD5 hash of the API key: hashlib.md5(self.api_key.encode()).hexdigest(). This deterministic hash is sent as the Mem0-User-ID header on every request — it identifies the caller for telemetry/correlation without exposing the raw key.

API-key validation & org/project resolution

_validate_api_key() runs at construction and does double duty:

  1. It hits GET /v1/ping/. A non-2xx response surfaces the server's detail field as a ValueError("Error: ...") — so a bad key fails fast at construction, not on first real call.
  2. The ping response carries org_id, project_id, and user_email. When present, org_id/project_id are stored on the instance and become the scope for project-management calls; user_email is stored for telemetry.
Gotcha AsyncMemoryClient._validate_api_key() is a synchronous method using the blocking requests library, called directly inside __init__. The async client therefore does one blocking network round-trip at construction time. Only subsequent memory operations use the non-blocking httpx.AsyncClient.
Insight org_id / project_id are resolved from the API key server-side, not injected into request params. MemoryClient._prepare_params() deliberately does not add them (see the in-code comment "org_id and project_id are resolved from API key — not injected into params"). Only the Project manager (project.py) puts them in the URL/query, because those endpoints are org/project-scoped by path.

Anonymous-ID aliasing

On init, _maybe_alias_anon_to_email(self.user_email) fires PostHog $identify events so a user's prior anonymous OSS/CLI telemetry IDs (read via read_anon_ids()) get merged into their resolved email. It is idempotent (guarded by is_aliased / mark_aliased), best-effort, and never raises. See telemetry for the OSS side. 

from mem0 import MemoryClient, AsyncMemoryClient

client = MemoryClient()                 # reads MEM0_API_KEY
client = MemoryClient(api_key="m0-...") # explicit

# Async: validation is sync, but ops are awaited; supports async context manager
async with AsyncMemoryClient() as ac:
    await ac.add("I love sci-fi movies", user_id="alice")

Only AsyncMemoryClient implements __aenter__/__aexit__; exiting the context calls await self.async_client.aclose(). The sync client has no context manager and no explicit close.

Entity params must go inside filters

The v3 API does not accept identity fields at the top level. search() and get_all() enforce this client-side: a module-level ENTITY_PARAMS = {"user_id","agent_id","app_id","run_id"} is intersected with the kwargs, and any hit raises a ValueError telling you to use filters={'user_id': '...'} instead.

Gotcha — asymmetry This guard fires only on search and get_all. add() and delete_all() do not reject top-level user_id — the proxy and many examples still pass user_id= straight to add(). So the same kwarg is accepted on writes but rejected on reads.

Typed options vs. kwargs

mem0/client/types.py defines Pydantic option models that give IDE autocompletion and runtime validation: AddMemoryOptions, SearchMemoryOptions, GetAllMemoryOptions, DeleteAllMemoryOptions, UpdateMemoryOptions, and ProjectUpdateOptions. Each method takes an optional options= model and **kwargs; they are merged with kwargs winning: {**options.model_dump(exclude_unset=True), **kwargs}. None-valued params are stripped before sending (_prepare_params / _prepare_payload).

AddMemoryOptions
filters, metadata, infer, custom_categories, custom_instructions, timestamp, structured_data_schema.
SearchMemoryOptions
filters, metadata, top_k, rerank, threshold, fields, categories. (Server-side reranking is opt-in via rerank.)
GetAllMemoryOptions
filters, page, page_size, start_date, end_date, categories.
UpdateMemoryOptions
text, metadata, timestamp.
latestOnly on hosted reads The v3 read endpoints support a latest_only flag that collapses a superseded-memory chain to just its current head. The TypeScript SDK surfaces it as a typed latestOnly option (serialized to latest_only; see mem0-ts/src/client/mem0.types.ts). The Python client does not have a dedicated field in types.py, but because every method forwards arbitrary **kwargs into the JSON body, you can pass latest_only=True directly to search() / get_all().

delete_linked

delete(memory_id, delete_linked=False) (and its async twin) gained delete_linked. When True, deleting a memory also transitively removes the older memories it superseded (the v3 linked_memory_ids chain). It is the delete-side counterpart of latest_only: without it, a superseded memory can resurface after you delete the current head. The flag is sent as a query param, normalized via {"delete_linked": delete_linked or None} so the param is omitted when False.

feedback

feedback(memory_id, feedback=None, feedback_reason=None) records relevance signals. The feedback string is upper-cased and validated against {"POSITIVE", "NEGATIVE", "VERY_NEGATIVE"} (or None); anything else raises ValueError. POSTs {memory_id, feedback, feedback_reason} to /v1/feedback/.

Deep dive: API-version sprawl in the endpoint paths

The client straddles three API generations. Writes/reads went to v3 (/v3/memories/add/, /v3/memories/, /v3/memories/search/), while per-ID operations, history, batch, exports, summary, feedback, and entity listing still use v1 (/v1/memories/{id}/, /v1/batch/, /v1/entities/, …). Entity deletion uses v2 (/v2/entities/{type}/{name}/), and org/project/webhook management uses the Django-style /api/v1/... prefix. The option-model docstrings still mention "v2 API" for search/get_all even though the code now posts to v3 — a doc-vs-code drift worth noting. The net effect: the client is a literal map of the platform's REST surface as it evolved, not a clean single-version contract.

Error handling: the api_error_handler decorator

mem0/client/utils.py defines api_error_handler, a decorator applied to every public client and project method. It converts raw httpx errors into the structured exception hierarchy in mem0/exceptions.py.

  • On httpx.HTTPStatusError: it parses the response body (preferring the JSON detail field), captures {status_code, url, method} as debug info, and calls create_exception_from_response(...) to pick the right exception class by status code.
  • For 429 it additionally extracts Retry-After and X-RateLimit-* headers into debug_info so callers can back off intelligently.
  • On httpx.RequestError it maps transport failures to NetworkError with a specific error_code: NET_TIMEOUT (TimeoutException), NET_CONNECT (ConnectError), or NET_GENERIC.

The HTTP_STATUS_TO_EXCEPTION map (in exceptions.py) wires status codes to classes:

StatusException
400, 409, 422ValidationError
401, 403AuthenticationError
404MemoryNotFoundError
408, 502, 503, 504NetworkError
413MemoryQuotaExceededError
429RateLimitError
500 / defaultMemoryError (base)

All inherit from MemoryError, which carries message, error_code, details, suggestion, and debug_info. The legacy APIError class still lives in utils.py but is explicitly marked deprecated ("Use specific exception classes from mem0.exceptions instead").

Gotcha api_error_handler wraps both sync and async methods, but its wrapper is a plain (non-async) function. It catches the exceptions raised inside the coroutine body of the async methods (which raise synchronously before awaiting, or surface via the awaited raise_for_status() inside the same call stack). The construction-time _validate_api_key is not decorated — it does its own try/except and raises a plain ValueError.

Telemetry capture

Each method ends with capture_client_event(event_name, self, {...}) from mem0/memory/telemetry.py. Events are named client.<method> (e.g. client.add, client.search, client.project.create) and tagged with sync_type ("sync"/"async").

  • It is gated on the MEM0_TELEMETRY flag and is never allowed to raise — failures are swallowed at debug level.
  • Payloads avoid leaking memory content: for add/search/get_all the event records only list(kwargs.keys()) (the names of params used), and metadata is explicitly del-eted from the captured kwargs before sending.
  • Events are attributed to the resolved user_email from the ping response (vs. the OSS capture_event path which records the local vector-store/LLM class names — see the engine telemetry).

Project & member management (project.py)

Each client exposes a .project attribute — a Project (sync) or AsyncProject (async) instance, both subclasses of the abstract BaseProject. They are constructed in the client's __init__ with the resolved org_id/project_id/user_email, and they share the client's underlying HTTP client object.

ProjectConfig
A Pydantic model (validate_assignment=True, extra="forbid") holding org_id, project_id, user_email. Exposed via read-only properties on BaseProject.
Validation
The constructor calls _validate_org_project(), raising ValueError("org_id and project_id must be set...") if either is missing — so a key whose ping did not resolve a project will fail when the .project manager is built.
_prepare_params vs _prepare_org_params
The project manager does inject org_id/project_id into params (unlike the memory client). _prepare_params requires both together (passing only one raises "Please provide both"); _prepare_org_params requires only org_id for org-level calls.

Memory Decay & multilingual project.update() accepts decay (a bool, off by default) that toggles search-time ranking which boosts recently-used memories and dampens stale ones, and multilingual to keep the input language for storage/retrieval. These project-level retrieval knobs are part of the hosted retrieval algorithm, not something the OSS engine exposes.

Deprecated client-level project methods

The older MemoryClient.get_project() and MemoryClient.update_project() (and their async twins) still work but log a DeprecationWarning-style warning steering you to client.project.get() / client.project.update(). They will be removed in package v1.0. Note update_project on the client supports memory_depth and usecase_setting (via ProjectUpdateOptions) which the new project.update() does not — the surfaces are not perfectly aligned during the transition.

The LLM proxy (mem0/proxy/main.py)

The proxy is an OpenAI-compatible chat-completion wrapper that transparently adds memory to any LLM call: it retrieves relevant memories, injects them into the prompt, fires the completion through LiteLLM, and asynchronously persists the new turn. It works with either a hosted MemoryClient or the OSS Memory engine.

Mem0
Top-level entry. Mem0(config=None, api_key=None, host=None). If api_key is given it builds a MemoryClient; otherwise it builds an OSS Memory.from_config(config) (or default Memory()). Exposes .chat.completions.create(...).
Chat → Completions
Nested classes that mimic the OpenAI client shape so the proxy is a near drop-in: client.chat.completions.create(model=..., messages=..., user_id=...).

LiteLLM bootstrapping

At import time the module tries import litellm; if missing, it auto-pip-installs litellm in a subprocess (pip install litellm) and re-imports, exiting the process if that fails.

Gotcha Importing mem0.proxy.main can trigger a live pip install as a side effect of import. This is convenient in notebooks but surprising in locked-down or production environments; pre-installing litellm avoids it.

The create() flow

Completions.create(model, messages, user_id=, agent_id=, run_id=, top_k=10, ...) takes the full OpenAI parameter set (temperature, tools, streaming, response_format, etc.) plus Mem0-specific args. The memory dance:

  1. Guard: requires at least one of user_id/agent_id/run_id (else ValueError), and requires the model to support function calling per litellm.supports_function_calling(model) (else ValueError).
  2. Prepend system prompt: _prepare_messages injects MEMORY_ANSWER_PROMPT as a system message if the conversation does not already start with one.
  3. Only when the last message is from the user:
    • Write (fire-and-forget): _async_add_to_memory spawns a daemon thread that calls mem0_client.add(...) with the messages. It does not block the completion and its result/errors are not surfaced.
    • Read: _fetch_relevant_memories joins the last 6 messages as "role: content" lines and calls search(query=..., top_k=top_k).
    • Inject: _format_query_with_memories rewrites the last user message to embed the retrieved facts plus an "Entities" line and the original question.
  4. Complete: forwards everything to litellm.completion(...) and returns its response unchanged.
  5. Telemetry: emits mem0.chat.create via capture_event (OSS Memory) or capture_client_event (hosted client).
from mem0.proxy.main import Mem0

client = Mem0(api_key="m0-...")   # hosted; or Mem0(config={...}) for OSS
resp = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "What movies should I watch tonight?"}],
    user_id="alice",
    top_k=5,
)
# memories about Alice's taste were retrieved + injected; this turn is saved async
Perf / correctness trade-off Memory writes run on a fire-and-forget daemon thread, so a slow or failing add() never delays or breaks the chat response — but it also means a failed write is silent, and a memory written this turn is not guaranteed to be searchable on the immediate next turn (race against indexing). Retrieval uses only the trailing 6 messages; the code has a TODO to summarize longer history instead of truncating.
Format branches on client type _format_query_with_memories reads relevant_memories["results"] and pulls relations (graph entities) only for the OSS Memory path; for the hosted MemoryClient path it iterates the result list directly and produces no entities. So injected context differs slightly between the two backends.

Hosted client vs. self-hosted engine

Same verbs, fundamentally different machinery. The hosted client is an HTTP shell; the engine runs the whole pipeline locally with pluggable LLM, embedding, and vector-store providers wired by the config system.

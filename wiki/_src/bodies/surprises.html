Surprises & Gotchas

This page collects the cross-cutting things that surprised us while reading the mem0 source: clever patterns worth stealing, latent footguns, performance and security subtleties, and the deprecations that make the code disagree with its own docs. The single biggest theme: the April-2026 rewrite turned mem0 into an ADD-only, single-LLM-call engine with no graph database and no LLM-driven UPDATE/DELETE — and a lot of older docs, prompts, and config keys still ship as dead weight. Every claim here was checked against the tree; counts were recounted from the actual provider files, not from AGENTS.md.

The one mental model that explains half this page The engine no longer asks the LLM to reconcile new facts against old ones. add() makes exactly one LLM call with ADDITIVE_EXTRACTION_PROMPT, emits only ADD events, dedupes mechanically by MD5 hash, and never overwrites. UPDATE/DELETE happen only when a caller invokes update()/delete() directly. Relationship awareness comes from a per-collection entity vector store, not a graph DB. Once you internalize this, most of the "this code branch never fires" surprises below follow directly. See the algorithm.

Clever patterns

Techniques in the codebase that are non-obvious but generalizable.

Factories store providers as dotted strings, imported lazily
Every factory in mem0/utils/factory.py maps a provider name to a dotted import path (e.g. "mem0.vector_stores.qdrant.Qdrant"), resolved on demand by load_class() (importlib.import_module + getattr). Heavy backend SDKs (boto3, sentence-transformers, google-genai) are imported only when that provider is actually selected; an unknown name raises ValueError at create() time. Each native-SDK provider also wraps its own import in try/except ImportError with a pip-install hint. See the config system.
Anti-hallucination integer ID mapping for dedup
When existing memories are shown to the LLM for dedup context, they are presented with sequential integer IDs ("0", "1", …) while a separate uuid_mapping dict resolves them back to real UUIDs. The model never sees a raw UUID, so it cannot fabricate or corrupt one; persisted memories always get a fresh uuid.uuid4(). See the algorithm.
Entity boosts are spread-attenuated so hubs can't dominate
_compute_entity_boosts in mem0/memory/main.py weights each match by similarity * 0.5 * (1 / (1 + 0.001·(num_linked−1)²)). A promiscuous entity (e.g. the user's own name, linked to hundreds of memories) contributes a far smaller per-memory boost, capped at ENTITY_BOOST_WEIGHT = 0.5. Only entity-store hits with similarity ≥ 0.5 count toward a boost; entity upsert/linking uses a much stricter ≥ 0.95 match threshold. See retrieval scoring.
Adaptive divisor keeps fused scores comparable
score_and_rank in mem0/utils/scoring.py normalizes the additive sum (semantic + BM25 + entity) by a max_possible divisor that adapts to which signals fired: 1.0 semantic-only, 1.5 semantic+entity, 2.0 semantic+BM25, 2.5 all three. BM25 and entity are additive bonuses on top of baseline semantic relevance, never a re-weighting of it. See data flow.
extract_json salvages dirty/fenced JSON from weak models
Tool arguments and JSON bodies pass through mem0.memory.utils.extract_json before json.loads, recovering JSON wrapped in markdown fences or prose — a recurring failure mode for small/local models. Bedrock even round-trips dict input through it. See LLM providers.
Self-healing deferred initialization (TS OSS)
Vector-store creation is deferred to _autoInitialize() so the embedding dimension can be auto-probed. _ensureInitialized() stores the first failure instead of throwing from the constructor and retries on the next method call, so a transiently-down embedder or store at startup doesn't permanently brick the instance. See the TypeScript SDK.
Single-use refresh tokens via one conditional UPDATE
consume_refresh_jti() in server/auth.py runs UPDATE refresh_token_jtis SET used_at=now WHERE jti=? AND used_at IS NULL AND expires_at>now and checks rowcount==0 to 401. This collapses the read-check-write race into a single atomic statement, so concurrent replays of the same token race on one row and at most one wins. See the server.
OTP claim upgrades an agent key in place
In the CLI, claim_via_otp() reuses the email-code flow but adds agent_mode_api_key to the verify body; the backend upgrades the key in place, so the API key value never changes, memories transfer, and agent_mode flips false without disrupting a running agent. See Integrations.
Dream-gate orders checks cheapest-first
OpenClaw's dream-gate.ts runs two local file-read gates (≥ 24h since last run, ≥ 5 sessions) before the one network round-trip for the ≥ 20 memory-count gate, and holds an exclusive wx lock file (reclaimed after 1h) so racing processes can't double-run consolidation. See Integrations.
Deep dive: AsyncMemory is a copy, not a wrapper

AsyncMemory in mem0/memory/main.py is a full structural duplicate of Memory — every method body is copied, and async-ness comes solely from wrapping blocking calls (embed, vector ops, LLM, SQLite, lemmatize, entity extraction) in asyncio.to_thread. The single shared SQLite connection is opened with check_same_thread=False and protected by a process-local threading.Lock.

Not actually concurrent Both async _add_to_vector_store and _search_vector_store wrap each blocking step in asyncio.to_thread but await them in sequence — the steps do not run in parallel. The only genuine fan-out via asyncio.gather is delete_all. The reranker is dispatched through to_thread specifically so it can't block the event loop.

Performance surprises

Where the engine spends — or deliberately avoids spending — time and money.

infer=False skips the LLM, dedup, and entity linking entirely
The fast path stores each message verbatim via _create_memory: one embed + one vector insert + one ADD history row per message, with name promoted to actor_id. No existing-memory search, no extraction call, no hash dedup, no entity linking. It is the right choice for pre-cleaned facts where you want minimal latency and zero LLM cost. See data flow.
Lazy SDK imports keep import mem0 cheap
Because all provider SDK imports are deferred to load_class(), importing mem0 and building a MemoryConfig is cheap regardless of how many backends are installed — you only pay import cost for the providers you actually instantiate. The empty 0-byte __init__.py files in mem0/embeddings/ and mem0/llms/ are a feature, not a bug. See embeddings.
text_lemmatized is precomputed at write time
The engine writes a lemmatized copy of the memory text into the payload on insert, so BM25/keyword search only lemmatizes the query at read time rather than re-tokenizing the whole corpus — cheap enough to run hybrid search on every search(). See vector stores.
AWS Bedrock pings the control plane during construction
AWSBedrockLLM.__init__ calls list_foundation_models to validate region/model, adding a network round-trip to Memory() setup for Bedrock users (failures are downgraded to a warning). See LLM providers.
LLMReranker makes N LLM calls per search
It scores each candidate document with a separate synchronous LLM call, making it by far the slowest and most expensive reranker — best reserved for small candidate pools or offline eval. See rerankers.
Qdrant is the only store with native batched search
The base search_batch loops over search() sequentially; Qdrant alone overrides it with query_batch_points (plus a sequential fallback on error). Heavy batch workloads on other stores are silently serial. See vector stores.
Server request logs are written off the hot path and pruned manually
_persist_request_log runs via loop.run_in_executor so DB writes never block responses. The append-only request_logs table (~864k rows/day at 10 req/s) uses a BRIN index on created_at and is pruned only by scripts/prune_request_logs.py / make prune-logs — nothing prunes automatically. See the server.
Plugin hooks are engineered to never block the editor
Every mem0-plugin hook command ends with 2>/dev/null || true, scripts exit 0 with 3–8s timeouts, and auto_capture.py reads only the transcript tail (200 lines / 8000 chars) and posts with infer=True so extraction is async — a slow capture can never stall the session. See Integrations.

Correctness & gotchas

Behavior that looks one way and is actually another — the highest-risk section for callers.

The ADD-only consequence: dead branches everywhere

Code branching on UPDATE/DELETE events silently never fires Since add() emits only event: 'ADD', any caller (or test) that switches on returned UPDATE/DELETE events is dead code. Memories accumulate and nothing is overwritten or deleted on the add path. Use update()/delete() explicitly. See the algorithm.

Silent empty results

  • add() returns {"results": []} on extraction failure without raising. If the LLM call fails, returns nothing, or all candidates are hash-deduped, add() logs at error/debug level and returns an empty list — but it still persists the raw messages and still calls db.save_messages to keep the rolling 10-message buffer for the next turn's Phase-0 context. Callers must inspect the list, not assume a write occurred. See the memory engine.
  • Conversation context is saved even when nothing is extracted — the buffer preservation above happens before the early return []. See data flow.

Asymmetric and inconsistent APIs

search/get_all reject top-level identifiers; add accepts them
_reject_top_level_entity_params raises ValueError if user_id/agent_id/run_id are passed as top-level kwargs to search() or get_all() — they must go inside filters={...}. add() (and on the hosted client, delete_all()) accept them directly. Identity params are valid on writes yet rejected on reads: a common runtime trap. See the engine and the hosted client.
Sync and async raise different exceptions for the same bad input
Sync add() raises Mem0ValidationError VALIDATION_002 for an invalid memory_type, but async add() raises a plain ValueError for the identical condition. Catching Mem0ValidationError will miss the async path. See the engine.
delete_all requires an identifier — there is no wipe shortcut
It raises ValueError if called with no user_id/agent_id/run_id, explicitly pointing callers at reset() to clear everything. See the engine.
Vector-store result shapes are duck-typed and inconsistent
There is no single OutputData — ~20 providers each define a local OutputData(BaseModel), Redis uses MemoryResult, and Qdrant returns native point objects; the engine reads .id/.score/.payload by attribute. list() nesting also differs: pgvector/turbopuffer/redis return [[OutputData,…]], Qdrant's list() returns the raw scroll() tuple while its search() returns a flat list. See the interface.

Scoring & retrieval edge cases

Threshold gates the semantic score BEFORE fusion In score_and_rank, any candidate with semantic_score < threshold is dropped before combining, so a strong BM25 hit or entity boost can never resurrect a sub-threshold semantic match. The candidate pool is also seeded only from semantic results (_search_vector_store over-fetches max(limit·4, 60)): a memory that matches BM25 or an entity but is absent from the semantic top-N cannot surface at all. See data flow.
  • No temporal/recency ranking at query time. score_and_rank never weights by created_at. Temporal reasoning is an extraction-time emergent property: ADDITIVE_EXTRACTION_PROMPT grounds relative references like "last week" to absolute dates against the Observation Date before storing, and because the engine is ADD-only, each dated instance becomes a separately retrievable memory. "Where did I live before SF?" matches the past instance directly — the cited reason the LoCoMo benchmark rose from 51% to 93%. See temporal reasoning.
  • Score sign/scale is not normalized across stores. pgvector returns cosine distance (lower = closer), turbopuffer returns 1 − dist, Redis returns raw vector_distance. Raw .score values are not comparable across backends; the engine's fusion accounts for this, your downstream code may not. See vector stores.
  • FAISS filters by in-memory post-filtering. No server-side filter engine: it over-fetches (fetch_k = top_k·2) then runs _apply_filters in Python, so filtered searches can under-return when matches fall outside the over-fetch window. See vector stores.
  • keyword_search returns None as a "not supported" sentinel, not []. VectorStoreBase.keyword_search defaults to None; the engine checks if keyword_results is not None before fusing BM25, so unsupported stores silently degrade to semantic-only. Returning [] would falsely claim support with zero hits. See the interface.

Reranking

Two independent guards gate reranking; either alone is a silent no-op
Reranking runs only if both a reranker is configured (MemoryConfig.reranker non-None) and search(rerank=True) is passed. An empty result set also short-circuits it. See rerankers.
Silent provider-level fallback to rerank_score 0.0
Every provider wraps scoring in except Exception and falls back to the original order with rerank_score=0.0 (LLMReranker uses 0.5 per-document). Uniform 0.0 scores are the tell that reranking failed and you are seeing unreranked order. Scales also differ wildly across providers (API relevance, judged 0–1, raw cross-encoder logits, optional min-max), so rerank_score is not comparable across backends. See rerankers.

Dimensions, NLP, and cross-SDK collections

Two unsynced embedding-dimension fields embedder.config.embedding_dims and vector_store.config.embedding_model_dims are independent; nothing copies one into the other, and both happen to default to 1536. Choosing a non-1536 model (Gemini 768, Vertex 256, FastEmbed/HF auto-detect) without also setting embedding_model_dims creates a wrong-width index and breaks inserts. See embeddings.
  • The nlp extra silently degrades retrieval when absent. Without mem0ai[nlp], extract_entities returns [] (no entity linking/boost) and lemmatize_for_bm25 returns raw text. Qdrant additionally needs fastembed for BM25 sparse vectors; if missing it warns and disables BM25. spacy_models.py auto-downloads en_core_web_sm on first use and sets sticky failure flags otherwise. See the algorithm.
  • Sharing one Qdrant collection across SDKs breaks BM25. Python writes the lemmatized field as text_lemmatized (snake_case); TypeScript writes textLemmatized (camelCase). A shared collection silently breaks lemma-based BM25 across languages — collections must be language/SDK-scoped. See the algorithm.
  • Qdrant collections created before hybrid search cannot do BM25. They lack the named bm25 sparse slot; writing into it is rejected. Qdrant detects this via _has_bm25_slot on init, warns, and disables BM25 (semantic still works). See vector stores.
  • OpenAI/Azure batch embeds re-sort by response index. embed_batch chunks into batches of 100 and re-sorts response.data by .index before returning, because the embeddings API does not guarantee output order matches input order — a naive list comprehension would silently misalign vectors with their source texts. See embeddings.
  • MockEmbeddings makes all memories identical. It always returns the same fixed 10-dim vector, so cosine similarity between any two memories is 1.0 and ranking is meaningless — fine for plumbing tests, useless for retrieval-quality tests. It doubles as the no-op stand-in for Upstash server-side embedding. See embeddings.

LLM provider quirks

The abstract generate_response signature omits response_format, but every provider needs it
LLMBase.generate_response declares only (messages, tools, tool_choice, **kwargs), yet the engine always calls it with response_format={'type':'json_object'}. Concrete providers add it explicitly; SarvamLLM accepts it only to ignore it. See LLM providers.
xai and sarvam silently drop tools/tool_choice
Their generate_response signatures have no tool parameters, so a tool-calling caller gets plain text. They still work for memory extraction because the algorithm uses response_format JSON, not tools. See LLM providers.
Anthropic and Bedrock omit top_p when temperature is set
Both native AnthropicLLM and AWSBedrockLLM (_build_inference_config) drop top_p/topP when temperature is present, because Anthropic and MiniMax reasoning models raise a ValidationException if both are sent. See LLM providers.
gpt-5-mini (the default) is deliberately NOT a reasoning model
LLMBase._is_reasoning_model matches an exact set (o1, o3, gpt-5, gpt-5o, gpt-5o-mini, …) plus o1-/o1./o3-/o3. prefixes, and the comment explicitly excludes gpt-5.x variants that support temperature. The default gpt-5-mini is not in the set, so it goes through full sampling params. See LLM providers.
Azure providers rewrite "assistant" → "ai" in the last message
Both AzureOpenAILLM and AzureOpenAIStructuredLLM run user_prompt.replace("assistant", "ai") on the final message before sending — an undocumented quirk that can mangle legitimate content containing the substring "assistant". See LLM providers.
reasoning_effort is lost when passing a BaseLlmConfig object
In LlmFactory.create, converting a BaseLlmConfig object to a provider-specific config copies only a fixed attribute list (model, temperature, api_key, max_tokens, top_p, top_k, enable_vision, vision_details, http_client_proxies). reasoning_effort is not in that list, so a base-config object can silently drop it; the dict path is safe because it spreads the whole dict. See the config system.

Evaluation harness traps

  • The in-repo harness only covers LoCoMo. run_experiments.py hard-codes dataset/locomo10.json for every technique; the headline LongMemEval (94.8) and BEAM (64.1/48.6) numbers come from the external mem0ai/memory-benchmarks repo, not this tree. See evaluation.
  • Category 5 is silently dropped from scoring. Both evals.py and metrics/llm_judge.py continue when category == 5 (LoCoMo's adversarial/unanswerable class), so reported accuracy excludes those questions even though the runner records adversarial_answer. See evaluation.
  • The LLM judge is the real headline metric. LoCoMo gold answers are terse and generated answers verbose, so BLEU/F1 under-report; the GPT-4o-mini judge at temperature 0 is what the 91.6/94.8 numbers actually measure. See evaluation.
  • store_true flags ignore their argument. --filter_memories False still evaluates to True — the README "False" is the absence-of-flag default, not a passable value. See evaluation.
  • LangMem's error path raises UnboundLocalError. Its except block returns t2 - t1, but t2 is assigned only in the try before the failing call, so the handler itself crashes. Several baselines also don't hit live APIs: the OpenAI baseline reads pre-dumped memories/{idx}.txt and returns a hard-coded search time of 0; Zep ingests only idx == 0. See evaluation.

OpenMemory pitfalls

  • PUT /api/v1/config/ silently discards the update. update_configuration() builds updated_config but never calls save_config_to_db() and returns None. The working paths are PATCH / and the granular /mem0/llm, /mem0/embedder, /mem0/vector_store, /openmemory setters. See OpenMemory.
  • MCP search bypasses the engine retrieval pipeline. search_memory does not call memory_client.search(); it manually embeds the query and calls vector_store.search() with limit=10, sidestepping reranking, score fusion, and entity linking. MCP search returns raw vector hits, not the engine's fused ranking. See OpenMemory.
  • Auto-categorization is hard-wired to OpenAI. categorization.py instantiates a bare OpenAI() client and always calls gpt-4o-mini regardless of the configured provider, so categorization needs OPENAI_API_KEY even on Ollama/Anthropic setups. It runs inside SQLAlchemy after_insert/after_update listeners on a separate Session. See OpenMemory.
  • Schema is owned by both create_all and Alembic. main.py calls Base.metadata.create_all() at import, so fresh installs build from ORM models while the Alembic chain is a separate manual mechanism. A model change not also encoded as a migration appears on new installs but never on upgraded ones. (Migration Create Date docstrings are decorative — only down_revision defines chain order.) See OpenMemory.

Client / proxy

  • The async client validates its API key with a blocking call in __init__. AsyncMemoryClient._validate_api_key() uses the synchronous requests library, called directly from the constructor, so building the async client performs one blocking network round-trip before any await; only later operations use the non-blocking httpx.AsyncClient. See the hosted client.
  • Endpoint paths straddle v1/v2/v3. Memory add/read/search use /v3/; per-ID ops, history, batch, exports, feedback, entity listing use /v1/; entity deletion uses /v2/entities/; project/webhook management uses /api/v1/. The option-model docstrings still say "v2 API" for search/get_all despite posting to v3. See the hosted client.
  • delete_linked is the delete-side counterpart of latest_only. delete(memory_id, delete_linked=True) transitively removes the older memories a memory superseded (the v3 linked_memory_ids chain) so a superseded memory cannot resurface. It's normalized via {'delete_linked': delete_linked or None} so the param is omitted when False. See the hosted client.

Security surprises

Both the hardening that's quietly correct and the import-time footguns that aren't.

Two packages can pip-install themselves at import time If ollama is missing, mem0/embeddings/ollama.py runs input("…Install it now? [y/N]") and shells out to pip install ollama at import. mem0/proxy/main.py does the same for litellm at module load, exiting the process on failure. In a non-interactive/locked-down server these block on stdin or install packages at runtime — surprising side effects for a bare import.
Telemetry hashes identifiers and samples hot paths
process_telemetry_filters MD5-hashes user_id/agent_id/run_id into encoded_ids and reports only filter key names. Lifecycle events fire at 100%; hot-path events obey MEM0_TELEMETRY_SAMPLE_RATE (default 0.1, clamped to [0,1]). MEM0_TELEMETRY=False disables everything; mark_aliased stores an SHA-256 of anon_id+email, never the plaintext email. See the engine.
At-most-one admin enforced at the DB layer
Migration 004_unique_admin_role.py adds a partial unique index on users(role) WHERE role='admin'. Combined with register()'s "registration closed once any user exists" guard and an IntegrityError rollback, the first registrant becomes the sole admin and the endpoint locks shut. See the server.
Constant-time login to avoid email enumeration
login() calls dummy_verify_password() (pwd_context.dummy_verify) when the email is not found, burning the same bcrypt cycles as a real verify so response timing does not leak whether an account exists. See the server.
SQL-injection-safe rich pgvector filter operators
OPERATOR_SQL_MAP + _build_filter_conditions compile eq/ne/gt/gte/lt/lte/in/nin/contains/icontains plus $or/$not and a '*' key-exists sentinel into parameterised SQL over the JSONB payload. contains/icontains escape backslash/%/underscore and add ESCAPE '\'. PR #5264 fixed boolean filter casing (json.dumps → true/false to match JSONB) and added LIKE wildcard escaping; earlier #4997 closed SQL injection via psycopg.sql.Identifier and bound params. See the server and vector stores.
Upstream errors are classified by walking the exception chain
errors.py _classify walks __cause__/__context__ so wrapped provider errors still map to stable codes (provider_auth_failed, provider_rate_limited, vector_store_unavailable, …), returning HTTP 502 with a request_id and no stack trace. See the server.
LLMReranker prompt-injection hardening
It truncates query and document to _MAX_INPUT_LEN = 4000 chars and sends instructions as a system message with memory text in the user role, so stored text cannot override scoring instructions. See rerankers.
OpenMemory has no auth and open CORS by design allow_origins=['*'], no API keys, a single implicit user, and MCP identity carried only in the URL path (/mcp/{client_name}/.../{user_id}) — i.e. spoofable. Acceptable for a localhost single-user tool, unsafe for shared/networked hosting; use server/ for that. Separately, mem0 agent-rush memories are public to other players — the CLI gates the first add on an explicit y and prints the PII warning to stderr for non-TTY agent runs. See OpenMemory and Integrations.

Deprecations & migrations

Where the code disagrees with its own docs, and what to migrate away from.

Graph memory is removed, not just deprecated There is no mem0/graphs/ directory, no graph_memory.py/memgraph_memory.py/kuzu_memory.py, no graph references in mem0/memory/main.py, no graph_store field on MemoryConfig, and no graphs/ in the TS OSS tree. The enable_graph/graph_store (and enableGraph/graphStore) config keys are silently ignored, not honored. Relationship awareness is now a lazily-created {collection}_entities vector store via VectorStoreFactory plus spaCy/compromise NLP — verified by counting zero graph-store providers in mem0/utils/factory.py. See graph memory (deprecated).

Graph-memory residue and naming traps

  • The relations field is a silent breaking change. search()/get_all() no longer populate the old relations key, and relationships are not exposed as a queryable graph. Apps that traversed triples directly have no drop-in equivalent. See graph memory.
  • Graph memory used to double LLM cost. A configured graph store ran a second LLM extraction pass per add() to mint triples (with a ThreadPoolExecutor fan-out). V3 entity extraction uses local spaCy NLP with zero extra LLM calls. See graph memory.
  • "Entity graph" is conceptual, not a graph DB. Prompts and the migration guide still say "entity graph boost" / "build a graph of related memories," but there is no graph database or traversal — only memory-to-memory links in payload fields scored at retrieval time. sanitize_relationship_for_cypher() and remove_spaces_from_entities() survive in mem0/memory/utils.py (and are tested), but remove_spaces_from_entities has no non-test caller — vestigial. See graph memory.
  • Neptune survives as a vector store, not a graph store. mem0/vector_stores/neptune_analytics.py remains as a vector index provider, distinct from the removed Neptune graph adapters. Same vendor, different feature. The self-hosted server/docker-compose.yaml defines only mem0, postgres (ankane/pgvector), and mem0-dashboard — no Neo4j/APOC. See graph memory and the server.

Dormant prompts & config fields

  • Legacy two-call prompts still ship but are dormant. prompts.py still defines FACT_RETRIEVAL_PROMPT, USER/AGENT_MEMORY_EXTRACTION_PROMPT, DEFAULT_UPDATE_MEMORY_PROMPT, and get_update_memory_messages — referenced only by memory/utils.py, NOT wired into the active _add_to_vector_store path (which uses only ADDITIVE_EXTRACTION_PROMPT). PROCEDURAL_MEMORY_SYSTEM_PROMPT remains live. See the algorithm.
  • MemoryConfig has custom_instructions, not custom_fact_extraction_prompt. There is no custom_fact_extraction_prompt or custom_update_memory_prompt field on MemoryConfig; the latter exists only as a parameter of the dormant get_update_memory_messages(). At add() time a per-call prompt= argument overrides it (custom_instr = prompt or self.custom_instructions). See the config system.

Provider-level deprecations

  • OPENAI_API_BASE is deprecated — OpenAIEmbedding emits a DeprecationWarning, slated for removal in 0.1.80; use OPENAI_BASE_URL. See embeddings.
  • scoring_prompt on LLMRerankerConfig is deprecated — if supplied it is now used as the system message and emits a warning; the built-in banded rubric prompt is preferred. See rerankers.
  • get_project/update_project are deprecated in favor of client.project.get()/update(), slated for removal in package v1.0; the surfaces aren't perfectly aligned (memory_depth/usecase_setting exist only on the legacy methods). See the hosted client.
  • Server /search deprecated top-level identifiers — PR #5263 stopped splatting the whole SearchRequest into Memory.search(); top-level user_id/agent_id/run_id are now merged into filters and only top_k/threshold forwarded, fixing a 502 when identifiers and filters were passed together. See the server.
Deep dive: stale docs to ignore
  • AGENTS.md provider counts are stale. It advertises 24 LLMs / 30 vector stores / 15 embeddings / 4 graph stores / 5 rerankers. Counting actual factory-registered modules in mem0/utils/factory.py (excluding base/configs/__init__/utils/mock) yields 18 LLMs, 24 vector stores, 11 embeddings, 5 rerankers, and zero graph stores. See architecture.
  • The OSS TS README is stale. src/oss/README.md shows import {`{ Memory }`} from "mem0-ts" (wrong package name — it's mem0ai/oss), a legacy positional add("text","user123") signature, and advertises "Optional graph-based memory relationships" — none of which match the code. See the TypeScript SDK.
  • The CLI [oss] extra is unwired. cli/python/pyproject.toml declares oss = ["mem0ai>=0.1.0"] and help text advertises --graph, but get_backend() unconditionally returns PlatformBackend; there is no OssBackend, and --graph appears only in the static _build_help_json() dict, not on live commands. See Integrations.

Design decisions

Deliberate structural choices that explain why the code is shaped the way it is.

One ADD-only LLM call replaces extract-then-diff
The pre-v3 algorithm used two LLM calls (extract facts, then diff against existing state for ADD/UPDATE/DELETE/NONE). The April-2026 algorithm collapses this into a single ADD-only call with mechanical MD5 dedup. This is the root cause of nearly every "dead branch" gotcha above and the temporal-reasoning win. See the algorithm.
The factory's provider_to_class is the source of truth, not __init__.py
Category __init__.py registries are partial: mem0/reranker/__init__.py re-exports only 3 of 5 rerankers (the rest work via lazy dotted-path import), and mem0/llms/__init__.py is empty. To enumerate real support, read the factory dicts. Note also the directory/naming traps: the reranker dir is mem0/reranker/ (singular) with _reranker-suffixed files, while its config classes live under mem0/configs/rerankers/ (plural); factory keys are llm_reranker (not llm) and sentence_transformer (singular). See rerankers and the config system.
Asymmetric config wrappers: only VectorStoreConfig eagerly types its inner config
LlmConfig and EmbedderConfig keep their inner config as a raw dict (the validator only checks the provider name); VectorStoreConfig's @model_validator(mode='after') immediately instantiates the typed provider config class. That's why the engine can read self.config.vector_store.config.collection_name as an attribute while LLM/embedder configs stay dicts until factory time. Consequence: dict-style and object-style configs are not perfectly interchangeable — the default path=/tmp/{provider} injection for file-backed stores only happens for dict configs. See the config system.
memory_action is plumbed everywhere but only Vertex AI uses it
The engine tags every embed() call with add/search/update, but of 11 providers only VertexAIEmbedding branches on it (RETRIEVAL_DOCUMENT vs RETRIEVAL_QUERY vs SEMANTIC_SIMILARITY). It's a forward-looking hook the other 10 accept and ignore. (And the abstract embed() declares memory_action as a required positional with no default — every concrete provider redeclares it as =None, so a custom subclass copying the base signature literally would break callers that omit it.) See embeddings.
Two *_structured LLM providers, but only one truly parses
OpenAIStructuredLLM calls client.beta.chat.completions.parse for schema validation, but AzureOpenAIStructuredLLM still calls chat.completions.create — it's effectively a leaner copy of AzureOpenAILLM, not a real structured-parse path. See LLM providers.
Entity store reuses the primary vector provider
Memory.entity_store lazily creates a {collection}_entities collection via the same VectorStoreFactory provider; for embedded Qdrant it reuses the existing client object rather than opening a second connection, specifically to avoid RocksDB lock contention on the same on-disk path. No separate database is configured. See the engine and graph memory.
History migration is lossy by design
_migrate_history_table renames the old table, recreates the new schema, and copies only the intersection of old and new columns inside one transaction — legacy group-chat columns are dropped and new columns left NULL. See the engine.
No AsyncMemory/AsyncMemoryClient in TypeScript
Python duplicates every method into sync and async classes; the TS SDK has exactly one Memory and one MemoryClient because all methods already return Promises — a structural divergence, not a feature gap. TS heavy deps are all external peer dependencies (guarded by tsup-externals.test.ts) imported lazily; compromise NLP is optional with a pure-regex fallback. See the TypeScript SDK.
Proxy writes are fire-and-forget on a daemon thread
Completions._async_add_to_memory spawns a daemon thread calling mem0_client.add(...), so a slow/failed write never blocks the chat response — but failures are silent, and a memory written this turn is not guaranteed searchable on the immediate next turn. org_id/project_id are resolved server-side from the API key (via /v1/ping/) and intentionally never injected into memory params. See the hosted client.
Self-hosted runtime config persists to DB and layers over .env
server_state.py keeps a single process-global Memory behind an RLock; POST /configure deep-merges and upserts overrides into a settings table. On restart, persisted overrides re-apply on top of .env-derived defaults — but a bundled-provider allowlist (BUNDLED_LLM_PROVIDERS, BUNDLED_EMBEDDER_PROVIDERS) returns 400 for providers whose package isn't in the image. See the server.
The "Proof-Editor honesty" pattern in Agent Mode agent_detect.detect_agent_caller() recognises CLAUDECODE/CURSOR_AGENT/CODEX_CLI env vars only as a context trigger to enable auto-bootstrap; the canonical agent_caller identity is always self-declared via --agent-caller or mem0 identify, never sniffed from env. Likewise plugin_sync only edits existing config entries via atomic tmp+rename and never creates new ones — deliberately conservative about clobbering unrelated config. See Integrations.
